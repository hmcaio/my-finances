# Shared components (`src/components`)

Read when building a list page, an error banner, a confirmation, a month field or pagination. Use these instead of re-inlining the markup; each replaced copy-pasted code from every settings/list page. The responsive set (`ResponsiveTable`, `ResponsiveDialog`, `ResponsiveFilterBar`) is in [frontend-responsive.md](frontend-responsive.md).

- `ErrorAlert`: dismissible error banner; renders nothing for a `null` message. `AccountDetailPage`'s banner is intentionally _not_ this (non-dismissible, different spacing).
- `InlineEditActions`: the pencil -> check/X trio for an inline-edit table row; `editLabel` is required (labels differ per page), `saveLabel` defaults to "Save", `saving` disables save/cancel. Its state is `useInlineEdit(emptyDraft)` (`hooks/`): `editingId`, `draft`/`setDraft`, `start(id, draft)` and `cancel()` (clears the row and resets the draft; call it after a successful save too, a failed save keeps the row open). `saving` is `useAction(setError).pending` ([frontend-data-loading.md](frontend-data-loading.md)).
- `ConfirmDialog`: destructive-action confirmation (delete/close/dismiss). A dialog containing a form is not a fit; keep those custom.
- `PaginationControls`: Previous/"Page X of Y"/Next for a `PagedModel`. `onPageChange` takes a functional updater (pass `setPage` directly) so rapid clicks stay correct against React's latest state; its `sx` overrides the default embedded-list spacing for standalone pages.
- `DataTableBody`: the `<TableBody>` for every list table: skeleton rows while loading, a "Could not load data (...)" row with Retry if the first fetch failed, real rows (fade-in) otherwise. Takes `state` (a `LoadState` from `useQueryState(query)`, or several merged with `combineLoadState`). `columns` must match the header; set `actionsColumn` when the last column holds icon buttons, so placeholder rows match the real row height.
- `FormDialog` (`feedback/`, F040): the shell of a form dialog, and what a new form dialog uses. It wraps `ResponsiveDialog` so the paper is a `<form noValidate>`: Enter in a single-line field submits the primary button (`type="submit"`, label from `submitLabel`), and the browser's own validation bubble never shows. Props: `open`, `title`, `onClose`, `onSubmit`, `canSubmit`, `busy`, `submitLabel`, `error`/`onDismissError`, `extraActions` (rendered between Cancel and the primary button) and the fields as `children`. The handler runs `onSubmit` only while `canSubmit && !busy`, so Enter does nothing on an invalid or saving form whatever the browser does with a disabled submit button; the primary button stays disabled until the draft is valid (no inline error machinery). Rules for the fields: **mark every field that must be filled for the primary button to enable with `required`** (MUI adds the asterisk; a `Select` that shows a placeholder `MenuItem` instead of a label gets `required` plus ` *` after the placeholder text), **give the first field `autoFocus`** (the first field the user must fill, not a pre-filled one: the Record snapshot dialog focuses Balance, not the pre-filled Date), and do not hand-code an `onKeyDown` Enter handler: the shell covers it. `autoFocus` on a text input inside any MUI `Dialog` does not stick under the Vite dev server (`npm run dev`, the `full` profile): `StrictMode` runs the focus trap's effect twice, and its simulated cleanup hands focus back to the button that opened the dialog before the dialog's own focus moves to the paper. A production build and the jsdom tests are unaffected (a `Select` with `autoFocus` keeps its focus even in dev, since it focuses itself later); do not try to fix it per dialog, and check autofocus against a build or with `StrictMode` removed temporarily. The shell renders the "Fields marked * are required" hint (`common:form.requiredHint`) at the end of the scrolling body, never in the actions row. A test that finds a required field by label uses `getByRole('textbox' | 'spinbutton', { name })` (the asterisk is `aria-hidden`, so the name stays clean) or a regex, because `getByLabelText('Name')` no longer matches the label text `Name *`. Migrated so far: `AddFormDialog` (below), the Record snapshot dialog (`SnapshotDialogs`) and the Ledger's New entry dialog (`EntryDialog`, via `FormDialogPane` below); the older form dialogs still on a bare `ResponsiveDialog` move over one page at a time.
- `FormDialogPane` (`feedback/`, F040): the same body and actions as `FormDialog` (`FormDialogSections`: fields, the required hint, Cancel / `extraActions` / the `type="submit"` primary button) inside a `<form noValidate>` of its own instead of the dialog paper, for a dialog the caller owns whose form changes while it stays open (the New entry dialog swaps its form when the type toggle moves; each form owns its submit). It is a flex column (`flex: 1 1 auto`, `minHeight: 0`), so the body still scrolls and the actions stay put in a full-screen phone dialog. Same rules as `FormDialog`: Enter submits only while `canSubmit && !busy`, `extraActions` buttons are `type="button"`. A dialog with one fixed form uses `FormDialog`, not this.
- `EntryDialog` (`features/ledger/components`, F040): the Ledger's one create/edit dialog for an expense, an income or a transfer. `useEntryDraft` (state) over the pure rules in `lib/entryDraft.ts` holds the type, the transaction draft Expense and Income share (so `TransactionForm`, in `features/transactions`, is controlled by it), the transfer form's seed and the date and account that travel on a switch (the transfer form reports them through `TransferForm`'s `onCarryChange`). The transfer form owns its own state and is remounted from the seed (`key`) on a switch to it and after "Add and new". **"Add and new"** (create only, never for a trade confirmation) saves and keeps the dialog open: `TransactionForm` focuses Amount and `TransferForm` (`focusDescriptionOnMount`) Description with an explicit `focus()` call, because `autoFocus` does not stick on dialog open under the dev server (above). Enter submits "Add", never "Add and new" (a button that is not the form's first submit button). Edit mode passes the full record (`editingTransaction` / `editingTransfer`): the type is fixed and the toggle is hidden. A new dialog that creates several kinds of record follows this split, not a second dialog per kind.
- `AddFormDialog` (`feedback/`) + `useAddDialog` (`hooks/`): the "Add" dialog of a settings-style page (Institutions, Categories, Vehicles, Budgets, Recurring templates), built on `FormDialog`. The shell (title, error banner, `FormGrid`, hint, Cancel/Add, Enter to submit) is shared, the fields stay in the page (mark them `required`, `autoFocus` the first); `useAddDialog(emptyDraft).close` resets the draft, so Cancel, Esc and a saved add all reopen empty (a failed save keeps the draft). A new page-level add dialog uses both rather than its own `useState` per field. A form that owns its state (`AccountCreateForm`, `InvestmentProductForm`) is not wrapped in it.
- `ReadOnlyNameListPage` (`layout/`): the page for a fixed, name-only taxonomy with no add/rename/delete (payment methods, investment segments; ADR 0028). Pass already-translated `title`/`description`/`emptyText`, the query and a `displayName` (the `translateSeedName` call), so each page keeps its own i18n namespace. A taxonomy with real editing (Categories, Institutions, Vehicles) or nesting (investment categories) is not a fit.
- `LoadFailedNotice`: inline "could not load" text + Retry; for non-table blocks (the `BudgetsPage` report).
- `MonthPicker` (`inputs/`): the `<input type="month">` field shared by every month-scoped view (`BudgetsPage`'s report month, `AllocationPlanEditor`'s effective-from, F026's `FiiPage`). `clampToCurrentMonth` (default off) clamps a selection past the current month back to it and caps the native picker with `max`: set it only where there's no future data to show (the FII page); omit it where a future month is meaningful (a plan's effective-from, which can be set ahead; a budget report month, which isn't clamped either).
- `MonthNavigator` (`inputs/`, F037): `‹ month ›` (previous/next `IconButton`s around `MonthPicker`, unclamped so a future month is reachable) for a view that steps through months, `value`/`onChange` in `YYYY-MM`; `shiftMonth`/`monthRange` in `utils/localDate` do the month arithmetic without `Date`/UTC conversion. The Ledger keeps its month in the URL, the account page's embed in local state.
- **Layout primitives** (`components/layout/`, issue #259) for the markup every page repeated; use them instead of re-inlining the `sx`:
  - `Layout` owns the page's one `main` landmark, `id="main-content"` and `tabIndex={-1}`, the target of its "Skip to content" link (F040): a page renders no `main` of its own.
  - `PageContainer`: the root of a routed page (`py: { xs: 2, sm: 4 }`).
  - `PageHeader`: the title row of a list page, `title` as the `h1` (h4 style) with the actions (an "Add" button, its menu) as children; the row wraps (`flexWrap: 'wrap'`) so an action drops under the title on a phone instead of squeezing it; `sx` merges after the base. A page with a title and no action keeps a plain `Typography variant="h4" component="h1"`.
  - `PageSection`: an outlined `Paper` with the section padding (`SECTION_PADDING`, 16px on a phone, 24px from `sm`); `sx` adds `mb: 3` or `maxWidth: 480`.
  - `FormDialogContent` (`feedback/`): `DialogContent` plus the `pt: 1` wrapper that keeps the first field's floating label from being clipped; the error banner and `FormGrid` go inside it.
  - `layout/layoutSx.ts` constants: `WRAP_ANYWHERE` (long text wraps instead of widening its container; spread to combine: `{ ...WRAP_ANYWHERE, mb: 2 }`), `SELECT_MIN_WIDTH` (a compact `Select`), `FORM_GRID_FULL_ROW` (a `FormGrid` child spanning every column), `SECTION_PADDING`.
  - A one-off spacing prop (`mb: 3`, `pt: 1`) or a `Paper` with a single padding value stays inline `sx`: a primitive needs 4+ identical uses and a name that says more than the props. Tests assert responsive `sx` through `emittedCss`/`emotionClass` (`src/test/utils/emittedCss.ts`), since jsdom does not evaluate `@media`.
- `NotificationHost` (`providers/notifications/`, F040): the success toast, a MUI `Snackbar` + `Alert severity="success" role="status"` that hides after 4 s and is rendered once by `Layout` (a jsdom test that renders `Layout` needs no extra wrapper: the store is module-level and `src/test/setup.ts` resets it after each test). It sits at the bottom start from `sm` up (beside the permanent drawer from `lg`, `DRAWER_WIDTH` in `layoutSx.ts`, so it never covers a nav item) and at the top on a phone, over the app bar and with `pointer-events: none`, so it never covers a dialog's bottom actions or the page's "Add" button; a second message replaces the first. The toast is portalled into a `div` of its own that is a child of `body` (`useAnnouncementHost`), not left inside `#root`: while any MUI modal (a `Dialog`, a `Menu`, a `Select` list) is open, the modal manager sets `aria-hidden="true"` on every other `body` child, and a toast in that subtree is not announced by a screen reader ("Add and new" keeps the dialog open, and a plain "Add" toasts before its dialog closes). MUI has no opt-out for it (no ignore attribute, one manager shared by all modals), and a node created after the modal opened is hidden again by the next modal, so the host exists from mount on and a `MutationObserver` drops the attribute whenever it appears on it; the dialog still hides `#root`. A new element that must be announced while a dialog is open (a live region) needs the same treatment, and a test for it renders the element beside an open `Dialog` and finds it with `getByRole` (`NotificationHost.test.tsx`; the role query respects `aria-hidden`). Do not render a `Snackbar` per page: set `meta.successMessage` on the mutation ([frontend-data-loading.md](frontend-data-loading.md)); `publish(message)` from `notificationStore` is for the query client, not for components.
- `LedgerTable` (`features/ledger/components`, F037): the one list of transactions and transfers, shared by `LedgerPage` and the read-only `AccountLedger` embed (omit `onEdit`/`onDelete` for read-only, pass `embedded` inside an outlined section). A row is told apart by icon, sign and colour from `ledgerEntryStyle` (never colour alone; theme tokens only), and its name cells come from `useLedgerLookups`, which also supplies the combined load state. A new view of ledger rows reuses it instead of re-declaring columns.
