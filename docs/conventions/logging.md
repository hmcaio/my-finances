# Logging (both stacks)

Rationale: ADR 0011; design: `docs/features/F016-logging/spec.md`. Boot `logging.*` properties only: no `logback-spring.xml`, no new dependency. The headline rule (ids and counts only) is in root `CLAUDE.md`; this file holds what to log, where, and the leak traps.

## Cross-stack: request id

The frontend sends `X-Request-Id` (`crypto.randomUUID()`) on every Axios request, nginx fills one in if it's missing and forwards it, and the backend accepts it only if it matches `^[A-Za-z0-9-]{1,64}$` (else generates its own), puts it in the MDC and echoes it back, so one failing click can be followed browser console -> nginx -> backend log.

## Backend

- **Where things are configured**: `application.yml` holds what is identical everywhere: the `[%X{requestId:-}] ` correlation pattern, the rolling caps (50MB per file, 90 days, 300MB total, gzip), and two guards against Spring logging values we never want (below). `application-dev.yml`: `com.chm.myfinances` at DEBUG, file `logs/backend.log` (`backend/logs/` under `bootRun`, gitignored). `application-prod.yml`: INFO, file `/var/log/my-finances/backend.log`, level overridable via `LOGGING_LEVEL_COM_CHM_MYFINANCES` (`LOG_LEVEL` in compose). Profile-specific values stay out of the base file. The rolling caps aren't wired to compose variables (set-and-forget, and `application.yml` stays their single source of truth); to change one, add an env var to the backend service via Boot's relaxed binding (`LOGGING_LOGBACK_ROLLINGPOLICY_MAX_FILE_SIZE`, `LOGGING_LOGBACK_ROLLINGPOLICY_MAX_HISTORY`, `LOGGING_LOGBACK_ROLLINGPOLICY_TOTAL_SIZE_CAP`) and recreate the container. `max-history` is applied first and the size cap second, so the cap can evict logs younger than `max-history`.
- **Reading prod logs**: they live in the `my-finances-logs-prod` volume (explicit `name:` in compose). Without the app: `docker run --rm -v my-finances-logs-prod:/logs alpine sh -c 'ls /logs; tail -n 200 /logs/backend.log'`; with it running: `docker compose -f docker-compose.prod.yml exec backend tail -n 200 /var/log/my-finances/backend.log` (Git Bash on Windows rewrites that path: prefix `MSYS_NO_PATHCONV=1`). Logs survive `stop`/`down`/image updates; `docker compose down -v` (which also wipes the database) or `docker volume rm` removes them, and files older than 90 days or beyond the 300MB total (whichever comes first) are deleted by design.
- **Tests never write a log file**: `build.gradle`'s `tasks.named('test')` sets the system property `logging.file.name` to `''`: tests run under the default `dev` profile, whose file name would otherwise create `backend/logs/`.
- **Request id**: `infrastructure/web/RequestLoggingFilter` (highest precedence) puts `requestId` in the MDC, echoes it as `X-Request-Id`, and writes one access line per request (method + path, never the query string or a body; `/actuator/**` at DEBUG because the prod healthcheck hits it). It accepts an inbound id only if it matches the pattern above, else takes one from `IdGenerator`, never `UUID.randomUUID()` (ADR 0005).
- **`GlobalExceptionHandler` logging is unchanged by F031's `ProblemDetail` body**: unexpected exception -> ERROR with the stack trace; a `@ResponseStatus` exception -> INFO with its class simple name only (the response's `type` is derived from that same name, so this isn't a new leak surface, but the log line is still the only place to see the exception's *message*, which the response never carries). Exception messages stay out of both.
- **Log statements**: never in `domain/` (`ArchitectureTest` enforces it); application services use a plain `private static final Logger log = LoggerFactory.getLogger(X.class)`, not Lombok `@Slf4j`. Log only state-changing events at INFO (cascades, generated data, new versions); plain CRUD is already covered by the access line. Never log inside a loop over a table.
- **Spring's own log lines leak values unless silenced**: `DefaultHandlerExceptionResolver` always warn-logs `Resolved [...]` including a validation failure's `rejected value [-12.34]`, so `application.yml` sets its logger to ERROR; and `spring.mvc.log-resolved-exception: false` is pinned because DevTools (on the `bootRun` classpath, not in tests) turns it on, which warn-logs every `@ResponseStatus` exception's message (entity names).
- **SQL**: `spring.jpa.show-sql` stays off; for ad hoc query debugging set `LOGGING_LEVEL_ORG_HIBERNATE_SQL=DEBUG`. **Never enable `org.hibernate.orm.jdbc.bind`** (TRACE): it prints bound parameters, i.e. amounts and descriptions.
- **Known leak, accepted**: an ERROR stack trace includes the exception message, and Postgres constraint-violation messages can echo the failing row (`Failing row contains (...)`). The file keeps those traces up to 90 days, so redact before pasting a log into a public issue.
- **Auth** logs outcome and failure count only ([auth.md](auth.md)).
- **Testing logs**: `testsupport/LogCapture` attaches a Logback `ListAppender` to one logger (try-with-resources) so a plain unit test can assert on level + formatted message without a Spring context. `LogCapture.of` forces the logger to TRACE; use `ofConfiguredLevel` in a `@SpringBootTest` to prove a `logging.level.*` setting really silences a third-party logger.
- **`audit_log` is not log output**: it holds amounts, descriptions, notes and entity names by design (F025, ADR 0022); `AuditRecorder` and the audit adapter must never echo those fields to a log line ([transactions-and-audit.md](transactions-and-audit.md)).

## Frontend

Browser logs are console-only; nothing is shipped to the backend.

- **Use `logger` (`src/utils/logger.ts`)**: ESLint `no-console` is an error everywhere except that file. `logger.error('what failed', err)`: pass an `Error` as context, not its message. Request/response bodies, amounts and descriptions stay out of every log call.
- **Level**: `VITE_LOG_LEVEL` (`debug | info | warn | error | silent`; `.env.development` debug, `.env.production` warn, `.env.test` silent; unknown -> `warn`). `localStorage.setItem('logLevel', 'debug')` in devtools overrides it at runtime, which is how you turn debug on in the prod build. Tests are silent by default: to assert on logging, `vi.spyOn(logger, 'warn')`, or `setLogLevel(...)` / `vi.stubEnv('VITE_LOG_LEVEL', ...)` to see real console output.
- **HTTP logging is owned by the interceptors in `src/api/core/client.ts`**: call sites and hooks do not log failed requests. They send a per-request `X-Request-Id` (the backend echoes it into its log, nginx into its own), log 4xx at `warn` and 5xx/no-response at `error`, and re-reject the original error untouched so `unwrap()` behaves as before.
- **Uncaught errors**: `installGlobalErrorLogging()` (window `error` + `unhandledrejection`) and `reactRootErrorHandlers` (`createRoot` options) are wired once in `main.tsx`. `ErrorBoundary` wraps the routed page inside `Layout` (`App.tsx`, keyed on the pathname so navigating away resets it) and deliberately doesn't log: `createRoot`'s `onCaughtError` already receives everything a boundary catches.
- Testing gotcha: dispatching an `ErrorEvent` that carries an `Error` on `window` when no listener of ours is attached makes Vitest report an unhandled test error.
