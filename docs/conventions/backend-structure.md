# Backend layout and shapes

Read when adding an aggregate, use-case service, repository adapter, query object, port or endpoint.

## Layering and what ArchUnit already enforces

Layer-then-context packages: `com.chm.myfinances.{domain,application,infrastructure}`, one subpackage per aggregate (ADR 0004). `domain/shared` holds the `IdGenerator` port (ADR 0005) and `TextFieldConstraints`. `infrastructure/persistence` holds the `AuditableEntity` base every table-backed entity extends.

`ArchitectureTest` (and `TestConventionsTest`) fail the build, so the code is the reference, not this file, for: no logging/slf4j in `domain..`; no domain dependency on Spring/Jakarta/Lombok (one documented exception, `TransactionRepository`/`TransferRepository` use Spring Data `Page`/`Pageable`); domain packages never import another aggregate's package; one `@RestControllerAdvice` and no `@ExceptionHandler` outside it; `UUID.randomUUID()` only in `RandomUuidGenerator` and no `@GeneratedValue` (ids come from `IdGenerator`); every `@Entity` extends `AuditableEntity`; `JpaRepository` interfaces are package-private; unique handler method names per controller; write use cases depend on the audit port; no `csrf()`/`user()` MockMvc post-processors in tests.

The one documented cross-aggregate domain import: `domain.transaction.Transaction` depends on `domain.category.CategoryType`, a denormalized field captured at creation (see `Transaction`'s javadoc). Cross-aggregate checks (category exists and is `EXPENSE`, account is open, ...) happen in the application service via the other aggregate's repository port. Domain constructors re-check their own invariants anyway as defense in depth.

## Shapes

- **Use-case service**: one `@Service` per aggregate, constructor-injected with its repository port(s) and, when it creates entities, `IdGenerator`. Plain use-case method names (`create`/`rename`/`delete`/`findAll`, not generic CRUD verbs). `findById(...).orElseThrow(...)` throws `{Aggregate}NotFoundException` (`@ResponseStatus(NOT_FOUND)`) in the same package.
- **Repository adapter** (`infrastructure/persistence/<aggregate>`): package-private Spring Data `JpaRepository`, a `@Component` adapter implementing the domain port and translating via `reconstitute(...)`, and a JPA entity extending `AuditableEntity` with Lombok `@Getter`/`@Setter`/`@NoArgsConstructor` (Lombok is fine here; ADR 0005 only forbids it on domain classes).
  - **Replacing a value-object child table wholesale (delete-then-insert) deletes via a bulk `@Modifying @Query`, never a derived `deleteBy...` method** (F026: `AllocationPlanEntryJpaRepository.deleteByVersionId`, replacing a version's `AllocationPlanEntry` rows on every `save`). A derived delete loads matching rows then schedules per-entity removal for the next flush; Hibernate flushes pending inserts before pending deletes, so inserting the fresh rows right after hits the still-present old ones' `UNIQUE` constraint. A bulk query executes immediately, so the delete is visible before the inserts run.
- **Query object** for a computed-not-stored value that other features' tables feed into (`AccountBalanceQuery`, `BudgetCapQuery`, `BudgetReportQuery`, `RecurringTemplateCurrentVersionQuery`): an application-layer class beside the service, read-only. When the computation reads only the one aggregate instance passed in and needs no repository at all (`FuelRatiosQuery`, F024: km/L, spend/km, L/km from one `Transaction`'s own fields), it's a plain static utility instead of a `@Service` bean: a response DTO's static `from(...)` factory calls it directly, the same shape every other response DTO already uses, rather than threading a service through the controller just to hand it to the DTO.
- **Domain port for a cross-feature side effect**: an aggregate announces something through a port it owns (`domain/account/AccountClosedNotifier`) and the reacting feature implements it (`infrastructure/recurringtemplate/RealAccountClosedNotifier`), so the announcer never depends on the reactor.
- **Read-only port with no domain aggregate behind it at all** (`application/backupstatus/BackupStatusPort`, F018): when there's no table and no entity (the F018 sidecar's `status.json` marker is owned and written by a separate shell-script codebase, read through a mounted file) there's no `domain/` package either, just the port (`application/`) and its one adapter (`infrastructure/backupstatus/FileBackupStatusAdapter`, reading `myfinances.backup.status-path`/`BACKUP_STATUS_PATH`, default `/backups/status.json`). A missing/unreadable/malformed file is `Optional.empty()`, never an exception. The adapter builds its own `ObjectMapper` (with `JavaTimeModule`) rather than `@Autowired`: this app has no general-purpose `ObjectMapper` bean, the same reason REST-layer tests build one by hand ([backend-testing.md](backend-testing.md)).

## Endpoints

- **Update endpoints** are `PATCH` with a full-replace body (every editable field required).
- **List endpoints**: `PagedModel` (`{content, page: {size, number, totalElements, totalPages}}`, Spring Data `Pageable` underneath) for tables that grow without bound (transactions, transfers); a plain list where the row count is inherently small (budgets, templates, pending occurrences). A filtered `PagedModel` list doesn't have to be a JPA `Specification`: when a filter dimension isn't a column on the entity itself (F023's investment product list filters by `accountId`/`status`, both read through `InvestmentHoldingRepository`, not the product table), filter/sort/paginate in memory over the existing repositories instead, the same "computed on read" style as a query object (`InvestmentProductService.findAll(filter, pageable)`, mirroring `FakeTransactionRepository`'s in-memory `Page` build): a local, single-user app never has enough rows for this to matter.
- Controller method names are never overloaded (operation ids are `<controller>_<method>`; enforced). Errors and `@ApiResponse` documentation: [errors.md](errors.md).

## Uniqueness and delete guards

- Names are unique (`UNIQUE` on `categories`/`payment_methods`/`accounts`/`institutions`/`investment_categories`/`investment_products` `name`, exact match, case-sensitive) via an application-layer `existsByName`/`existsByNameAndIdNot` check that throws `{Aggregate}NameAlreadyExistsException`. Investment sub-categories are unique per parent category (`existsByInvestmentCategoryIdAndName...`), never globally; investment products moved from per-account to globally unique in F022/ADR 0020 (the same instrument at two brokers is now one product with two `InvestmentHolding`s, not two products sharing a name).
- `CategoryService.delete()` rejects a category still referenced by a transaction, budget or recurring template (`CategoryInUseException`).
- Account deletion guard: [accounts-and-investments.md](accounts-and-investments.md).
