# Backend testing specifics

Read when writing a backend test beyond a plain domain/fake-based unit test: a `@SpringBootTest`, a REST test, a transaction-boundary, migration or concurrency test, or any fixture that creates a category, payment method, institution, investment category/segment or account. Strategy: ADR 0013, ADR 0010.

- **Spring Boot 4.x removed the test-slice annotations** (`@DataJpaTest`, `@WebMvcTest`, `@AutoConfigureMockMvc`, `@AutoConfigureTestDatabase`) and `TestRestTemplate`. Persistence and REST tests use full `@SpringBootTest` + `@Import(TestcontainersConfiguration.class)` + `@Transactional` (automatic rollback between tests). For REST tests build `MockMvc` by hand in `@BeforeEach` via `MockMvcBuilders.webAppContextSetup(webApplicationContext).build()` with a plain `WebApplicationContext` field and a locally-constructed `ObjectMapper` (there's no `ObjectMapper` bean); controller tests go through `MockMvcSupport.build` ([auth.md](auth.md)). `TestcontainersConfiguration` is `public` so any package can import it.
- **Two test tiers, split by the JUnit tag `integration`**: `test` excludes it, `integrationTest` runs only it. `@DatabaseIntegrationTest` and `@WebIntegrationTest` carry the tag; a `@SpringBootTest` class that doesn't use one of them (transactional, concurrency, migration, context tests) must add `@Tag("integration")` itself, or `TestTaggingTest` fails.
- Application-layer logic is unit-tested against the hand-written `testsupport/Fake*Repository` fakes, no Spring context. Fakes don't enforce DB constraints, so they need the same port methods as the real repository added by hand.
- **Exception: transaction-boundary tests must NOT be `@Transactional`.** To prove a service method's `@Transactional` rolls back a multi-write use case (`*ServiceTransactionalTest`), the test carries no class- or method-level `@Transactional`, or the service just joins the test's transaction and a same-transaction re-read still sees the un-rolled-back writes. Spy the downstream repository with `@MockitoSpyBean` on a *field* (not a method parameter), stub the *second* write to throw, then re-read through fresh repository calls. These tests commit real rows: clean up leftovers inline with a repository method you did *not* stub (`reset(spy)` first; custom derived `deleteBy...` queries need a caller-provided transaction, plain `deleteById` does not), and give fixtures with no delete port (categories/accounts/templates) unique names because they stay behind.
- **Seed rows collide with `UNIQUE` constraints in real-DB tests.** `V2` seeds categories/payment methods ("Groceries", "Rent", "Debit Card", ...) into the shared Testcontainers Postgres before any test runs, so rollback never removes them. Real-DB fixtures must not reuse those names (convention: a `" Test"` suffix) or any name a non-`@Transactional` test leaves committed.
  - `V14` flags the seeded `Other` (renamed "Other Expense") and "Other Income" categories as built-in the same way: never reuse those names, and never assume `categories` has no built-in row (one per type).
  - `V12` seeds the built-in institution ("No institution"): never reuse that name, and never assume `institutionRepository.findAll()` is empty or a fixed size. Because `accounts.institution_id` is `NOT NULL` with an FK, **any real-DB test that creates an `Account` needs a valid `institutionId`**: use `TestInstitutions.builtInId(institutionRepository)` (`testsupport`) or save a fixture institution first; a random UUID is rejected by the FK at flush.
  - `V13` seeds the investment taxonomy (categories "Fixed Income", "Variable Income", "Funds", "Pension (Previdência)", "International", "Crypto", "Other", and sub-categories such as "CDB" or "ETFs"): fixtures must not reuse those names (`" Test"` suffix) and no test may assume `investment_categories`/`investment_subcategories` are empty.
  - `V24` seeds `investment_segments` (Lajes Corporativas, Shoppings, Logística, Papel (Recebíveis), Híbrido, Fiagro, Hospitalar, Residencial, Outros, F034/ADR 0028): fixtures must not reuse those names and no test may assume the table is empty or a fixed size.
  - An `INVESTMENT` account is built with `Account.create(id, name, institutionId, AccountType.INVESTMENT, null, null)`; every other type still needs both opening values.
- **Testing a migration against pre-existing data** (the case a fresh migrate can't show, e.g. a dedupe before a new `UNIQUE`): run Flyway by hand into a throwaway schema of the shared container (`Flyway.configure()...schemas(...).target("N")`, insert the rows, migrate to `N+1`; `PendingOccurrenceCycleUniquenessMigrationTest`). Use a **non-pooled** `DriverManagerDataSource` built from the Hikari pool's URL/credentials: `Connection.setSchema` changes the physical connection's `search_path`, and on a pooled connection that leaks into the next test ("relation does not exist" once the schema is dropped).
- **A migration that enables a Postgres extension (`V25`, `unaccent`)** is database-wide, and the shared test database already has it, so the throwaway-schema pattern above proves nothing: `UnaccentMigrationTest` migrates a throwaway *database* of the same container (`CREATE DATABASE`, V1..V24 then V25, non-pooled connection) and drops it afterwards.
- **Concurrency tests** (`RecurringOccurrenceCatchUpConcurrencyTest`): no `@Transactional` on the class, release callers together with a `CyclicBarrier`, and hard-delete the committed fixtures afterwards through `JdbcTemplate` (children first): the domain has no delete port, and a leftover template breaks other tests that list or count templates (`findAll().hasSize(2)`), or, if active, generates pending rows in their catch-up runs.
- Log assertions (`LogCapture`) and the no-log-file test setting: [logging.md](logging.md).
