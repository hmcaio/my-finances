# Internationalization (F033, ADR 0027)

Read when adding or changing any user-visible string, number/date/money display, a translation namespace, a seeded taxonomy label or a fixed-enum label.

English + Brazilian Portuguese via `react-i18next`; full coverage is required at ship (no English fallback runtime path). Frontend-only: the backend sends no translatable text (ADR 0011, ADR 0026/F031, F032).

- **Locale provider**: `src/hooks/locale/{LocaleProvider.tsx,useLocale.ts}`, shaped exactly like `colorMode/{ColorModeProvider.tsx,useColorMode.ts}`. A context seeded once on mount from `localStorage.getItem('my-finances:locale')`, else `navigator.language` (`pt*` -> `pt-BR`, else `en`, default `pt-BR` when ambiguous), persisted back on every change, calling `i18next.changeLanguage(locale)` as the side effect (a `useLayoutEffect`, so a test that renders without `LocaleProvider` still sees the pre-effect `en` default on first paint). `useLocale()` throws outside the provider. `App.tsx` wraps `<LocaleProvider>` alongside `<ColorModeProvider>`; `Layout.tsx`'s header `IconButton` next to the dark-mode toggle calls `toggleLocale()`.
- **Namespace/key convention**: `src/i18n/locales/{en,pt-BR}/<namespace>.json`, one namespace per `src/features/<area>` folder plus `common` (nav, shared buttons/labels, shared component defaults) and `errors` (the two `apiError.ts` maps). Statically imported in `src/i18n/i18n.ts`'s `resources` object (no HTTP backend plugin: two locales' worth of JSON is trivial bundle weight) and typed in `src/i18n/i18next.d.ts`'s module augmentation against the canonical `en` resources, so an unknown/typo'd `t()` key is a compile error; `src/i18n/localeParity.test.ts` separately asserts every namespace's `pt-BR.json` has exactly the same key set (TS only checks against the one declared-canonical shape). **A namespace added to one must be added to all three** (`i18n.ts`, `i18next.d.ts`, both locale folders) or the type and the parity test go stale independently. `i18n.ts` sets `lng: 'en'` explicitly (matches jsdom's default `navigator.language` and this suite's long-standing English-by-default assumption for any component rendered without `LocaleProvider`) and `fallbackLng: 'pt-BR'` (only matters for a key genuinely missing, which full coverage means should never happen).
- **Formatter module** (`src/i18n/format.ts`): `formatMoney(amount, locale)` (2 decimals, no currency symbol: PRD §3/§6.14, a deliberate non-goal), `formatNumber(value, locale, fractionDigits)`, `formatDate(date, locale, options?)` (defaults to `{ dateStyle: 'long' }`). Thin `Intl.NumberFormat`/`Intl.DateTimeFormat` wrappers replacing every ad hoc `.toFixed()`/hardcoded `'en-US'` call site. **`Intl.NumberFormat` inserts a thousands separator `.toFixed()` never did** (`"1234.56"` -> `"1,234.56"`, even in `en`): any test asserting a literal formatted amount >= 1000 needs updating to match, not just non-English-locale tests.
- **Seed-name lookup** (`src/i18n/seedNames.ts`): five `Record<string, string>` tables (categories, payment methods, institutions, investment categories, investment sub-categories), keyed by the _exact_ literal strings a migration seeded (`V2`/`V12`/`V13`/`V14`/`V18`/`V20`). `translateSeedName(table, currentName, t)` looks up `currentName` and returns the translated string on a hit, `currentName` verbatim otherwise. This degrades gracefully: the moment a user renames a seeded row, it stops matching and renders their own text in both languages, with no schema flag or migration needed. The same pattern (a `Record<Enum, string>` of keys + a small `xLabel(value, t)` function) is reused anywhere else a fixed enum needs a translated display label (`accountTypes.ts`, `activityEnumLabels.ts`, `fieldLabels.ts`'s per-entity-type field names).
- **A shared label helper takes `Translate`, its key table is `QualifiedKey`** (`src/i18n/translate.ts`): a helper like `translateSeedName`/`accountTypeLabel` is called from many components with differently-namespace-branded `t` functions, and a `TFunction` scoped to `['ledger', 'common']` does not fit one scoped to `'accounts'`. `Translate` (`(key: never, options?: never) => string`) accepts any real `t` with no cast at the call site; the helper looks its key up in a `Record<Enum, QualifiedKey>` table and calls `translateKey(t, key, options?)`, the one place the `never` cast lives. `QualifiedKey` is the union of every `'ns:key'` in the `en` resources, so a typo'd or removed key in such a table is a compile error (the tables used to be plain strings, unchecked). Never cast `t` at a call site or write `as never` at a use: type the key as `QualifiedKey` and go through `translateKey`. A sub-component or helper that calls `t` with its _own_ literal keys of one namespace takes `TFunction<'ns'>` (`import type { TFunction } from 'i18next'`) and the caller passes its `t` as is; the keys stay checked.
- **`apiError.ts`'s `i18next.t()`-outside-React pattern**: `PROBLEM_TYPE_MESSAGES`/`VALIDATION_CODE_MESSAGES` are `type`/`code` -> translation-key maps ([errors.md](errors.md)), resolved by calling the `i18next` singleton's `t()` directly (`import i18n from '../../i18n/i18n'`) inside `toApiError`/`summaryFor`, not the `useTranslation()` hook, since this module has no React dependency and shouldn't gain one. `i18next.t()` works identically outside a component. The resolved string is baked into `ApiError.message` once, at catch time; an error banner already on screen does not retroactively re-translate if the user flips language afterward (acceptable: banners are dismissed well before that matters). The same pattern applies to any other non-component module that needs a translated string (e.g. `api/reports/reports.ts`'s `reversedRangeMessage()`) and to the one class component, `ErrorBoundary` (no hooks available to a class component).
- **`<input type="month">`'s native picker chrome follows the OS locale, not this toggle**: not controllable from JS, an accepted limitation (`MonthPicker`).
- **Full-area migration left real gaps the first pass didn't catch**: a shared component's _default_ prop value (`ResponsiveTable`'s `actionsLabel`/`emptyMessage`, `FuelTimeSeriesChart`'s old `formatValue`) can't call `useTranslation()` from a default-parameter expression. Compute the resolved value from `t()` in the component body instead (`resolved = prop ?? t('key')`), or drop the default entirely and require every caller to pass a locale-aware value (`FuelTimeSeriesChart.formatValue` has no `locale` of its own to fall back on, so every caller must supply its own `formatMoney`/`formatNumber`-backed formatter). A plain grep for `.toFixed(` or a capitalized literal in an `aria-label="..."`/`label="..."` attribute, re-run after a feature believed "done", is the way to catch these: some only ever render when a prop that isn't passed on every call site (`actions`) is also present, so they're easy to miss by inspection.
