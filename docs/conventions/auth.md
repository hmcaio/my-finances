# Authentication and network binding (F036, ADR 0029)

Root `CLAUDE.md` carries the always-needed rules (login in every profile, the `.env` hash quoting, `permitAll` for a new open path). This file holds the mechanics for work on the login, session, CSRF, CORS or port binding.

## Deployment surface

- Only `POST /api/auth/login` and `/actuator/health` (the Docker healthcheck has no cookie) are open. Swagger UI and `/v3/api-docs` need a session too, which is why `npm run generate-api-types` logs in first; the `prod` profile disables both outright (404).
- `BIND_ADDR` (default `127.0.0.1`) is the single knob that moves the backend/frontend port bindings in both compose files off loopback. Postgres/pgAdmin in the dev file are pinned to `127.0.0.1` independent of it: never route them through `BIND_ADDR`.
- The credential is `AUTH_USERNAME` + `AUTH_PASSWORD_HASH`, required by the backend in dev and prod alike and by `docker-compose.prod.yml`. Generate the hash with `cd backend && ./gradlew -q generateAuthHash` (reads `$AUTH_PASSWORD`, else prompts on stdin), or, without a checkout, from the published backend image (`docker run --rm -e AUTH_PASSWORD --entrypoint java <image> -Dloader.main=...AuthHashGenerator -cp app.jar org.springframework.boot.loader.launch.PropertiesLauncher`; full command in `docs/operations.md`'s Login section); `.env` needs it **single-quoted**, because the hash contains `$` and Compose would otherwise silently expand it. `AUTH_USERNAME`/`AUTH_PASSWORD_HASH` are bound with `@Validated` constraints whose messages say what to fix (`$`-expansion in `.env` is the usual cause of a bad hash).
- **CORS is dev-only**: `WebConfig` registers a mapping only when `myfinances.cors.allowed-origins` is set (dev: `http://localhost:5173`; the `full` compose profile appends `http://<BIND_ADDR>:5173`), always with `allowCredentials(true)`, so the origin list must be exact. Prod registers none: nginx proxies `/api/` same-origin.

## Backend

- **`infrastructure/auth` is the whole security layer**; nothing in `domain`/`application` knows about it and no aggregate has an owner column.
  - `SecurityConfig`: the `SecurityFilterChain`. Default-deny, only the two open paths above; cookie CSRF via `CookieCsrfTokenRepository.withHttpOnlyFalse()` + plain `CsrfTokenRequestAttributeHandler` + `CsrfCookieFilter`, which forces the lazily-created `XSRF-TOKEN` cookie onto every response.
  - `SingleUserDetailsService`: one user from `AuthProperties`, no table.
  - `AuthPasswordEncoder`: the one place the Argon2 parameters are chosen, shared by the runtime encoder and `AuthHashGenerator`/`generateAuthHash`. `matches` reads parameters from the stored hash, so changing defaults never invalidates one.
  - `SessionAuthenticator`: the JSON login's equivalent of `formLogin` (authenticate, rotate session id + CSRF token, save into the same `SecurityContextRepository` bean the chain reads).
  - `LoginAttemptTracker` + `ClientAddressResolver`: in-memory per-client failure counter on the injected `Clock`; behind nginx the key is `X-Real-IP`, trusted only where `myfinances.auth.client-ip-header` is set, i.e. prod.
- **`ProblemDetailAuthenticationEntryPoint`/`ProblemDetailAccessDeniedHandler` are the one sanctioned second place an RFC 9457 body is built.** Spring Security's filter chain rejects a request before MVC dispatch, so `GlobalExceptionHandler` can never see it. These two are filter-chain components (not `@ControllerAdvice`s, so the one-advice ArchUnit rule is untouched) that write the same `type`/`title`/`status`/`instance`, no `detail`, via `ProblemDetailResponseWriter`. Two fixed slugs, `ProblemTypeSlugs.UNAUTHENTICATED_TYPE` (401) and `ACCESS_DENIED_TYPE` (403: in this single-role app, a failed CSRF check), are constants like `INTERNAL_ERROR_TYPE`, not derived. The third F036 slug, `too-many-login-attempts` (429), *is* derived: `TooManyLoginAttemptsException` is an ordinary `@ResponseStatus` exception thrown from `AuthController.login`. A wrong password goes through the entry point too (the controller calls it), so a wrong username and a wrong password are byte-identical responses. (Error contract: [errors.md](errors.md).)
- **Auth never logs the username, password, hash or client address** (ADR 0011): `AuthController` logs outcome and consecutive-failure count only, and `AuthProperties`/`LoginRequest` override `toString()`.
- **Controller tests**: `MockMvcSupport.build` is authenticated by default (real filter chain, a pre-populated session plus a matching `XSRF-TOKEN` cookie / `X-XSRF-TOKEN` header pair), so every controller test keeps working and still runs behind the chain; `buildUnauthenticated` is for auth tests. `SecurityMockMvcRequestPostProcessors.csrf()`/`user()` stay out of tests (`TestConventionsTest` enforces it): `csrf()` permanently swaps the shared, context-cached filter chain's CSRF repository for a session-based one, after which no `XSRF-TOKEN` cookie is written in that JVM and cookie-behavior tests pass or fail depending on class order. The test JVM's credential (`test-user` / `test-password-f036`, `TestCredentials`) is injected as `myfinances.auth.*` system properties in `build.gradle`; a test that logs in must use its own fake `remoteAddr`, since the attempt tracker is per context.

## Frontend

- **`/login` is the only route outside the guard.** `App.tsx` mounts `<BrowserRouter>` at the top with two routes: the lazy `LoginPage` and `*` -> `<RequireAuth><AuthenticatedApp/></RequireAuth>`, where `AuthenticatedApp` is everything that used to be the app shell (onboarding gate, `BackupStatusBanner`, `Layout`, the page routes). So **no data hook fires until `useSession()` confirms a session**: a new top-level data-fetching component goes inside `AuthenticatedApp`, never beside it. `RequireAuth` redirects to `/login` with the requested path+query in router state; `LoginPage` navigates back to it (only an in-app `/...` path is honoured). A session check that fails for a reason other than 401 shows a retry notice, not the login form.
- **The session is a query**, `SESSION_QUERY_KEY` (`api/core/queryClient.ts`), `{ authenticated }`; `getSession()` folds a 401 into `authenticated: false`. **A 401 from any other query or mutation flips that same entry and drops the cached app data** (`QueryCache`/`MutationCache` `onError` in `createQueryClient`): that is how an expired session mid-use lands on `/login` with no per-call-site code. A mutation whose own 401 is the answer (the login form) sets `meta: { skipSessionExpiry: true }`. `useLogin`/`useLogout` set `skipInvalidate` and await a session refetch instead of relying on invalidate-everything; logout also removes every non-`auth` query so nothing financial stays in memory behind the login screen.
- **`apiClient` is `withCredentials: true` and `withXSRFToken: true`**: axios reads the `XSRF-TOKEN` cookie and sends `X-XSRF-TOKEN` itself (`true`, not the same-origin-only default, is what makes dev's cross-origin Vite -> backend calls carry it). No custom interceptor. In dev, `resolveBaseUrl` swaps `localhost` in `VITE_API_BASE_URL` for the page's own hostname when the page was opened on another host (`BIND_ADDR`), because the session cookie is scoped to the host the page was served from.
- **`npm run generate-api-types` logs in first, unless run `-- --offline`** (`scripts/generateApiTypes.mjs`): `AUTH_PASSWORD=... npm run generate-api-types` (username from `AUTH_USERNAME`, else the repo `.env`). The backend gates `/v3/api-docs` like everything else, so the script does the SPA's own sequence (GET for the XSRF cookie, login POST, then the document) and runs openapi-typescript on the local copy. `--offline` skips all of it: the Gradle task `exportOpenApi` fetches the document through `MockMvcSupport.build`, which is already authenticated ([tooling.md](tooling.md#api-types-and-time-zone)).
- **Tests/mocks**: `src/mocks/handlers/auth.ts` keeps one piece of module state, "is there a session", default `true` so every page/e2e test is signed in without ceremony; `signOutMockSession()` starts a test signed out, and the login/logout handlers flip it (reset by `resetStores()` through `onResetStores`). To test a mid-use expiry, leave the session handler alone and make a data handler return a 401 problem. A component that renders `Layout` needs a `QueryClientProvider` (its logout button uses `useLogout`).
