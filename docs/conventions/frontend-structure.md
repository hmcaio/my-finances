# Frontend layout, routes and API clients

Read when adding a route, a feature folder, an API area or a shared module, or when looking for where a kind of file lives.

## Layout

- `src/api`: one folder per area, `src/api/<area>/`, holding the typed HTTP client `<area>.ts` and its sibling `<area>Queries.ts` with the TanStack Query key factory and hooks, plus their tests. The investment modules share `src/api/investments/`, split by sub-domain, each folder keeping the same `<name>.ts` + `<name>Queries.ts` pairs: `products/` (products, holdings, opening positions, snapshots, value series, trade confirmation lines), `taxonomy/` (categories/sub-categories, segments), `allocation/` (allocation by grouping), `fii/` (FII allocation, dividends, portfolio, allocation plan). `src/api/core/` holds the shared plumbing: `client`, `apiError`, `queryClient`, `schemaDrift`. Generated types are in `src/api/generated/`.
- `src/components`: shared UI, grouped by role. `feedback/` for `ErrorAlert`, `ErrorBoundary`, `LoadFailedNotice`, `ConfirmDialog`, `FormDialog`, `FormDialogPane`, `AddFormDialog`, `FormDialogContent`, `fadeIn`; `table/` for `DataTableBody`, `PaginationControls`, `InlineEditActions`; `layout/` for `Layout`, `BackupStatusBanner` (app-shell chrome), `ReadOnlyNameListPage` (page template), `ResponsiveFilterBar`, the page primitives `PageContainer`, `PageHeader`, `PageSection` and the shared `sx` constants in `layoutSx.ts`; `charts/` for the shared line-chart math and svg frame ([frontend-charts.md](frontend-charts.md)); `inputs/` for `MonthPicker` and `MonthNavigator`. Usage notes: [frontend-components.md](frontend-components.md).
- `src/routes`: the route table and everything about reaching a page (see Routes below).
- `src/features/<area>`: one folder per feature area, mapping to a route. Investments is the one grouped domain: `src/features/investments/{overview,products,categories,segments,fii}/`, one folder per route there. A feature folder that grows past about 12 files is split by kind of file: the `*Page` entries (and their tests) stay at the folder root, and the rest go to `components/` (other `.tsx`), `hooks/` (`use*`) and `lib/` (pure `.ts` logic: builders, validation, formatting, URL contracts); a test sits beside what it tests. Smaller folders stay flat. Split so far: `ledger`, `transfers`, `accounts`, `activity`, `investments/overview`, `investments/products`. Component name suffix says its role: `*Page` a routed page; `*Section` a block embedded in a page that fetches its own data; `*Panel` a block of a detail page for one kind of record, with its own actions; `*Card` a small summary of one value or record; `*Widget` a self-fetching dashboard tile; `*Dialog`/`*Dialogs` one modal / the modals of one panel. Name a block for what it lists and where it lives, so two blocks never differ by one word (`InvestmentProductsOverviewSection` on the Investments page, `AccountInvestmentProductsSection` on the account detail page).
- `src/hooks`: `queryState` (the query-result adapter), `useAction` (a guarded write: clears the banner, maps the error, exposes `pending`), `useAddDialog` and `useInlineEdit` (the add-dialog and inline-row-edit state of a settings-style page), `useHasAccounts`, `useDelayedFlag`, `useBreakpointBand`, `useDebouncedValue`; the app-wide state providers are in `src/providers`, not here.
- `src/providers`: one folder per app-wide context, holding its provider and consumer hook: `colorMode/` (`ColorModeProvider`, `useColorMode`), `locale/` (`LocaleProvider`, `useLocale`) and `notifications/` (the toast: `notificationStore`, a module-level store with no provider, and `NotificationHost`).
- `src/utils`: helpers shared across features with no UI of their own, e.g. `nameLookup`, `lazyNamed` (route code splitting).
- `src/mocks`: MSW handlers and their in-memory stores. `src/test`: `setup.ts` (the Vitest setup file), `utils/` (render helpers, `viewport`, `emittedCss`, `errorMessages`) and `contracts/` (shared assertion suites: `apiContract`, `settingsPageContract`, `loadStates`).

## Routes

**Every route is `React.lazy`-loaded** (issue #94: all pages were one eagerly-bundled >500kB chunk) behind one shared `<Suspense>` around `<Routes>`. Routing lives in `src/routes/`: `lazyPages.ts` declares the pages, `AuthenticatedRoutes.tsx` holds the route table, `LegacyRedirects.tsx` the old-URL redirects, `RouteFallback.tsx` and `PageErrorBoundary.tsx` the Suspense fallback and the per-page error boundary; `App.tsx` keeps the providers, the login route and the onboarding gate. Page components are named exports, not default, so each is `export const XPage = lazyNamed(() => import('../features/x/XPage'), 'XPage')` in `lazyPages.ts` (`src/utils/lazyNamed.ts`, a typed `React.lazy` wrapper: the name is checked against the module and the `import()` stays literal, so each page is still its own chunk), plus one `<Route>` in `AuthenticatedRoutes.tsx`: a new route follows the same shape, not a bare `lazy(() => import(...))`. The login guard around the routes: [auth.md](auth.md).

## API clients

All clients share one Axios instance (`src/api/core/client.ts`) configured from `VITE_API_BASE_URL` (`.env.development` / `.env.production`). That base URL already includes `/api`, so call sites use bare relative paths (`apiClient.get('/categories')`), never a hand-built `${API_BASE_URL}/api/...`. Error unwrapping: [errors.md](errors.md). Feature code reaches clients through hooks: [frontend-data-loading.md](frontend-data-loading.md).
