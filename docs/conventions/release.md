# Cutting a release

Read when a change is user-visible (its `CHANGELOG.md` entry, [below](#changelog-entries)), when cutting a release PR or when tagging a version. The decisions are in [ADR 0032](../adr/0032-github-flow-main-only.md) (`main` is the only long-lived branch; a release is a release PR plus a tag; images publish on release tags only; merge methods and rulesets), [ADR 0007](../adr/0007-single-shared-semver-and-changelog.md) (one SemVer, manual process), [ADR 0031](../adr/0031-image-vulnerability-scan-gates-publishing.md) (the scan gates the publish) and [ADR 0015](../adr/0015-automated-encrypted-backups-sidecar.md) (the forced `pre-upgrade` backup); the `release` skill (`.claude/skills/release/SKILL.md`) drafts the CHANGELOG promotion, prepares the release branch and commit, tags, checks the published images, and pushes, opens the PR and creates the release, each only after the user confirms that command; merging the PR is the user's. The steps are the flow of ADR 0032, first run for 0.1.2; the verification checklist is the one that proved the 0.1.0 images. A hotfix is an ordinary fix PR into `main` followed by a patch release (below): there is no `hotfix/` flow and no second branch. Tags are annotated (`git tag -a`; the notes are the tag name), and only the person with push rights pushes them, including through the `release` skill, which asks first.

## CHANGELOG entries

Every PR with a user-visible change adds its bullet under `## [Unreleased]` in `CHANGELOG.md`, in the same commit as the code, so the release only reconciles and promotes what is already there ([ADR 0007](../adr/0007-single-shared-semver-and-changelog.md)).

- **Which changes.** `feat`, `fix`, a breaking change, and a `refactor`/`perf` that users would notice. `docs`, `chore`, `test`, `ci`, `build`, `style` and internal refactors need no entry; say so in the PR or the closing summary.
- **Format.** One bullet per feature id: `**F004 — Transactions** — <user-visible summary>`, the title from the feature's `spec.md` heading. A change with no feature id is a plain bullet citing its issue: `closes [#N](…)`, or `part of [#N](…)` when the issue tracks several PRs.
- **Section.** Keep a Changelog order: Added, Changed, Deprecated, Removed, Fixed, Security (as in the 0.1.0 and 0.1.1 sections). A breaking change goes under Changed, marked **BREAKING**.
- **`Upgrade:` sub-line.** A nested `- Upgrade: …` line when the change alters how someone runs or upgrades the stack: compose files, volumes, env vars, config keys, migrations (say when one can fail on existing data).
- **PR links.** The PR number does not exist while the entry is written, and a link added afterwards would cost a commit and a push per PR. The release step fills every missing `([#N](…))` from the merged PRs (the `release` skill's reconcile, step 5b in `.claude/skills/release/SKILL.md`), so entries are merged without one.
- **Release time.** The version bump, renaming `[Unreleased]` and tagging happen when releasing (below, [ADR 0007](../adr/0007-single-shared-semver-and-changelog.md)); the SemVer bump is read off the commit types ([ADR 0009](../adr/0009-conventional-commits.md)), not off the section an entry sits in.

## Steps

There is no scope freeze: the tag pins the commit, so PRs may keep merging into `main` while a release is prepared (they are simply not in it).

- [ ] **1. Release PR into `main`** (branch `chore/release-vX.Y.Z` off an up-to-date `main`, one commit `chore: release vX.Y.Z`, squash-merged; the `release` skill creates the branch and the commit from the approved draft). Fill every missing `([#N](…))` PR link from the merged PRs (the `release` skill's reconcile does it), rename `[Unreleased]` to `## [X.Y.Z] - <date>` with a fresh empty `[Unreleased]` above it; the date is the day the **final** tag will be pushed, decided before the PR is opened: with an rc (and its manual checks) that is usually days after the merge, so date it for the day you plan to tag, and the `release` skill records it in the PR body. Set `version` to `X.Y.Z` in `backend/build.gradle`, `frontend/package.json` and `frontend/package-lock.json` (equal, ADR 0007; `npm version X.Y.Z --no-git-tag-version` in `frontend/` does both npm files). That is all the PR changes: `CHANGELOG.md` (promotion, link footer, PR links), `backend/build.gradle`, `frontend/package.json` and `frontend/package-lock.json`. `README.md`, `docs/operations.md` and `.env.example` hold no release version (the quickstart uses a `vX.Y.Z` placeholder, the hash command `:latest`, the Project status a pointer to the CHANGELOG and the Releases page), so a release never edits them; keep it that way when writing examples (placeholder `vX.Y.Z` or `latest`, never the current version). A CHANGELOG-only PR is docs-only and skips the test jobs; touching the version files runs them.
- [ ] **2. Scan the images** (`bash scripts/verify.sh scan` on the release PR's branch, [tooling.md](tooling.md#image-vulnerability-scan-adr-0031); the `Build images and scan` check on the release PR is this step whenever the PR touches the image inputs, which a version bump does since the version files match the `images` filter, but a CHANGELOG-only release PR is docs-only and skips it, so scan locally then). The same filter match makes the PR-time `Prod smoke` (`bash scripts/verify.sh smoke`, [tooling.md](tooling.md#prod-smoke-adr-0032)) run on the release PR too, so the fresh-install smoke is already green before any tag. The scan gates `build-and-push`, so a fixable HIGH/CRITICAL finding found only in the tag run publishes nothing and burns that version; clear it first (base image or dependency bump, or a dated `.trivyignore` entry) in a PR into `main`.
- [ ] **3. Release candidate** `vX.Y.Z-rc.1`, tagged on the release PR's squash commit (the versions in it are already `X.Y.Z`) with `git tag -a vX.Y.Z-rc.1 -m vX.Y.Z-rc.1 <sha>`. Optional now that the PR-time image build and prod smoke jobs exist (ADR 0032 follow-up work, implemented): they cover the image build, the scan and a fresh-install smoke, so the rc adds the publish steps themselves (registry login, push, tags) and gives the manual upgrade test published images to run against. Do it for a release that touches the workflow, the Dockerfiles or the compose file, and for the first release after any of them changed. It runs the same publish pipeline as the final tag and publishes `vX.Y.Z-rc.N` and `sha-<short>`; it never moves `latest`. Tags are immutable (`protect-release-tags` forbids delete, move and update), so a bad candidate means `rc.N+1`, never a retag. A defect found during the rc is fixed in an ordinary PR into `main`, with its CHANGELOG bullet under the existing `## [X.Y.Z]` section (re-dated to the day of the final tag); then tag `rc.N+1` and finally `vX.Y.Z` on that later commit, not on the original release commit.
- [ ] **4. Verify the published images** (below), from a clean directory, against the rc's images when there is an rc. With no rc, run it against the final tag after step 5; a defect it finds is a patch release.
- [ ] **5. Tag `vX.Y.Z` on the release PR's squash commit**, not on whatever `main` is by then, so merges that landed in between do not leak in: `git fetch origin`, `gh pr view <PR number> --json mergeCommit -q .mergeCommit.oid` for the sha, `git tag -a vX.Y.Z -m vX.Y.Z <sha>` (annotated, like every released tag but one), `git push origin vX.Y.Z`. (After a fix during the rc, the sha is the last fix's squash commit.) The tagged commit's message must not carry a skip-CI marker. Wait for the tag run; check all three images (`backend`, `frontend`, `backup`) carry `vX.Y.Z` and `sha-<short>` and that `latest` has the same digest as `vX.Y.Z`.
- [ ] **6. GitHub release** with the notes taken from the CHANGELOG section: `gh release create vX.Y.Z --verify-tag --latest`.
- [ ] **7. Docs**: tick any plan item the release proved (F014 for the first one).

## Verifying the published images

The PR-time `Prod smoke` job (and the same check in the tag run, before the push) already proves the **fresh install** against locally built images: all four services healthy, ports on `127.0.0.1` only, login and a wrong password, nginx's security-header and cache matrix, `/api/backup-status` reaching OK, and a clean backend log ([tooling.md](tooling.md#prod-smoke-adr-0032)). So the items below that overlap it (healthy, loopback ports, login) only need a quick look at the published artifact; what the smoke cannot see stays manual: anonymous pull and public visibility of the GHCR packages, a real UI flow, the restore drill, logging hygiene against real data, and the upgrade from the previous tag.

Work in an empty directory holding only `docker-compose.prod.yml` and `.env.example` (from the tag, as in [Running the published images](../operations.md#running-the-published-images-production)), not a checkout, so nothing local leaks in. The prod compose hardcodes `container_name`s and the `my-finances-logs-prod` volume, so use a unique `-p` project name, a scratch `BACKUP_DIR` and tear everything down afterwards; do not run it beside a stack you care about.

- [ ] Anonymous pull of the three images works (set `DOCKER_CONFIG` to an empty scratch directory for the pull, so your own `docker login` is neither used nor removed); `up -d` reaches healthy.
- [ ] Published ports are bound to `127.0.0.1` only.
- [ ] Login works, one UI flow end to end (create an account, a transaction), and the backup banner shows nothing once the first backup is in.
- [ ] Restore drill ([Backups](../operations.md#backups)): a wrong key and a corrupt file fail before the database is touched; a good restore brings the data back.
- [ ] Logging hygiene: grep `docker compose logs` and the `my-finances-logs-prod` volume for the test amounts, descriptions and names; none may appear (ADR 0011, [logging.md](logging.md)).
- [ ] From the second release on, the upgrade test from the previous tag (stays manual: the smoke job only installs fresh, it never starts from a previous release's volumes): a forced `pre-upgrade` backup (`decision: forced`, file `myfinances-<ts>.pre-upgrade.dump.age`) lands before the backend restarts; Flyway reports "up to date" or migrates; the data is byte-identical; rollback works (restore the `pre-upgrade` backup, run the old tag).

## Gotchas

- **A publish-only failure burns the version.** `build-and-push` runs only on release tags, and tags are immutable, so a failure that only the image build, the scan or the push can show costs that version number: the tag keeps pointing at the commit whose workflow file failed, and a fix on `main` does not change the run for it. Re-running the failed jobs from the Actions UI is right for a transient error (a registry or network blip); a workflow or Dockerfile defect needs the next tag (`rc.N+1`, or the next patch). The PR-time image build and prod smoke, the smoke step in the tag run (it runs before any push), and the `-rc.N` rehearsal exist to move this failure class before the final tag.
- **`backend/gradlew` exec bit.** The first publish run (0.1.0) failed in the backend image build because `build-and-push` did not `chmod` the wrapper, unlike the test job. Fixed in #160 (mode 100755 and `COPY --chmod=755`); details in [tooling.md](tooling.md). A change to `backend/Dockerfile` or the wrapper is proven by the PR-time image build (`Build images and scan`, `Prod smoke`), not by the other checks.
- **A failing scan blocks the publish (ADR 0031).** `build-and-push` scans before it pushes, so a red scan in a tag run means no images for that tag. The fix is a bump (or a dated `.trivyignore` entry) in an ordinary PR into `main` and then a new release PR and the next tag, because the failed tag cannot be moved; scan (step 2) before tagging so it does not come to that, and re-check the CHANGELOG date if the delay crosses a day.
- **The tag guard.** The tag run fails before building anything unless the tag is exactly `vX.Y.Z` or `vX.Y.Z-rc.N` and its commit is an ancestor of `origin/main`. A failure means the tag was put on the wrong commit (a branch that was not merged, or a mistyped name); the tag is immutable, so tag the right commit with the next version.
- **GHCR packages are public**: confirm anonymous pull (step 4) each release, since a package created private would break the no-login quickstart in `docs/operations.md`.
- **The CHANGELOG date must match the tag day.** Date it for the day you plan to push the final tag (step 1); if the tag slips a day, fix the date in a docs-only PR into `main` before tagging and tag that later commit (after the tag, the tagged commit keeps the wrong date for good).
