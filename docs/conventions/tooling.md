# Running, verifying and shipping the stack

Read when changing compose files, Dockerfiles, CI, a pinned tool version, the verify script, or when running the prod-shaped stack locally. The commands themselves live in `scripts/verify.sh` (stages and their prerequisites are in its header) and `.github/workflows/ci.yml`; this file keeps only what those don't say.

## Dev stack

- The `full` profile is the default dev path because its toolchain versions are the pinned ones CI and prod use; native `bootRun`/`npm run dev` is the fast-loop alternative. They both bind 8080/5173, so use one or the other. `docker compose --profile full down` stops the app containers too (plain `down` leaves them running).
- The dev `full` services report health too: the backend on `/actuator/health`, the frontend on the Vite server at `http://127.0.0.1:5173/` with a 120 s start period and 60 retries, because the first start runs `npm ci` into an empty `node_modules` volume before Vite listens. `docker compose --profile full ps` shows them `starting` until then.
- pgAdmin login, the pre-registered server, and the "editing `servers.json` needs `docker compose down -v`" caveat are commented in `docker-compose.yml`.
- Port exposure (`BIND_ADDR`): [auth.md](auth.md).

## Verify and CI

- `scripts/verify.sh` is the one definition of the checks: CI's jobs call it, so a green local run means a green CI run. Change a check in that script, not only in `ci.yml`. It runs every stage even if one fails.
- `backup` stage: needs only Docker. The bats unit tests run in an image built from `backup/test/Dockerfile` (the sidecar's Alpine tag plus `bats`, `bash`, `coreutils`, `findutils`, `jq`), so a checkout needs no bats-core and the tests run on the userland the scripts ship on; CI uses the same path. `backup/test/e2e.sh` (the stage's second half) builds the real sidecar image and runs it against throwaway Postgres containers of its own: safe to re-run, cleans up after itself. The `postgres` image declares its data directory as a volume, so a throwaway Postgres started without a data mount leaves an anonymous volume behind after `docker rm -f`: the script keeps that directory on a `--tmpfs` and removes with `rm -fv`, and any new script that starts one must do the same (`docker run --rm` also works). Testcontainers needs nothing extra: its reaper removes the volumes, even when the test JVM is killed.
- CI builds and pushes all three images to GHCR on `vX.Y.Z` and `vX.Y.Z-rc.N` tags only (`build-and-push` job in `ci.yml`, ADR 0032); a `main` push publishes nothing. The workflow triggers on PRs, `main` pushes and `v*` tag pushes, so a feature branch is built once, by its PR, and the tag run repeats the test jobs the publish job needs. A stable tag publishes `vX.Y.Z`, `sha-<short>` and `latest`; an rc tag publishes `vX.Y.Z-rc.N` and `sha-<short>` and never moves `latest`. A guard step fails the run unless the tag is release-shaped and its commit is an ancestor of `origin/main`.
- The same job scans the images and smoke-tests the production stack on them before pushing any of them: [Image vulnerability scan](#image-vulnerability-scan-adr-0031) and [Prod smoke](#prod-smoke-adr-0032).
- **Pull requests build the images too** (ADR 0032 follow-up): two jobs, `Build images and scan` (`bash scripts/verify.sh scan`) and `Prod smoke` (`bash scripts/verify.sh smoke`), so a Dockerfile, nginx, compose or image mistake fails the PR instead of burning a release tag. They run on `pull_request` only (the tag run has `build-and-push`), build with plain `docker build` and push nothing. Two jobs, each building the three images in parallel, so each is its own required check and a new CVE cannot mask whether the stack still works. Both are gated by the `changes` job's `images` output (below) and are **required checks**.
- `backend/gradlew` is committed with the executable bit (mode 100755; Windows checkouts don't track it, so a regenerated wrapper must be re-flagged with `git update-index --chmod=+x backend/gradlew`), and `backend/Dockerfile` copies it with `--chmod=755` so the image build does not depend on it either. The PR-time image build (and, in the tag run, `build-and-push`) would show a missing bit; check a Dockerfile change locally by building from `git archive HEAD:backend | docker build -` (a bind-mounted or extracted Windows tree fakes the exec bit).
- Docs-only PRs (every changed path under `docs/` or `.claude/`, or a `*.md`) skip the test jobs through the `changes` job in `ci.yml`: they start, are skipped by `if:`, and a skipped job counts as passed for a required check. Never use `[skip ci]` or `paths-ignore` for this: the workflow would not start, the required checks would stay "Expected" and the PR could not merge. A new test job must also get `needs: changes` and the same `if:`. The same job's second output, `images`, is true on non-PR events and, on a PR, when a non-markdown path is under `backend/`, `frontend/` or `backup/`, is `docker-compose*.yml`, `.github/workflows/*`, `scripts/trivy/*`, `.trivyignore`, `scripts/verify.sh`, `scripts/smoke-prod.sh` or `.env.example` (the last two are the smoke test's own inputs); it gates the two image jobs, so a PR touching only `docs/`, `.claude/`, markdown, other scripts or the other workflow-adjacent files skips them. Keep the list in step with what the image build and the smoke test read.
- **The frontend e2e is three `--shard` jobs plus one aggregator** (#210): the required check `Frontend e2e (Playwright)` is the `e2e-frontend` aggregator, not the `e2e-shards` jobs (their names carry the shard number), so changing the shard count never touches `protect-main.json`; keep the matrix and the `/3` in `E2E_SHARD` equal. The shards run in `mcr.microsoft.com/playwright:v<version>-noble` (browsers, fonts and OS libraries inside, so no `playwright install --with-deps`: its `apt-get` stalled for 6-12 min on the runner's Azure mirror in half the first shard jobs); `--ipc=host` is in `options` for Chromium's shared memory. The aggregator runs `if: always()` and fails when `changes` failed or, with code changed, a shard did not succeed: a skipped required job counts as passed, so a plain `needs` chain would let a failed `changes` job through. Workflow `concurrency` cancels a superseded run on a PR only, never a `main` or tag run (the tag run publishes).
- Branch and tag protection is code: `.github/rulesets/*.json` (ADR 0032), applied with `scripts/apply-rulesets.sh` (needs `gh` with admin rights; upserts by name = file basename, and never deletes a ruleset: remove one with `gh api -X DELETE repos/hmcaio/my-finances/rulesets/<id>`, ids from `gh api repos/hmcaio/my-finances/rulesets`). Edit the file, then re-run the script; don't change a ruleset only in the GitHub UI. The required status checks are the job `name:` values in `ci.yml` (the four test jobs plus `Build images and scan` and `Prod smoke`), so renaming a job there means updating `protect-main.json` in the same PR, or every merge blocks. A new required job reaches GitHub only when the owner re-runs `scripts/apply-rulesets.sh` after the PR merges; until then it runs but does not block.

## Pinned versions

A tool version is pinned in every file that names it, and `scripts/check-versions.sh` (the `versions` stage, CI's first backend step) fails if they disagree. Images use full patch tags (Dependabot bumps them), never floating `:24-alpine`-style tags, so bump every sibling in the same PR.

- `postgres`: both compose files + `TestcontainersConfiguration`.
- `backup/Dockerfile` (F018, rebuilt on Alpine in #204): `FROM alpine:<x.y.z>` (a full patch tag; the form is checked) and `ARG POSTGRES_MAJOR`, which installs `postgresql${POSTGRES_MAJOR}-client`. `check-versions.sh` fails unless that major equals the major of the `postgres` tag above, because `pg_dump`/`pg_restore` must match the server's major (Alpine ships the latest minor of the major, compatible with any server of it). A Postgres major bump therefore touches both compose files, `TestcontainersConfiguration`, `backup/test/e2e.sh` and `POSTGRES_MAJOR` in one PR, and the image build fails loudly if the Alpine release no longer carries that client package.
- Playwright: the `image:` tag in `ci.yml`'s `e2e-shards` job must equal the `@playwright/test` version in `frontend/package-lock.json` (`check-versions.sh` compares them). Dependabot bumps the npm package but cannot see the workflow line, so the npm PR fails the `versions` step until the tag is bumped in it.
- Node: `frontend/.nvmrc` is the source; `frontend/Dockerfile`, the dev compose `frontend` service, CI's `setup-node` and `engines` follow it.
- `eclipse-temurin` JDK/JRE: `backend/Dockerfile` + dev compose `backend`. The Java major is also pinned in `backend/build.gradle` (toolchain), `backend/gradle/gradle-daemon-jvm.properties` (regenerate with `./gradlew updateDaemonJvm --jvm-version=<n>`: a stale one makes the image build try to download a second JDK and fail) and CI's `setup-java`; `check-versions.sh` requires all of them to equal the tag's major.
- `nginx`: only `frontend/Dockerfile`, on the `-alpine-slim` variant (the full image adds modules and libraries the app does not use, which carry scan findings); `check-versions.sh` has no sibling to compare.
- `backup/test/Dockerfile` (the bats test image, #213): `FROM alpine:<x.y.z>` must be the same full patch tag as `backup/Dockerfile`'s (`check-versions.sh` compares them), so bump both together (Dependabot opens one PR per directory).
- Trivy: only `scripts/trivy/Dockerfile` (tag + digest, so `check-versions.sh` checks its form, not siblings).

## Image vulnerability scan (ADR 0031)

The `build-and-push` job builds the three images into the runner (`load: true`), scans them with Trivy, and pushes only if all three pass, so a vulnerable image is never published (no `latest`, sha or `vX.Y.Z` tag moves). The check is `bash scripts/verify.sh scan`, run by CI and locally alike: it runs the Trivy image pinned in `scripts/trivy/Dockerfile` (tag + digest, bumped by Dependabot) against a `docker save` tarball and fails on any **fixable HIGH or CRITICAL** finding in OS packages or app libraries (`--ignore-unfixed`, `--pkg-types os,library`). There is deliberately no `aquasecurity/trivy-action`: its tags were hijacked in March 2026 and it would run third-party code beside the `packages: write` token.

- Locally: `bash scripts/verify.sh scan` builds the three images (as `my-finances-<name>:scan`) and scans them; `SCAN_IMAGES="ghcr.io/hmcaio/my-finances-backend:vX.Y.Z ..." bash scripts/verify.sh scan` scans existing images instead (pulled when not local). Needs Docker; the first run downloads the vulnerability DBs (a few minutes) into the `my-finances-trivy-cache` volume. Scan published images anonymously by pointing `DOCKER_CONFIG` at an empty directory, so your own login is neither used nor touched.
- Not in the default `verify.sh` run (it builds images), but it **is** a PR check: the `Build images and scan` job runs `bash scripts/verify.sh scan` on every PR whose `images` filter matches (see [Verify and CI](#verify-and-ci); ADR 0031's "not on PRs" is amended by ADR 0032's follow-up), and it is a required check. So a CVE published after the last merge blocks the next backend, frontend or backup PR until a bump or a dated `.trivyignore` entry lands in it; revisit the required status if that happens more than about once a quarter (ADR 0032). A PR that changes a `Dockerfile` or a pinned base image can run it locally first.
- When it fails, the output names the package, installed and fixed versions. Prefer the fix: a base image finding (alpine/OpenSSL/libexpat in `postgres`, `nginx`, `eclipse-temurin`) is cleared by bumping that image's pinned tag in every sibling file (Dependabot proposes it; [Pinned versions](#pinned-versions)); a library finding in `app.jar` is cleared by bumping the dependency (Spring Boot BOM, or an explicit constraint in `build.gradle`). A binary the base image bundles that no tag bump fixes is replaced by the distro's package instead (the backup sidecar once had to delete the postgres image's bundled `gosu`, whose Go stdlib was stale, #177); the sidecar is on plain Alpine now (#204), so its `gosu`, `age` and `rclone` are Alpine's packages and nothing is bundled.
- Only when no fix can ship in time, add a line to `.trivyignore`: `CVE-... exp:YYYY-MM-DD   # package in image: why it is not exploitable`. A CVE id, a reason and a review-by date are required; `exp:` is enforced by Trivy (after it the entry stops matching and the scan fails again), keep it within about 90 days. Review the file at every release. The CVE is accepted per id, for every image and package.
- The scan only sees what the registries' advisory data knows on the day it runs, so an image that passed can be flagged later. That is not a publish gate: re-scan before the next release (`SCAN_IMAGES=... bash scripts/verify.sh scan`).

**Major bumps of `postgres`, `eclipse-temurin` and `node` are ignored in `.github/dependabot.yml` on purpose** (`version-update:semver-major`, in every ecosystem block naming them: `/backend`, `/frontend` and the root compose files); minor/patch bumps still arrive, though Dependabot edits one file per PR, so those fail `check-versions.sh` until the siblings are added to the PR. `/backup` is not in that list any more: its `FROM` is `alpine`, not `postgres` (#204), so Dependabot there only bumps the Alpine tag, and the Postgres major it installs is `ARG POSTGRES_MAJOR`, which Dependabot cannot see and `check-versions.sh` compares with the compose tag. The Alpine packages the image installs (`age`, `rclone`, ...) are unpinned and untracked. A major is a deliberate, coordinated move (Postgres 18, the JDK 25 LTS, Node 24), so do it by hand: bump every file in the lists above in one PR (for the JDK also bump the three Java-major pins above; for Postgres also check the major's data-directory upgrade path for existing volumes: the official image's data directory and `VOLUME` moved at 18 (`/var/lib/postgresql/<major>/docker`, volume at `/var/lib/postgresql`), a major cannot open the previous one's files, and a volume reused under the old name would silently initialise an empty cluster beside the old files, so give the new major a new volume name, mount it at the image's `VOLUME`, and document a backup/restore migration; bump `POSTGRES_MAJOR` in `backup/Dockerfile` and confirm Alpine packages that client major; for Node, `frontend/.nvmrc` first), run `bash scripts/verify.sh versions`, and add an `Upgrade:` note to the CHANGELOG if it changes how the stack is run. Dependabot then tracks minors on the new line; the ignore needs no edit. `nginx` (`frontend/Dockerfile`) is held to the stable line (even minors, e.g. 1.30; odd minors are mainline): its minor and major bumps are ignored too, so only patch updates arrive, and moving to the next stable line (e.g. 1.32) is a manual bump of the Dockerfile followed by `bash scripts/verify.sh scan`.

## Prod smoke (ADR 0032)

`bash scripts/verify.sh smoke` (body: `scripts/smoke-prod.sh`) runs `docker-compose.prod.yml`, unchanged, against locally built images and asserts what only the real images show. It is the `Prod smoke` job on PRs (required) and a step of `build-and-push` between the scan and the push steps, on the already loaded images (`SMOKE_BACKEND_IMAGE`, `SMOKE_FRONTEND_IMAGE`, `SMOKE_BACKUP_IMAGE`), so a broken image is never published. Its aim is the failures that used to surface on a release tag: the `gradlew` exec bit, an nginx header or cache policy mistake, duplicate headers, a compose or `.env.example` drift, a backend that does not start on the prod profile.

- **Locally**: Docker with Compose v2 (`up --wait`), `curl` and a POSIX shell (Git Bash works; it follows `scan_image`'s `cygpath`/`MSYS_NO_PATHCONV` handling). Without `SMOKE_*_IMAGE` set it builds the three images first (`my-finances-<name>:smoke`, seconds warm, several minutes cold); the run itself took about 40 s with the images present on a Windows Docker Desktop machine, and the stack start dominates it. **It refuses to run** if any container `my-finances-{postgres,backup,backend,frontend}-prod`, the volume `my-finances-logs-prod` or anything of its own project `my-finances-smoke` exists, because the compose file hardcodes those names: stop your real prod stack first, or remove the leftovers it lists. Nothing of yours is touched.
- **Isolation**: its own compose project (`my-finances-smoke`), a temp directory with a copy of the compose file, the `.env` (made from `.env.example`), the backups bind folder (`BACKUP_DIR`, not the external volume) and the cookie jar, random login and Postgres passwords never printed, the Argon2 hash from the backend image's `AuthHashGenerator` and the age recipient from `backup-keygen` (private key dropped unread), the frontend on a Docker-chosen free port on `127.0.0.1`. The `EXIT` trap runs `down -v`, removes the volumes, the temp directory and the `ghcr.io/hmcaio/my-finances-*:smoke` tags it created. An aborted run (kill -9, power loss) leaves containers behind, which the next run's precheck names.
- **Assertions**: all services healthy within 300 s (`up --wait`), and each of the four containers reports `healthy` (read back with `docker inspect`, because `--wait` also passes for a service with no healthcheck, which is how the frontend's missing one went unnoticed); only the frontend publishes a port, on `127.0.0.1`, and Postgres, backend and backup publish none; the backup container's only mounts are the backups folder and `rclone.conf` (no anonymous volume inherited from a base image, #204); unauthenticated `GET /api/accounts` and `/api/auth/session` are 401; a wrong password is 401, the right one 200 (XSRF cookie dance as in [auth.md](auth.md)), then `/api/auth/session` and `/api/accounts` are 200; `/swagger-ui.html` and `/v3/api-docs` through nginx are the SPA shell (never the document), and 404 at the backend itself (asked from inside the container with the session); the four security headers (`Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`) and `Cache-Control` each appear exactly once on `/`, `/index.html`, `/ledger`, the real hashed `/assets/*.js`, a missing `/assets/x.js` (404), `/api/auth/session` (401) and the login POST, and on `/healthz` (200, body `ok`); `Cache-Control` is `no-cache` on the shell paths, `public, max-age=31536000, immutable` on the asset, `no-store` on the missing one and on `/healthz`, and neither the probes nor the smoke's own `/healthz` request appear in the frontend's access log; `/api/backup-status` reaches `OK` (using the README's on-demand `backup.sh` if the start-time backup is not yet visible); the backend log has no `ERROR` line and no stack trace. Each failure prints one line and the run exits 1 after listing them all.
- **Not covered**: the upgrade from a previous release (fresh volumes only), restore (`restore.sh`), the browser UI (Playwright runs against the Vite dev server, not nginx), the published GHCR images and their public visibility, TLS, non-loopback `BIND_ADDR`, and the optional `rclone` remote. Those stay in [release.md](release.md)'s checklist. The temp backups folder is a bind mount, so the named-volume path of `my-finances-backups-prod` is not exercised either.
- Add an assertion here and in the script's header when a new prod-only behaviour needs a guard; keep the file list of the `images` filter in `ci.yml` in step with what the script reads.

## Production packaging (F014, ADR 0006)

`docker-compose.prod.yml` is wholly separate from the dev loop.

- Local smoke test: `bash scripts/verify.sh smoke` does all of the following automatically, with throwaway secrets and cleanup ([Prod smoke](#prod-smoke-adr-0032)). By hand, to poke around in a running stack: build `ghcr.io/hmcaio/my-finances-{backend,frontend,backup}:local` from `backend`/`frontend`/`backup`, `cp .env.example .env` with `IMAGE_TAG=local`, the auth variables and a real `BACKUP_AGE_RECIPIENT` (`docker volume create my-finances-backups-prod`, then `docker compose -f docker-compose.prod.yml run --rm --no-deps backup backup-keygen`: Compose resolves the whole stack for `run`, so the volume and the auth variables must exist first), then `docker compose -f docker-compose.prod.yml up -d` / `down -v`. The auth variables it also needs: [auth.md](auth.md).
- **nginx security headers (`frontend/nginx.conf`)**: declared once at server level. nginx replaces every inherited `add_header` in a location that declares its own, so a location must not set one (the cache policy is a `map "$status $uri" $cache_control` for that reason, keyed on the status so the immutable policy never lands on a 404, and `/api/` is left out of its error rules because Spring sends its own `Cache-Control`); if one is ever unavoidable, repeat the security headers in it. `location = /healthz` (the frontend's healthcheck target, below) sets no `add_header` either: it inherits the security headers and gets its `no-store` from the same map. `location /api/` hides the upstream `X-Frame-Options` and `X-Content-Type-Options` (`proxy_hide_header`) so Spring Security's copies don't double nginx's; the dev setup has no nginx, so the backend code is untouched. The `Prod smoke` job asserts this matrix on every PR that touches the file (e2e uses the Vite dev server, not nginx), so a mistake fails the PR; to see it yourself, or to check a change before pushing, run `bash scripts/verify.sh smoke`, or by hand: `docker run --rm my-finances-frontend:local nginx -t`, then with the image running (behind a service named `backend`) `curl -sI` `/`, `/index.html`, `/assets/<hashed file>`, a deep link such as `/ledger` and `/api/health`: each must show `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options` and `Referrer-Policy`, `/` and `/index.html` `Cache-Control: no-cache`, and `/assets/*` `public, max-age=31536000, immutable`; a missing `/assets/x.js` must be a 404 with `Cache-Control: no-store`, and `/api/health` must show each security header once.
- **Healthchecks**: every prod service reports health, so `docker compose ps` shows all four as `healthy`. The frontend's is `wget --spider http://127.0.0.1:80/healthz` (every 5 s, 5 s timeout, 5 retries, 5 s start period, like Postgres): nginx answers `/healthz` itself (`return 200`, `access_log off`) and never reaches the backend, so a backend outage does not flag the frontend (its `depends_on` already orders startup) and the request-id access log gets no line per probe. `127.0.0.1`, not `localhost`: busybox `wget` (the slim nginx image has no `curl`) tries `::1` first and `nginx.conf` listens on IPv4 only, the same trap the backend's check comments. A new nginx location or a changed `listen` must keep `/healthz` answering, and the smoke fails if it does not.
- Both compose files default to the same project name and both have a `postgres` service, so prod `up`/`down` replaces/removes the *dev* Postgres container (its data volume survives; `docker compose up -d` brings dev back).
- The prod stack's fourth service, `backup` (F018, ADR 0015), writes into `my-finances-backups-prod`, an `external: true` volume `down -v` does **not** remove. Setup/restore: the README's Backups section; full design: `docs/features/F018-backups/spec.md`. The README's "Running the published images" section is the end-user path (release tag, no checkout); keep it in step with `docker-compose.prod.yml` and `.env.example`.

## API types and time zone

- **API types are generated**: `AUTH_PASSWORD=... npm run generate-api-types` (backend running) regenerates `frontend/src/api/generated/schema.ts` from `/v3/api-docs`. Operation ids are pinned to `<controller>_<method>` by `OpenApiConfig` because springdoc's default positional `delete_8` ids collide silently when two PRs each add a controller method and git merges the regenerated file without a conflict; `ArchitectureTest` enforces unique handler names, and the schema is regenerated again after rebasing a branch that touched controllers. CI runs `npm run build`, so a broken generated file fails the PR. When an aggregate introduces a new `java.time` type, check its generated schema shape: springdoc mis-maps `YearMonth` as an object without `OpenApiConfig`'s `replaceWithClass(YearMonth.class, String.class)`.
- **Time zone is explicit**: the backend's "today" is the JVM default zone (`Clock.systemDefaultZone()`), set in containers from `TZ` (`.env`, default `UTC`); backend tests run with `-Duser.timezone=America/Sao_Paulo` (`build.gradle`) and frontend tests with `test.env.TZ` (`vite.config.ts`), so a UTC-vs-local bug fails in CI. A test that needs another zone overrides it (`vi.stubEnv('TZ', ...)`).
