# Running, verifying and shipping the stack

Read when changing compose files, Dockerfiles, CI, a pinned tool version, the verify script, or when running the prod-shaped stack locally. The commands themselves live in `scripts/verify.sh` (stages and their prerequisites are in its header) and `.github/workflows/ci.yml`; this file keeps only what those don't say.

## Dev stack

- The `full` profile is the default dev path because its toolchain versions are the pinned ones CI and prod use; native `bootRun`/`npm run dev` is the fast-loop alternative. They both bind 8080/5173, so use one or the other. `docker compose --profile full down` stops the app containers too (plain `down` leaves them running).
- pgAdmin login, the pre-registered server, and the "editing `servers.json` needs `docker compose down -v`" caveat are commented in `docker-compose.yml`.
- Port exposure (`BIND_ADDR`): [auth.md](auth.md).

## Verify and CI

- `scripts/verify.sh` is the one definition of the checks: CI's jobs call it, so a green local run means a green CI run. Change a check in that script, not only in `ci.yml`. It runs every stage even if one fails.
- `backup` stage: needs `bats` (bats-core) on `PATH`. CI installs it with `apt-get install bats`; locally, run it via a one-off Docker image with `bash`/`coreutils`/`jq` added to `bats/bats`, or install bats-core yourself. `backup/test/e2e.sh` (the stage's second half) builds the real sidecar image and runs it against throwaway Postgres containers of its own: safe to re-run, cleans up after itself.
- CI builds and pushes all three images to GHCR on `main` and `vX.Y.Z` tags only (`build-and-push` job in `ci.yml`). It triggers on PRs, `main` pushes and `v*` tag pushes, so a feature branch is built once, by its PR.
- The same job scans the images before pushing any of them: [Image vulnerability scan](#image-vulnerability-scan-adr-0031).
- `backend/gradlew` is committed with the executable bit (mode 100755; Windows checkouts don't track it, so a regenerated wrapper must be re-flagged with `git update-index --chmod=+x backend/gradlew`), and `backend/Dockerfile` copies it with `--chmod=755` so the image build does not depend on it either. CI's `build-and-push` job only runs on `main`/tag pushes, so a missing bit shows up there first; check a Dockerfile change by building from `git archive HEAD:backend | docker build -` (a bind-mounted or extracted Windows tree fakes the exec bit).
- Docs-only PRs (every changed path under `docs/` or `.claude/`, or a `*.md`) skip the test jobs through the `changes` job in `ci.yml`: they start, are skipped by `if:`, and a skipped job counts as passed for a required check. Never use `[skip ci]` or `paths-ignore` for this: the workflow would not start, the required checks would stay "Expected" and the PR could not merge. A new test job must also get `needs: changes` and the same `if:`.
- Branch and tag protection is code: `.github/rulesets/*.json` (ADR 0008), applied with `scripts/apply-rulesets.sh` (needs `gh` with admin rights; upserts by name = file basename). Edit the file, then re-run the script; don't change a ruleset only in the GitHub UI. The required status checks are the job `name:` values in `ci.yml`, so renaming a job there means updating `protect-main.json` and `protect-develop.json` in the same PR, or every merge blocks.

## Pinned versions

A tool version is pinned in every file that names it, and `scripts/check-versions.sh` (the `versions` stage, CI's first backend step) fails if they disagree. Images use full patch tags (Dependabot bumps them), never floating `:24-alpine`-style tags, so bump every sibling in the same PR.

- `postgres`: both compose files + `TestcontainersConfiguration` + `backup/Dockerfile` (F018: its `pg_dump`/`pg_restore` must match the server major, and the pinning rule applies to it exactly as to the others).
- Node: `frontend/.nvmrc` is the source; `frontend/Dockerfile`, the dev compose `frontend` service, CI's `setup-node` and `engines` follow it.
- `eclipse-temurin` JDK/JRE: `backend/Dockerfile` + dev compose `backend`.
- Trivy: only `scripts/trivy/Dockerfile` (tag + digest, so `check-versions.sh` checks its form, not siblings).

## Image vulnerability scan (ADR 0031)

The `build-and-push` job builds the three images into the runner (`load: true`), scans them with Trivy, and pushes only if all three pass, so a vulnerable image is never published (no `latest`, sha or `vX.Y.Z` tag moves). The check is `bash scripts/verify.sh scan`, run by CI and locally alike: it runs the Trivy image pinned in `scripts/trivy/Dockerfile` (tag + digest, bumped by Dependabot) against a `docker save` tarball and fails on any **fixable HIGH or CRITICAL** finding in OS packages or app libraries (`--ignore-unfixed`, `--pkg-types os,library`). There is deliberately no `aquasecurity/trivy-action`: its tags were hijacked in March 2026 and it would run third-party code beside the `packages: write` token.

- Locally: `bash scripts/verify.sh scan` builds the three images (as `my-finances-<name>:scan`) and scans them; `SCAN_IMAGES="ghcr.io/hmcaio/my-finances-backend:v0.1.0 ..." bash scripts/verify.sh scan` scans existing images instead (pulled when not local). Needs Docker; the first run downloads the vulnerability DBs (a few minutes) into the `my-finances-trivy-cache` volume. Scan published images anonymously by pointing `DOCKER_CONFIG` at an empty directory, so your own login is neither used nor touched.
- Not in the default `verify.sh` run (it builds images) and not on PRs: the gate lives where the publish does, so a new CVE cannot fail an unrelated PR. A PR that changes a `Dockerfile` or a pinned base image should run it locally first.
- When it fails, the output names the package, installed and fixed versions. Prefer the fix: a base image finding (alpine/OpenSSL/libexpat/`gosu`'s Go stdlib in `postgres`, `nginx`, `eclipse-temurin`) is cleared by bumping that image's pinned tag in every sibling file (Dependabot proposes it; [Pinned versions](#pinned-versions)); a library finding in `app.jar` is cleared by bumping the dependency (Spring Boot BOM, or an explicit constraint in `build.gradle`).
- Only when no fix can ship in time, add a line to `.trivyignore`: `CVE-... exp:YYYY-MM-DD   # package in image: why it is not exploitable`. A CVE id, a reason and a review-by date are required; `exp:` is enforced by Trivy (after it the entry stops matching and the scan fails again), keep it within about 90 days. Review the file at every release. The CVE is accepted per id, for every image and package.
- The scan only sees what the registries' advisory data knows on the day it runs, so an image that passed can be flagged later. That is not a publish gate: re-scan before the next release (`SCAN_IMAGES=... bash scripts/verify.sh scan`).

**Major bumps of `postgres`, `eclipse-temurin` and `node` are ignored in `.github/dependabot.yml` on purpose** (`version-update:semver-major`, in every ecosystem block naming them: `/backend`, `/backup`, `/frontend` and the root compose files); minor/patch bumps still arrive, though Dependabot edits one file per PR, so those fail `check-versions.sh` until the siblings are added to the PR. This holds for `backup/Dockerfile` too: a `postgres` minor/patch PR touching only it needs both compose files and `TestcontainersConfiguration` bumped by hand in the same PR. Dependabot sees only the `FROM` line there; the Alpine packages the image installs (`age`, `rclone`, ...) are unpinned and untracked. A major is a deliberate, coordinated move (Postgres 17, the JDK 21 LTS, Node 24), so do it by hand: bump every file in the lists above in one PR (for Postgres also check the major's data-directory upgrade path for existing volumes and the backup image's `pg_dump`/`pg_restore`; for Node, `frontend/.nvmrc` first), run `bash scripts/verify.sh versions`, and add an `Upgrade:` note to the CHANGELOG if it changes how the stack is run. Dependabot then tracks minors on the new line; the ignore needs no edit. `nginx` (`frontend/Dockerfile`) is held to the stable line (even minors, e.g. 1.30; odd minors are mainline): its minor and major bumps are ignored too, so only patch updates arrive, and moving to the next stable line (e.g. 1.32) is a manual bump of the Dockerfile followed by `bash scripts/verify.sh scan`.

## Production packaging (F014, ADR 0006)

`docker-compose.prod.yml` is wholly separate from the dev loop.

- Local smoke test: build `ghcr.io/hmcaio/my-finances-{backend,frontend,backup}:local` from `backend`/`frontend`/`backup`, `cp .env.example .env` with `IMAGE_TAG=local`, the auth variables and a real `BACKUP_AGE_RECIPIENT` (`docker volume create my-finances-backups-prod`, then `docker compose -f docker-compose.prod.yml run --rm --no-deps backup backup-keygen`: Compose resolves the whole stack for `run`, so the volume and the auth variables must exist first), then `docker compose -f docker-compose.prod.yml up -d` / `down -v`. The auth variables it also needs: [auth.md](auth.md).
- Both compose files default to the same project name and both have a `postgres` service, so prod `up`/`down` replaces/removes the *dev* Postgres container (its data volume survives; `docker compose up -d` brings dev back).
- The prod stack's fourth service, `backup` (F018, ADR 0015), writes into `my-finances-backups-prod`, an `external: true` volume `down -v` does **not** remove. Setup/restore: the README's Backups section; full design: `docs/features/F018-backups/spec.md`. The README's "Running the published images" section is the end-user path (release tag, no checkout); keep it in step with `docker-compose.prod.yml` and `.env.example`.

## API types and time zone

- **API types are generated**: `AUTH_PASSWORD=... npm run generate-api-types` (backend running) regenerates `frontend/src/api/generated/schema.ts` from `/v3/api-docs`. Operation ids are pinned to `<controller>_<method>` by `OpenApiConfig` because springdoc's default positional `delete_8` ids collide silently when two PRs each add a controller method and git merges the regenerated file without a conflict; `ArchitectureTest` enforces unique handler names, and the schema is regenerated again after rebasing a branch that touched controllers. CI runs `npm run build`, so a broken generated file fails the PR. When an aggregate introduces a new `java.time` type, check its generated schema shape: springdoc mis-maps `YearMonth` as an object without `OpenApiConfig`'s `replaceWithClass(YearMonth.class, String.class)`.
- **Time zone is explicit**: the backend's "today" is the JVM default zone (`Clock.systemDefaultZone()`), set in containers from `TZ` (`.env`, default `UTC`); backend tests run with `-Duser.timezone=America/Sao_Paulo` (`build.gradle`) and frontend tests with `test.env.TZ` (`vite.config.ts`), so a UTC-vs-local bug fails in CI. A test that needs another zone overrides it (`vi.stubEnv('TZ', ...)`).
