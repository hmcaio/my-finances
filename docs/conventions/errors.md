# Errors (both stacks)

Every error response is an RFC 9457 Problem Details body (F031, ADR 0026; validation detail F032). Root `CLAUDE.md` carries the headline (shape, `detail` stays null); this file holds the mechanics.

## Backend

- **One `@RestControllerAdvice`: `infrastructure/web/GlobalExceptionHandler`**, enforced by `ArchitectureTest` (no second advice, no `@ExceptionHandler` elsewhere). The filter-chain 401/403 writers in `infrastructure/auth` are the documented exception ([auth.md](auth.md)). It is a single `@ExceptionHandler(Exception.class)` that builds and returns a `ProblemDetail` (`type`/`title`/`status`/`instance`) for **every** branch; it rethrows nothing to Spring's default resolver chain. Status resolves in this order: a merged `@ResponseStatus` value, else `ErrorResponse.getStatusCode()` (Spring's own MVC exceptions, e.g. `NoResourceFoundException`), else a hardcoded 400 for the two client-error exceptions that implement neither (`HttpMessageNotReadableException`: bad JSON body; `TypeMismatchException`: bad UUID/date in path or query, issue #19), else 500. Any other exception type Spring maps to 4xx without `ErrorResponse` is added to that status-resolution chain, not to a second handler. Backed by `spring.web.error.include-{stacktrace,message,binding-errors}: never` (Boot 4.x spelling; not `server.error.*`).
- **`type`/`title` are derived, not authored.** `infrastructure/web/ProblemTypeSlugs.slugFor(exceptionClass)` takes the exception's simple class name, strips a trailing `Exception`, kebab-cases it (a hyphen before each internal uppercase letter, lowercased) - `AccountHasHistoryException` -> `account-has-history` - and `typeUriFor`/`titleFor` wrap that into `urn:my-finances:error:<slug>` / a humanized title. Adding a new `@ResponseStatus` exception is the only step.
  - Classes duplicated across aggregate packages only for the no-cross-aggregate-import ArchUnit rule (ADR 0014) - `AccountClosedException` in `application.transfer`/`application.transaction`/`application.recurringtemplate`, `AccountTypeNotAllowedException` in `application.transaction`/`application.recurringtemplate` - deliberately collapse to the identical slug: the duplication is a code-organization artifact, not a different real-world condition, and the frontend needs one message per condition.
  - The generic unexpected-exception (500) case uses the fixed `ProblemTypeSlugs.INTERNAL_ERROR_TYPE`/`INTERNAL_ERROR_TITLE` constants (`urn:my-finances:error:internal-error` / "An unexpected error occurred"), never derived from the actual exception class: that set is unbounded and includes third-party exception types never vetted for safety.
  - `detail` is `null` on every branch; ADR 0011 forbids populating it with exception text or entity data.
- **Bean-validation failures carry an `errors` member (F032).** `MethodArgumentNotValidException` (`@Valid @RequestBody`) gets an extra `errors` `ProblemDetail` extension member beside the usual `type`/`title`/`status`/`instance`. `GlobalExceptionHandler` builds it from the `BindingResult`: one `{field, code}` per `getFieldErrors()` entry (`field` is Hibernate Validator's own path verbatim, including bracket/dot notation, e.g. `tradeConfirmation.lines[0].quantity`) plus one per `getGlobalErrors()` entry (`field: null`; forward-compatible, nothing in this codebase produces one today). `code` is the violated constraint annotation's simple name kebab-cased via `ProblemTypeSlugs.codeFor(FieldError|ObjectError)`, the same transform `slugFor` uses; never the interpolated Jakarta message or the rejected value. This covers `@Valid @RequestBody` only. The one parameter-level constraint (F037) is `@Size` on the Ledger's `q` request parameter (`LedgerController`), with **no `@Validated` on the class**: Spring 7's built-in method validation then raises `HandlerMethodValidationException` (an `ErrorResponse`), which the single advice answers as a `400` of type `urn:my-finances:error:handler-method-validation` and no `errors` member (the frontend maps that `type` in `PROBLEM_TYPE_MESSAGES`, one generic message). A class-level `@Validated` would switch to an AOP proxy and throw `ConstraintViolationException`, which the handler would turn into a `500`: never add it.
  - **A class-level `@AssertTrue` invariant does NOT produce a global/object error.** JSR-380's `@AssertTrue` can only target a method/field, so every such invariant here (`TradeConfirmationRequest.isAtMostOneResultingBalancePerProduct`, `TradeConfirmationLineRequest.isCloseHoldingOnlyOnSell`, `CreateAccountRequest.isOpeningFieldsConsistentWithType`, `CreateTransactionRequest`/`UpdateTransactionRequest.isFuelFieldsGivenTogether`) is an `isXxx()` getter; Hibernate Validator treats `xxx` as a bean property and Spring's `SpringValidatorAdapter` reports a **field**-level violation whose field is that synthetic property path (verified against a real `LocalValidatorFactoryBean` and real `MockMvc` calls; see `GlobalExceptionHandlerTest`). `ProblemTypeSlugs.isAssertTrueViolation(FieldError)` detects it by constraint code (`"AssertTrue"`), and `GlobalExceptionHandler` reports it with `field: null` and a `code` derived from the synthetic property name (`ProblemTypeSlugs.codeForAssertTrue`, e.g. `isAtMostOneResultingBalancePerProduct` -> `at-most-one-resulting-balance-per-product`), because the literal `"AssertTrue"` code is identical for every invariant and would carry no information.
- **A new *expected* error case gets its own `@ResponseStatus`-annotated exception, never a new `@ExceptionHandler`.** Status: **409** when validity depends on another aggregate's persisted state (closed account, non-`EXPENSE` category budgeted, category still referenced, duplicate name); **400** when the request is malformed regardless of state (`SameAccountTransferException`); **404** for unknown ids. Document the operation's possible `type` values with `@ApiResponse`/`@Content(schema = @Schema(implementation = ProblemDetail.class))` on the controller method (springdoc 2.8.5 generates the `ProblemDetail` schema itself, no wrapper class), one `@ApiResponse` per status code, description text listing every `type` that status can carry for that operation.
  - **An operation with no success-status annotation of its own** (no `@ResponseStatus(CREATED)` etc., just the plain return type) loses its implicit 200 schema from `/v3/api-docs` entirely once only error `@ApiResponse`s are added. Add an explicit `200` `@ApiResponse` alongside the error ones (`InvestmentSnapshotController.list`, `InvestmentValueSeriesController.valueSeries`), or a response type used only by that operation silently vanishes from generated `schema.ts`.
- **A find-then-insert race on a `UNIQUE` constraint is still a new expected error case, not a reason for a second `@ExceptionHandler`.** `InvestmentSnapshotService.record()` checks `(holdingId, date)` then inserts; two concurrent callers can both see "absent" (issue #94, same shape as issue #20's recurring-occurrence race). Catch `DataIntegrityViolationException` at the call site and throw the existing `@ResponseStatus(CONFLICT)` exception for that case (`InvestmentSnapshotDateTakenException`) instead of letting it fall through to `GlobalExceptionHandler`'s generic 500.
- Logging in the handler: [logging.md](logging.md).

## Frontend

- **`unwrap()`/`ApiError`** (`src/api/core/apiError.ts`; Axios throws on non-2xx). `unwrap()` takes only the request promise: no per-call-site override parameter (F031/ADR 0026 removed the old `conflictMessage` argument). It reads the backend's RFC 9457 `type` off the response body and looks it up in the module's central `PROBLEM_TYPE_MESSAGES` record, falling back to the generic `"Request failed with status {status}"` when `type` is absent or not in the map. Add a new entry to that map (not a new function parameter) when a conflict/validation case needs its own wording; several `type`s intentionally share one message where the old code already bundled their causes under one string, and a `type` collapsed across backend aggregate packages (e.g. `account-closed`) gets exactly one entry. `ApiError.type` carries the raw value through for a screen that genuinely needs to branch on it. `defaultErrorMessage(err, statusOverrides?)` turns a caught error into UI text; use `statusOverrides` for a page that special-cases one status (e.g. 404). Feature code never calls these HTTP functions itself: it uses the area's `<area>Queries` hooks ([frontend-data-loading.md](frontend-data-loading.md)), whose `mutationFn`s call them, so `unwrap` stays in `src/api/<area>/`.
- **F032: a 400 whose body carries `errors`** (`type: method-argument-not-valid`) builds `ApiError.message` from `VALIDATION_CODE_MESSAGES`: the same pattern as `PROBLEM_TYPE_MESSAGES`, but keyed by `errors[].code`, since `field` is DTO-specific and the same `code` (e.g. `not-blank`) recurs across many fields/forms. Per-violation messages are deduplicated and joined into one summary string for the generic `ErrorAlert` banner, falling back to the usual `Request failed with status {status}` text when every code is unmapped. `ApiError.fieldErrors` carries the raw `{field, code}[]` through unused: **no per-field `TextField` error/helperText UI is wired yet**; whoever picks it up reads `fieldErrors` directly instead of re-parsing the summary string.
- Both maps resolve through i18next ([frontend-i18n.md](frontend-i18n.md)).
