# Accounts, net worth and investment balances (backend)

Read when code reads an account's opening balance, computes a balance or net worth as of a date, queries investment snapshots, or adds a table that references accounts.

- **`Account.getOpeningBalance()`/`getOpeningBalanceDate()` are `null` for an `INVESTMENT` account** (ADR 0012, backed by a DB `CHECK`), so any code that reads them branches on `getType()` first. `AccountBalanceQuery` does: its `INVESTMENT` branch sums the latest snapshots of the `InvestmentHolding`s pointing at that account (`LatestInvestmentSnapshotQuery`, F022/ADR 0020). `TransactionService`/`RecurringTemplateService` reject such an account with their own package's `AccountTypeNotAllowedException`. Building an `INVESTMENT` account in a test: [backend-testing.md](backend-testing.md).
- **A non-`INVESTMENT` balance is `openingBalance` plus the ledger sum, and the ledger sum is computed in SQL** (issue #189): `AccountBalanceQuery.balancesAsOf(accounts, date)` (one account: `balanceAsOf`) asks the `AccountLedgerActivityPort` read model (`infrastructure/persistence/account/AccountLedgerActivityAdapter`, one native query per call for all accounts, and per day for `NetWorthQuery.trend`) and adds the opening balance in Java, so the accounts list, net worth now, account detail and the account-balances report cost a constant number of statements. The adapter restates the sign rules of `AccountBalanceQuery.signedContribution`/`transferContribution` in SQL, which stay the reference (`FakeAccountLedgerActivity` uses them in Java): **change a sign rule in both places**. `AccountLedgerActivityParityTest` compares the SQL with the Java rules on randomized data. `FakeAccountLedgerActivity` is the fast-tier fake and that Java reference (the pre-#189 loop over the repository ports). A per-account loop that calls `balanceAsOf` for many accounts is a regression: pass the list to `balancesAsOf`.
- **`NetWorthQuery` counts an account only between its `openingBalanceDate` and its `closedDate` (exclusive)**, per date, never "every non-closed account" (that would drop a closed account from every past month). An `INVESTMENT` account has no opening date, so it always counts and is `0` until its first snapshot. Sums are as-of, computed on read from `AccountBalanceQuery`; nothing is stored. `trend()` is one forward pass (issues #94, #189): the ledger accounts' net effect per day comes from `AccountLedgerActivityPort.dailyActivityUpTo` (one grouped query, the same SQL sign rules as `activityAsOf`), and the `INVESTMENT` accounts' holdings and snapshots are read once and walked with a cursor per holding, so the statement count does not depend on the number of sampled dates or rows (`NetWorthTrendStatementCountTest`). It must keep agreeing with `asOf(date)`, which goes through `AccountBalanceQuery` per date (`NetWorthQueryTrendEquivalenceTest`); the snapshot rule (latest on or before the date, per holding) therefore exists in `AccountBalanceQuery.investmentBalance`/`LatestInvestmentSnapshotQuery` and in `NetWorthQuery`'s walk: change it in both.
- **`LocalDate.MAX`/`MIN` never reach a repository query**: Postgres can't represent it and the request fails with a 500. "The latest snapshot regardless of date" is `LatestInvestmentSnapshotQuery.latestOf(holdingId)` / `latestByHolding()` (in-memory reduce over `findByHoldingId`/`findAll`), not `findAllOnOrBefore(LocalDate.MAX)`.
- **Deleting an account**: `AccountService.delete()` hard-deletes only an account nothing references (409 `AccountHasHistoryException` otherwise, ADR 0017), via the `AccountUsageChecker` port (`infrastructure/account/RealAccountUsageChecker`: transactions, transfers on either side, templates incl. inactive, investment holdings incl. closed; moved from `investment_products` to `investment_holdings` by F022/ADR 0020, since the product itself no longer has an `account_id`). **A new table with an FK to `accounts` must be added to that checker** (and `RealAccountUsageCheckerTest`), or deleting an account it references surfaces as a 500 from the FK instead of the 409. `RealAccountUsageCheckerTest` enforces it: a test lists the tables with an FK to `accounts` from `information_schema` and fails on an unlisted one.
- **A holding's history has several sources, and a new table with an FK to `investment_holdings` must be added to `RealHasHoldingHistoryChecker`** (and its `RealHasHoldingHistoryCheckerTest`), or a hard delete of a holding it references is a 500 from the FK instead of the 409. Today: snapshots, trade lines (matched by product and account), dividend transactions, and the opening position (F038, ADR 0033).
- **An `InvestmentOpeningPosition` (F038) is a second source beside trade lines, counted like a `BUY` dated its `asOfDate`.** Every read that sums a product's trade lines also reads the positions of that product's holdings: `FiiPortfolioQuery`, `InvestmentValueSeriesQuery` (its cost lands in its as-of month only, so the monthly `contributed` figures keep summing to the running total, and `units` is `null` only with neither lines nor positions), `InvestmentSnapshotFreshnessQuery` and `InvestmentsReportGenerator`. A new read of trade lines needs the same second source, and, once F028 ships, a position's quantity goes through the same `InvestmentSplitAdjustment` with its `asOfDate` as the trade date. It moves no cash: `AccountBalanceQuery` and net worth never read it. The date order against trades is enforced in the application layer in both directions (`TransferService.requireValidHoldings`, `InvestmentOpeningPositionService`), same day allowed.
