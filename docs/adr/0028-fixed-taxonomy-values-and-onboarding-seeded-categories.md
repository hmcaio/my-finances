# 0028. Lock four taxonomy entities to fixed system values; seed Category defaults through onboarding, not migration

Status: Accepted
Date: 2026-10-15

## Context
Six entities share the same "flat, named reference list" shape: `Category`, `PaymentMethod`, `Institution`, `InvestmentCategory`, `InvestmentSubcategory`, `InvestmentSegment`. F002 established the pattern (fully user-editable, predefined starter set seeded via Flyway) and every later one copied it — including `InvestmentSegment` (F026), which ended up with the pattern but no actual seed data (`V20` creates the table with no `INSERT`).

Two problems accumulated under this one-size-fits-all shape:

1. **Protection drifted out of sync across entities that do need it.** `Category.built_in` originally blocked delete only; issue #117 (commit `986714f`) unified it with the fuel/dividend flags to block rename too, closing a real bug (a built-in category could be silently renamed away from its anchor name). `Institution.built_in` has the identical shape and the identical bug — `InstitutionService.rename()` has no guard at all today — just never fixed alongside it. Left alone, this is a second copy of the same bug with its own fix cycle.
2. **Four of the six don't actually need user customization, and carrying it is pure cost.** Payment methods are bank rails (debit, credit, PIX, cash) — a closed, slow-changing real-world set, not personal data. Investment category/sub-category is a fixed, Brazilian-market taxonomy (F008) that every other investment feature (F009, F022, F026, F027) was written assuming is stable. Investment segment is a fixed set of real-estate-FII sectors. None of these are "my own words for my own thing" the way a `Category` name is — letting a user rename "PIX" to anything, or invent a 9th investment category, buys nothing and has already produced zero actual seed data for segments three features later. `Category` is the opposite case: it's the one entity in the group that's genuinely personal (everyone's spending categories differ), yet F002 seeded it with Flyway's one fixed list for every install regardless of language or the user's own habits — pure coincidence of implementation, not a deliberate choice that categories should be uniform across installs.

These two problems share a root cause (the six-entity pattern never distinguished "needs protecting because it's structurally load-bearing or universally fixed" from "is genuinely user data that happens to ship with a starter list"), so they're resolved together rather than as two unrelated fixes.

## Decision
- **Institution closes the same gap Category already closed.** `InstitutionService` gains a guard mirroring `CategoryService`'s `requireNotProtected`, blocking both rename and delete on the `built_in` row ("No institution"). No schema change — `institutions.built_in` already exists (`V12`).
- **`PaymentMethod`, `InvestmentCategory`, `InvestmentSubcategory`, `InvestmentSegment` lose user customization entirely**, rather than gaining a protection flag. Every row in these four tables is now fixed and system-owned, so a flag distinguishing "protected" from "not" would carry no information — the create/rename/delete endpoints and the domain mutator methods are deleted outright, not guarded. Their content is fixed by Flyway migration alone, forever (changing the fixed list is a future migration, not a runtime operation). `InvestmentSegment` gets its first real seed data as part of this (a common B3 FII sector list) — previously an empty table.
- **`Category` stops being migration-seeded beyond the four rows that are structurally load-bearing**: "Other Expense", "Other Income" (`built_in`, §5.1), "Fuel" (`fuel_category`, ADR 0021), "Dividends" (`dividend_category`, ADR 0023). These stay exactly as eagerly seeded and protected as today — nothing about them changes. The eight *regular* starter categories F002 seeded (Groceries, Rent, ...) stop being migration data at all. Instead, a new onboarding step (F011, extended) presents a localized list of suggestions the user can accept, reject or supplement with their own; accepted/custom names are inserted through the existing `POST /api/categories` as ordinary, unprotected rows — indistinguishable from anything the user types in later. This is the direct consequence of the asymmetry above: `Category` is the one entity where a fixed, English-literal, Flyway-seeded list was never actually the right shape, since it's the one list a user should see and choose in their own language.
- **Two tiers of "seeded" now coexist, deliberately.** Migration-seeded + permanently protected (Institution's built-in row, Category's four flagged rows, and the entire content of the four fully-locked entities) vs. onboarding-seeded + ordinary (Category's regular suggestions, once accepted). A future reader must not assume "this row came from a migration" implies "this row is protected," or vice versa — the two are now orthogonal, where before F002's pattern made them look like the same thing.

## Consequences
- `PaymentMethodController`/`InvestmentCategoryController`/`InvestmentSubcategoryController`/`InvestmentSegmentController` lose their `POST`/`PATCH`/`DELETE` handlers; their domain classes lose `create()`/`rename()` (kept read-only, reconstituted from persistence only). Their Settings pages become read-only lists, grouped under a new collapsed-by-default "System values" nav section — `Institution` and `Category` stay as flat, fully-editable nav items since both keep real CRUD (only specific rows are protected on those two).
- `V2__categories_and_payment_methods.sql` is edited directly to drop its eight regular category inserts (keeping the two rows `V14` needs to adopt/flag). Acceptable only because no tagged release exists yet (`CHANGELOG.md` still has no `## [X.Y.Z]` section, version `0.1.0`) — a local dev database needs `docker compose down -v` to pick up the change. This is a one-time allowance, not a precedent for editing applied migrations after the first real release.
- `InvestmentSegment` finally gets non-empty seed data; `F026`'s original "no seed" gap is closed as a side effect, not a new decision.
- Onboarding (F011) goes from a single screen to a two-step flow. The suggestion step's trigger stays exactly as derived as F011's existing one (zero accounts) — no new "has onboarding happened" flag is introduced anywhere, consistent with F011's original reasoning that a persisted flag can drift out of sync with reality.
- The existing `seedNames.ts` exact-string-match translation mechanism (F033/ADR 0027) needs no new design — it already degrades correctly on rename and already works off literal-name lookups rather than a stable id. Onboarding-inserted categories just add more literal strings to its `CATEGORY_SEED_NAMES` map, including both the English and Portuguese literal of each suggestion (either could be the name actually stored, depending on the locale active at onboarding time).
- Does not amend ADR 0021/0023/0026/0027 — it generalizes their flag-based protection pattern (0021, 0023) and reuses their seed-name translation mechanism (0027) unchanged, but introduces no change to any of them.

## Addendum: extending a fixed list after a release (issue #227)
- The seeded segment and sub-category lists were widened after comparing the FII segments of Fundamentus, Investidor10, Status Invest and ANBIMA and the instruments retail investors hold (RDB, the new Tesouro RendA+/Educa+, fund types, crypto assets, gold). Five segments and fourteen sub-categories were added in `V26__expand_investment_taxonomy_seeds.sql`; the seven investment categories and every existing name are unchanged.
- The Consequences above allow editing an applied migration only before the first tagged release. `v0.1.2` is tagged, so this and any later change to a fixed list is a **new migration**, never an edit of `V13`/`V24`. It uses `INSERT ... ON CONFLICT DO NOTHING` on the unique key (`name`; `(investment_category_id, name)`), so it is safe over a database that already has a row.
- A seeded name that code selects by value (`REITs (FIIs)`, `Fixed Income`, ...) is never renamed. A new name needs entries in `seedNames.ts` and in the en and pt-BR `common.json`.
- Fiagro stays an FII segment, not a sub-category: the FII page and the allocation plan select funds by the "REITs (FIIs)" sub-category.
