# 0019. Responsive layout: MUI breakpoints, cards over tables, shared primitives, geometry-only e2e

Status: Accepted
Date: 2026-09-27

## Context
The frontend (F001–F019) was built desktop-only: a permanent 240px drawer, `main` at a fixed `p: 3`, and 16+ list pages rendering a plain MUI `<Table>` with no breakpoint awareness. F021 makes the whole app usable on phones and tablets as well. jsdom (Vitest) does not compute layout, so a horizontal-overflow or wrong-mode regression is invisible to the existing test suite; F020 added Playwright for that reason and must ship first.

## Decision
- **Breakpoints are the MUI defaults** (`xs` 0, `sm` 600, `md` 900, `lg` 1200), read through one hook, `useBreakpointBand()` (`hooks/useBreakpointBand.ts`) returning `'mobile' | 'tablet' | 'desktop'` (`useIsMobile()` for the common binary case). Feature code uses this hook or `theme.breakpoints` in `sx`, never a raw `useMediaQuery` — `Layout` is the one documented exception, because its nav-mode switch and its own padding are read before any child component exists to receive a band prop. Centralizing it means a breakpoint change is a one-file edit, and it gives every component the same viewport-faking test seam (`setViewportWidth`/`restoreViewport`, `src/test/viewport.ts`).
- **Nav**: a permanent drawer at `lg` and up; below it, an AppBar hamburger opens a temporary drawer that closes on route change. A bottom nav was rejected — the app has ~12 nav items across two levels, well past what a bottom bar holds without its own overflow menu.
- **Cards over tables on mobile, not a second table layout.** A list with 3 or more data columns renders as cards below `sm`; a list with 1–2 stays a plain table at every size (a card would add nothing). Tablet keeps the table and hides low-priority columns behind a per-row chevron that expands them as label/value pairs, rather than horizontal scroll (poor to use) or silently dropping data. This is one primitive, `ResponsiveTable`, not a bespoke card component per page: columns are declared once with a role (`primary`/`secondary`/`hideOnCard`) and a tablet priority, with `renderCard` as an escape hatch for a page the generic card can't serve (e.g. Transactions' signed, coloured amount) and `embedded` for a list nested inside an already-outlined section.
- **One surface for add/edit, not two.** Where a page had a separate add/edit form panel (most list pages), the panel is removed and a header button opens the same fields in `ResponsiveDialog` (a regular dialog from `sm` up, full screen below it) at every size — this was simpler and more consistent than keeping a panel on desktop and a dialog only on mobile, and it matches how `ConfirmDialog` already behaves at every size. Where a page had *true* inline row editing (a rename, a cap, an amount), that stays inline on tablet/desktop; a mobile edit dialog is added only when the row's own presentation actually changes on mobile (a table that becomes cards) — a 1–2-column table that stays a plain table at every size keeps its inline edit inline everywhere too, since the same table-cell field is exactly as usable at 390px as at 1280px, and a second surface would add nothing. Either way, a form that owns its state and buttons takes a `dialog` prop (`DialogContent` + `FormGrid` + `DialogActions`) rather than existing twice.
- **Verification is geometry and DOM assertions, never screenshots.** Pixel baselines are flaky across Windows (dev) and Linux (CI) — different font rendering and anti-aliasing would produce noisy diffs unrelated to real regressions. Every migrated page gets a Playwright spec at the three F020 viewport projects (390/768/1280) checking for no horizontal overflow, the right nav/table/card mode, and dialog full-screen only on mobile; screenshots may be attached as CI artifacts for a human to look at, but nothing is ever pixel-compared.
- **`maxWidth` bounds width, never fixes it.** A `sx` width is a fraction unless given a unit (`width: 1` is 100%, not 1px — this bit F021 once, see `frontend/CLAUDE.md`); a narrow form field or a `maxWidth` cap on an outlined section is fine because it still shrinks below that cap on a small screen, but a *fixed*, non-shrinking width on content that must fit a 360px viewport is not.

## Alternatives considered
- **Horizontal scroll inside `TableContainer` instead of cards.** Cheaper (no second render path) but poor to use on a touch device and was rejected for any list with 3+ columns; still used implicitly wherever a `ResponsiveTable` is left as a plain table (1–2 columns fit without it).
- **A bottom navigation bar on mobile.** Rejected: doesn't fit ~12 items without an overflow menu, which is extra UI for no real gain over a drawer.
- **Column-picker / user-configurable columns** instead of the tablet chevron. Rejected as over-engineering for a single-user local app; the chevron needs no page code at all once a column is marked `tabletPriority: 'low'`.
- **Keeping the add/edit panel on desktop and only dialog-ing it on mobile.** Rejected: two surfaces to keep in sync (validation, error display) for marginal desktop benefit; every migrated page uses one dialog at every size instead.
- **Screenshot regression testing.** Rejected for this repo's OS mix (Windows dev machine, Linux CI); revisit only behind a single OS/container-pinned renderer if a future need for true visual regression appears.

## Consequences
- Every list page in the app follows one shape: `ResponsiveTable` (or a plain table if it's 1–2 columns) + `ResponsiveFilterBar` if it has real filters + `ResponsiveDialog` for add/edit + the existing `PaginationControls` (compact below `sm` by itself). A new list page gets responsive behaviour by using these, not by re-deriving breakpoint logic.
- `frontend/CLAUDE.md`'s "Shared components" section is the living reference for which primitive to reach for and why; this ADR is the rationale, not a duplicate of that guidance.
- Migrating F021 surfaced and fixed two independent bugs it wasn't looking for: a `width: 1` visually-hidden style that caused real overflow, and an investment-allocation legend button whose default `white-space: nowrap` could force the page wider than a phone. Both are now documented gotchas.
- The dashboard's mobile overflow (a plain `<Table>` widget forcing the page wide) was fixed as a side effect of migrating that widget to `ResponsiveTable`, before the batch nominally assigned to the dashboard ran — evidence that the primitive, not per-page effort, is what removes this class of bug going forward.
- Chromium-only e2e (per F020) means Firefox/WebKit/Safari layout quirks are not caught by this suite; a real cross-browser check remains manual.
