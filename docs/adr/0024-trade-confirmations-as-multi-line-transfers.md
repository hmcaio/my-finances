# 0024. Model a buy/sell as a multi-line Trade Confirmation, with backend-derived settlement amount

Status: Accepted (amends [0012](0012-investments-as-accounts-and-transfers.md))
Date: 2026-10-08

## Context
ADR 0012 modeled a buy/sell as a `Transfer` carrying at most one `investmentProductId` and one `InvestmentTradeDetails` triple (`quantity`, `unitPrice`, `taxes`). In practice the user's source document is a *nota de negociação*: a single brokerage settlement that can list several products (ETFs, FIIs, ...) together, with one aggregate tax/fee figure covering all of them, not apportioned per product. Today's model forces one `Transfer` per product per note, each needing its own (fabricated) tax split — it doesn't match the document the user is actually transcribing from.

ADR 0012 also decided "the backend does not enforce the [amount = quantity × price ± taxes] equality (brokers round per lot)". That reasoning weakens once a single settlement spans several products: the settlement amount is no longer a simple per-product arithmetic check a user can eyeball and override — it's a net across every line and the shared tax figure, which the backend is in a better position to get right than the user retyping it.

## Decision
- **A `Transfer` generalizes to carry a `TradeConfirmation`**: zero-or-one `TradeConfirmation`, replacing the old nullable `investmentProductId` + single `InvestmentTradeDetails`. A `TradeConfirmation` holds one-or-more `TradeConfirmationLine`s (`productId`, `side` BUY/SELL, `quantity`, `unitPrice`, optional `resultingBalance`, optional `closeHolding` — SELL-only). `taxes` stays a single field on `Transfer` itself (not per line) — it is the note's one aggregate figure and is never apportioned across lines, consistent with ADR 0012's "nothing is computed from quantity/price" (deriving a per-line tax share would itself be such a computation).
- **One confirmation = one cash settlement = one INVESTMENT account.** Every line of a confirmation shares the same cash account and the same INVESTMENT account; a note spanning two brokerage accounts isn't modeled (matches how a real nota settles).
- **Mixed BUY/SELL lines are allowed**, including the same product appearing on more than one line (partial fills at different prices) and the same product on both a BUY and a SELL line (a same-day round-trip).
- **The backend now derives and enforces `amount` and direction** (`fromAccountId`/`toAccountId`) for any `Transfer` carrying a `TradeConfirmation`: net = Σ(SELL line totals) − Σ(BUY line totals) − `taxes`; the sign picks direction, the magnitude is `amount`, rounded once (HALF_UP, scale 2) after netting rather than per line. A net of exactly zero is rejected. This reverses ADR 0012's "the backend does not enforce the equality" for trades — a plain (lineless) `Transfer` is unaffected and keeps manual `amount`/direction entry. The API reflects this: a confirmation request carries `cashAccountId` + `investmentAccountId` (unlabeled) + `lines[]` + `taxes`; the client never sends `amount`, `fromAccountId` or `toAccountId` for a confirmation.
- **No backfill.** Existing single-product `Transfer` rows are mechanically migrated one-for-one into a single-line `TradeConfirmation` (the flat `investment_product_id`/`quantity`/`unit_price` columns are retired); no attempt is made to regroup historical trades into the multi-line notes they actually came from, since that information wasn't captured.
- Applies uniformly, including a one-line confirmation — there is no separate "simple trade" code path once this ships.

## Consequences
- `InvestmentTradeDetails` is removed; `TradeConfirmation`/`TradeConfirmationLine` replace it. `transfers` gains a child table for lines; `taxes` stays a column on `transfers`.
- `FiiPortfolioQuery`, `InvestmentValueSeriesQuery` and `InvestmentSnapshotFreshnessQuery` (F009/F022/F026), which key off `Transfer.findByInvestmentProductId`/`getInvestmentProductId()` and sum one quantity per transfer, move to querying the lines table, signed by each line's `side` instead of inferring direction from the transfer's endpoints.
- `DataExportService`'s CSV export splits: `transfers.csv` keeps confirmation-level fields (date, accounts, amount, taxes, description); a new `transfer_trade_lines.csv` carries per-line detail.
- Frontend: `TransferForm` becomes a multi-line entry form (n=1 is the trivial case, not a separate mode); `TransfersPage`'s trade label shows a chip per line; `InvestmentProductDetailPage`'s trade table shows one row per matching *line* (not per transfer) and drops its Taxes column (a confirmation's taxes cover its whole settlement, not one product — showing it on a single product's row would misattribute it), each row linking to its parent confirmation so the real total taxes stay reachable.
- A user who wants to record a buy funded partly from outside the tracked accounts, or wants an uneven tax split for their own reporting, can no longer type an arbitrary `amount`/per-product tax override — they must enter the actual settlement as recorded on the note. This is a deliberate narrowing: ADR 0012's "not supported: buys funded from outside the tracked accounts" already excluded the former case; the latter was never a real capability, only an unenforced one.
- Changes the F009, F022, F026 specs and PRD §5.5. A new F027 spec/plan covers the shipped shape.
