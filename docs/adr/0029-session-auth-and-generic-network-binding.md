# 0029. Session-cookie authentication and generic private-network binding for non-localhost access

Status: Accepted
Date: 2026-10-15

## Context
PRD §3/§7.1 originally decided "no authentication — app is single-user and bound to localhost only, not exposed to LAN or internet," and §9 listed "remote/LAN access with authentication" as an explicit future direction. The user now wants to reach the app from other devices on a home network, and eventually from a VPS, without opening it up unauthenticated.

Two separable problems fall out of that:
1. **Something must authenticate requests** once the app is reachable from more than the machine it runs on — today there's no login of any kind, and no actor concept at all (ADR 0011/0022: `audit_log.origin` is `USER`/`SYSTEM`, not an identity).
2. **Something must create the private reachability** in the first place — a home LAN, an overlay network (Tailscale, Headscale, WireGuard, ZeroTier, Netmaker, Nebula, ...), or eventually a VPS. The app itself must not be coupled to which one.

The app stays single-user by design (PRD §4) — this is explicitly *not* a multi-tenant auth system. It's a lock on the door, not a `users` table.

## Decision

### Authentication: single shared credential, session cookie
- One shared username/password, Argon2-hashed, provided via environment variables — no `User` aggregate, no per-user data scoping, no change to any existing table. `AccountService`, `TransactionService`, etc. are untouched; this sits entirely in `infrastructure/web`/a new `infrastructure/auth` package.
- Session-cookie login via Spring Security, not HTTP Basic and not a bearer token in `localStorage`: `POST /api/auth/login` (sets the session cookie), `POST /api/auth/logout` (invalidates it), `GET /api/auth/session` (lets the frontend learn its auth state on boot without tripping normal error handling). Chosen over Basic Auth for logout support and centrally revocable sessions, and over a `localStorage` token because an `HttpOnly` cookie isn't readable by injected JS, cheap insurance alongside the existing CSP (`frontend/nginx.conf`'s `script-src 'self'`).
- Argon2 for the password hash (not BCrypt) — the Password Hashing Competition winner, available via Spring Security's `Argon2PasswordEncoder`. The plaintext password is never written to `.env`/compose files; only its hash is. A one-off Gradle task (mirroring F018's `backup-keygen` precedent for one-off setup tooling) generates the hash from a typed password, using the same `Argon2PasswordEncoder` the app verifies with — no new runtime HTTP endpoint for this.
- Session timeout: 30 days idle. This gates a personal app usually reached from the owner's own devices; the real access control is the network layer (below), not an aggressive session policy. In-memory session store, no Redis — a dev DevTools restart may drop an active session (new `ApplicationContext`, likely a new session manager); accepted, since re-login costs seconds and an external session store is disproportionate infrastructure for one user.
- CSRF: Spring Security's `CookieCsrfTokenRepository.withHttpOnlyFalse()` (cookie `XSRF-TOKEN`), paired with axios's built-in `withXSRFToken: true` (supported by the pinned `axios@1.20.0`) plus `withCredentials: true` on the shared `apiClient`. No custom interceptor code — axios already knows how to read that cookie and attach `X-XSRF-TOKEN`.
- 401/403 responses still conform to the existing RFC 9457 `ProblemDetail` contract (ADR 0026) — but `GlobalExceptionHandler` cannot provide this for Spring Security's `AuthenticationException`/`AccessDeniedException`, since those are thrown in the security filter chain, before Spring MVC dispatch ever reaches a `@ControllerAdvice`. A dedicated `AuthenticationEntryPoint`/`AccessDeniedHandler` pair builds the identical `ProblemDetail` shape directly, reusing `ProblemTypeSlugs`'s derivation helpers. New slugs: `unauthenticated` (401), `access-denied` (403).
- Rate limiting: in scope for v1. An in-memory, per-source-IP failed-login tracker (no new library, no new infrastructure) returns `429` with a new `too-many-login-attempts` slug past a threshold. Cheap to build, meaningful defense-in-depth against a compromised device on the same private network hammering the login endpoint — the overlay network (below) is the primary gate, this is the second one.
- Logging: login attempts are logged as outcome/count only — never the username or password (ADR 0011 is unchanged by this feature, not loosened).
- No change in dev vs. prod: both require real login. A dev-profile bypass was considered and rejected — the dev stack (`docker-compose.yml`'s `full` profile) can itself be the thing exposed over the private network while developing, and bypassing auth there would defeat the purpose for exactly that case.

### Network exposure: a generic bind-address, not a named product
- A new `BIND_ADDR` environment variable (default `127.0.0.1`, preserving today's behavior unchanged) replaces every hardcoded `127.0.0.1:PORT:PORT`-style port mapping for `backend`/`frontend` in both `docker-compose.yml`'s `full` profile and `docker-compose.prod.yml`. Whichever private-network tool is actually in use (Tailscale is the expected real-world choice, but Headscale/WireGuard/ZeroTier/Netmaker/Nebula/a VPN of any kind all work identically) sets `BIND_ADDR` to its own interface IP — the app has no vendor-specific code or config anywhere. TLS termination, if wanted, is an equally generic, separately-chosen concern (e.g. Caddy/certbot) — not assumed to come bundled with whichever overlay tool is used.
- `postgres`/`pgadmin` in `docker-compose.yml` are pinned to `127.0.0.1` **unconditionally**, not tied to `BIND_ADDR` at all. They currently publish with no host-IP prefix at all (`"5432:5432"`, `"5050:80"`), i.e. already bound to every interface including whatever `BIND_ADDR` would later point at — meaning the moment `BIND_ADDR` exposes the app over a private network, the database and its admin UI would be reachable on that same network with their plaintext dev credentials, bypassing the entire authentication layer above. There is no legitimate reason for either to be reachable from outside the host; only the app itself, reached through the authenticated frontend/backend, should ever be exposed via `BIND_ADDR`. `docker-compose.prod.yml` already doesn't publish Postgres's port at all, so prod has no equivalent gap.
- Prod's CORS story is unaffected: nginx already reverse-proxies `/api/` to the backend same-origin (`frontend/nginx.conf`, ADR 0006), so cookie auth in prod needs no `allowCredentials`/cross-origin handling. Dev's `WebConfig` CORS does need `allowCredentials(true)` with an explicit configured origin (replacing the current wildcard-style `allowedOriginPatterns`), since Vite (`:5173`) and the backend (`:8080`) are different origins — though still the same site, so `SameSite=Lax` (the default) still sends the cookie; no HTTPS/`SameSite=None` complication in dev.

## Alternatives considered
- **HTTP Basic Auth.** Simpler (no CSRF, no session state), but no real logout, credentials cached by the browser indefinitely, and no central revocation. Rejected in favor of session cookies for a system expected to eventually sit on a VPS.
- **Bearer token in `localStorage`.** Avoids CSRF entirely, but readable by any injected JS; an `HttpOnly` cookie is strictly safer for the same amount of code, especially stacked with the existing CSP. Rejected.
- **BCrypt instead of Argon2.** Both are supported by Spring Security with no extra dependency complexity worth agonizing over; Argon2 was the user's explicit preference and is the newer, generally-regarded-as-stronger KDF. Accepted.
- **A `users` table / full multi-tenant auth.** Rejected outright — this app is single-user by product decision (PRD §4); that would be a different product, not an access gate, and would require scoping every existing aggregate (accounts, transactions, budgets, ...) by owner, none of which carry that today.
- **Tying network exposure to Tailscale specifically** (e.g. `tailscale serve`, Tailscale-specific ACL headers). Rejected per explicit user request: the app must not assume or depend on one vendor's product, even though Tailscale is the expected real-world choice.
- **A dev-profile authentication bypass.** Considered for faster local iteration, matching `WebConfig`'s existing "CORS is a dev convenience, not a security boundary" precedent. Rejected because the dev stack can itself be exposed over the same private network while developing, which would leave that scenario completely unauthenticated — the one case this feature exists to close.
- **Skipping rate limiting for v1.** Considered, given the overlay network is the primary gate. Rejected once the actual implementation cost was sized as small (an in-memory tracker, no new dependency) — cheap enough to include as defense-in-depth from day one.

## Consequences
- No existing aggregate, table, or business rule changes. This is purely a new cross-cutting `infrastructure/auth`-style layer plus compose/env changes — no migration touches `accounts`, `transactions`, or any other domain table.
- Every controller now sits behind authentication by default; anything that must stay reachable without a session (e.g. the Docker healthcheck's `/actuator/health`) needs an explicit `permitAll` carve-out in the new `SecurityFilterChain`.
- `GlobalExceptionHandler` gains two new slugs it doesn't itself produce (`unauthenticated`, `access-denied` are emitted by the new entry-point/handler pair, not by the existing exception-to-`ProblemDetail` path) — documented as a deliberate second body-building path, the one exception to ADR 0026's "`GlobalExceptionHandler` is the only place that happens" framing, because Spring Security's filter chain architecturally can't reach it.
- Setting `BIND_ADDR` is now the single control for how exposed the whole stack is, in both dev and prod, uniformly — a safer default (`127.0.0.1`) stays the default, and opting into any private-network tool is one env var, not a code change.
- Postgres/pgAdmin's binding in dev changes from "every interface" to "loopback only" regardless of `BIND_ADDR` — closes a real pre-existing gap that predates this feature, independent of whether `BIND_ADDR` is ever changed from its default.
- PRD §3/§7.1/§9 all need updating: the "no authentication"/"bound to localhost only" non-goal and tech-stack claims are no longer accurate, and the "remote/LAN access with authentication" future direction has graduated into actual scope.

## Implementation notes (added when F036 shipped)
- The OpenAPI document and Swagger UI are behind the login like every other path - no dev-only `permitAll`, since that would be exactly the profile-based bypass rejected above. `npm run generate-api-types` therefore signs in first (`frontend/scripts/generateApiTypes.mjs`, credentials from the environment).
- Dev CORS uses an exact origin list (`myfinances.cors.allowed-origins`) rather than a pattern. `allowedOriginPatterns` can in fact be combined with credentials; the exact list is chosen because a `localhost:*` pattern would let any other local page make cookie-carrying calls. The `full` compose profile adds `http://<BIND_ADDR>:5173` so the dev stack works when exposed.
- The rate limiter keys on the socket address, or on nginx's `X-Real-IP` in prod only (the backend is reachable solely through nginx there, which overwrites that header); elsewhere the header is ignored so it cannot be used to evade the limit.
- The session cookie carries `Max-Age` 30 days (persistent), so "stays signed in after closing the browser" holds; it is not `Secure`, because TLS is not assumed - set `SERVER_SERVLET_SESSION_COOKIE_SECURE=true` where a TLS terminator sits in front.
