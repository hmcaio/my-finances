# 0027. Frontend-only i18n with react-i18next: client-only locale, English + Brazilian Portuguese, locale-aware formatting

Status: Accepted
Date: 2026-10-13

## Context

Every UI string in the frontend is hardcoded English, with no i18n library, context, or resolver anywhere in the codebase. Numbers are formatted ad hoc (`.toFixed(2)`/`.toFixed(1)`/`.toFixed(3)` across ~30 files: `AccountsPage`, `BudgetsPage`, `FuelPage`, `DividendHistorySection`, `FiiPage`, every dashboard widget and chart, ...) — dot decimal, no thousands separator, no `Intl.NumberFormat`. One file, `groupByDay.ts`, deliberately hardcodes `'en-US'` for its date label specifically *because* no real i18n existed yet (its own docblock says so); `ActivityPage.tsx` does the same for a time string.

The backend never sends translatable text to begin with: every error response is an RFC 9457 `ProblemDetail` with `detail` always `null` (ADR 0011, ADR 0026/F031), and `MethodArgumentNotValidException` field errors carry a structured `code`, never Jakarta's interpolated message (F032). `type`/`title`/`code` are all mechanically derived slugs that the frontend's own `apiError.ts` maps to English sentences (`PROBLEM_TYPE_MESSAGES`, `VALIDATION_CODE_MESSAGES`) — a frontend-only concern already.

The app is local, single-user, no-auth (PRD §3/§4), with no settings/preferences entity anywhere in the domain model. It already has one precedent for a per-device UI preference with no backend involvement: `ColorModeProvider`/`useColorMode` (dark/light mode) — a React context seeded from a browser signal (`prefers-color-scheme`) on first load, then persisted to `localStorage`, with no server round trip.

Several taxonomy tables (`categories`, `payment_methods`, `institutions`, `investment_categories`, `investment_subcategories`) are seeded by Flyway migrations (V2, V12, V13, V14, V18, V20) with literal English names (`'Groceries'`, `'Debit Card'`, `'Fixed Income'`, ...). Only a small subset of these carry a `built_in` flag (one row per category type, plus the one seeded institution) — the bulk of the starter data is otherwise indistinguishable, at the schema level, from a row the user typed themselves.

## Decision

- **Frontend-only.** No backend change of any kind — the backend already emits no translatable text, so there is nothing for it to localize. This feature touches `frontend/` exclusively.
- **`react-i18next` + `i18next`** for string translation (interpolation, pluralization) instead of a hand-rolled context+dictionary scheme. Two locales only: `en`, `pt-BR`.
- **Locale state mirrors `ColorModeProvider`'s existing shape exactly**: a new `LocaleProvider`/`useLocale` (`src/hooks/locale/`) is a client-only React context, `localStorage`-persisted (`my-finances:locale`), seeded on first load from `navigator.language` (starts with `pt` → `pt-BR`; otherwise → `en`; anything ambiguous defaults to `pt-BR`, the app's primary real-world context — BRL amounts, fuel prices in R$, `America/Sao_Paulo` as the backend test timezone). No `i18next-browser-languagedetector` dependency — the detect-then-persist logic is simple enough to write by hand, same as `ColorModeProvider`'s own `getInitialMode`. Toggled from a header `IconButton` next to the existing dark/light toggle (`Layout.tsx`). No new settings page, no backend persistence: a dedicated Settings concept is speculative (no second feature needs one yet — CLAUDE.md's "don't design for hypothetical future requirements"), and a single client-side preference is consistent with the single-user/no-auth scope.
- **Scope = UI chrome, not user data**: every label, button, nav item, validation/error message (`PROBLEM_TYPE_MESSAGES`, `VALIDATION_CODE_MESSAGES`) is externalized to translation resources and must have both an `en` and a `pt-BR` entry. Category names, transaction descriptions/notes, and any other free text the user typed are never translated.
- **Formatting changes with locale, not just strings.** A shared `Intl.NumberFormat`/`Intl.DateTimeFormat`-backed utility (`src/i18n/format.ts`) replaces every ad hoc `.toFixed()` call and the hardcoded `'en-US'` in `groupByDay.ts`/`ActivityPage.tsx`: `pt-BR` renders `1.234,56` / `16 de março de 2026`, `en` renders `1,234.56` / `March 16, 2026`, each preserving its call site's existing decimal precision (2 for money, 3 for liters, 1 for odometer/km). Amounts stay symbol-less in both locales — introducing `R$`/`$` is a separate, unrelated decision (PRD §3 already has no multi-currency support and no symbol today).
- **Seeded/built-in taxonomy names are translated by exact-string match, not by a schema change.** A small per-entity-type lookup (the literal seeded English name → its translation) is checked before rendering a `Category`/`PaymentMethod`/`Institution`/`InvestmentCategory`/`InvestmentSubcategory` name; a row whose current name doesn't match any known seed string (because the user renamed it, or created a new one) renders verbatim. No new `code` column, no backend change — the existing `built_in` flag doesn't cover most of the seeded rows anyway (V14 only flags one row per category type), so a schema-level fix would need to touch five entities for a cosmetic problem this app's scale doesn't need solved more durably.
- **Full coverage at ship, enforced at build time.** TypeScript module augmentation types every translation key against the `en` resource, so a key missing from `pt-BR.json` (or vice versa) is a compile error, plus a test asserting both locale files have identical key sets — no runtime fallback-to-English-key path to maintain.

## Consequences

- A one-time refactor touching every page/component currently calling `.toFixed()` (~30 files) to go through the shared formatter instead — larger than a pure string-translation pass, but a locale switch that doesn't also reformat numbers reads as broken on a translated screen.
- Every future PR that adds user-facing text must add a key to both locale files, or the build fails — this is now a standing cross-cutting rule, the reason this is an ADR rather than a plain feature.
- Seeded-data translation is best-effort name matching: correct for a fresh install's starter data, and it silently (and correctly) stops applying the moment a user renames a built-in row — that row is then ordinary user data, shown in whatever language the user typed it in.
- No server-side or multi-user locale concept exists. If a future feature introduces real multi-user support (PRD §9) or a persisted settings entity, it will need its own decision about whether locale moves server-side — this ADR only covers the current single-user, client-only case.
- Currency symbols and locales beyond `en`/`pt-BR` are explicitly deferred (PRD §9).
