# 0026. Structured error responses: RFC 9457 Problem Details

Status: Accepted
Date: 2026-10-12

## Context
ADR 0011's security-audit fix made every error response status-code-only: `GlobalExceptionHandler` never returns exception text, and `spring.web.error.include-message: never` backs that up at the framework level. An unexpected exception gets a fixed generic body (`{"message": "An unexpected error occurred"}`); every `@ResponseStatus` exception and every one of Spring's own `ErrorResponse`-implementing exceptions gets rethrown to Spring's default resolver and sends **no body at all** — only the status code.

That closed a real leak, but it also means the frontend can't distinguish two different causes behind the same status code. A survey of the 69 `@ResponseStatus` exception classes (43×409, 16×404, 10×400) found several controller operations where more than one distinct exception maps to the *same* status:
- `POST /api/budgets` → `BudgetAlreadyExistsException` or `CategoryNotExpenseException`, both 409.
- `CategoryService.rename`/`delete` → 3-4 distinct 409 causes each (`FuelCategoryException`, `DividendCategoryException`, `CategoryNameAlreadyExistsException`, `BuiltInCategoryException`, `CategoryInUseException`).
- `InstitutionService.delete` → `BuiltInInstitutionException` or `InstitutionInUseException`, both 409.
- `InvestmentHoldingService.close` → `InvestmentHoldingAlreadyClosedException` or `InvestmentHoldingNotEmptyException`, both 409.
- `AllocationPlanService.setAllocation` → two 400 causes plus a third, unrelated 409.
- `TransferService.requireExactlyOneRequestShape` → two 400 causes, plus three more 409 causes elsewhere in the same method.

Today the frontend papers over this with a single hardcoded `conflictMessage` string per API-client call site (`frontend/src/api/core/apiError.ts`'s `unwrap()`, 38 call sites across 20 files) — one generic message regardless of which of the above actually fired, which is often wrong or misleading for the case that didn't match the common one.

## Decision
- Every error response — all 69 `@ResponseStatus` exceptions, Spring's own built-in exceptions previously special-cased and rethrown (`HttpMessageNotReadableException`, `TypeMismatchException`, and any exception implementing Spring's `ErrorResponse`), and the generic unexpected-exception fallback — now returns one uniform [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) ("Problem Details for HTTP APIs", obsoleting RFC 7807) body via Spring's `ProblemDetail`: `type`, `title`, `status`, `instance`. **`detail` is always omitted/null** — this is the one field the RFC expects to carry human-readable specifics, and it is exactly the field ADR 0011 forbids populating with exception text or entity data. That prohibition is unchanged; this ADR only adds a safe, stable identifier alongside it.
- **`type` is auto-derived from the exception's simple class name**: `Exception` suffix stripped, PascalCase converted to kebab-case, namespaced as a URN — `urn:my-finances:error:<slug>` (e.g. `AccountHasHistoryException` → `urn:my-finances:error:account-has-history`). No per-exception authoring: the class name is already the identifier `GlobalExceptionHandler` logs at INFO as the safe way to tell which case fired (ADR 0011), so this reuses that single source of truth instead of introducing a second one (an explicit code field/annotation every exception would need to declare).
- **A URN, not a dereferenceable `https://` URI.** RFC 9457 doesn't require `type` to resolve to anything (§4.1.2 Benefits "SHOULD... SHOULD NOT be assumed to be dereferenceable" language) — it only needs to be a URI reference, and a URN carries no implication of a live endpoint. This app has no public doc site (PRD §7.3, ADR 0006) to host `/errors/*` pages, and an `https://` URI that 404s reads as a broken link.
- **Classes duplicated across aggregate packages collapse to the same `type` on purpose.** `AccountClosedException` exists separately in `application/transfer`, `application/transaction` and `application/recurringtemplate` (and `AccountTypeNotAllowedException` in two packages) only because domain packages may never import another aggregate's package (ADR 0014's ArchUnit rule) — the duplication is a code-organization artifact, not a difference in the real-world condition. Same slug for all of them is correct, not a collision to disambiguate.
- **The generic 500 case gets a fixed slug**, `urn:my-finances:error:internal-error`, rather than deriving one from whatever exception actually fired — the set of exceptions that can reach that branch is unbounded (any uncaught `RuntimeException`, a third-party library's own exception type), and a long tail of ad hoc slugs derived from internal class names is its own small leak surface. "Unexpected" stays one stable identifier.
- `title` is a static humanized form of the slug (e.g. "Account has history"). `instance` is the request's method+path, matching `RequestLoggingFilter`'s existing access-line convention (no query string).
- **`GlobalExceptionHandler` stops rethrowing to Spring's default resolver chain.** It now builds the `ProblemDetail` body itself for every case it previously rethrew (its own `@ResponseStatus` exceptions, Spring's `ErrorResponse` exceptions, and the two 400-mapped non-`ErrorResponse` exceptions from issue #19), using the same slug-derivation utility throughout. The three-way special-case list from ADR 0011 is removed, not grown.
- **Big-bang migration.** One rewrite of `GlobalExceptionHandler`, not an opt-in per exception — auto-derivation means no per-exception authoring gates a gradual rollout, so there is no transition state worth preserving.
- **OpenAPI documents error shapes for the first time** (the codebase has zero `@ApiResponse` usage today): a shared `ProblemDetail`-shaped response schema (fields typed as plain strings) referenced via `@ApiResponse` per controller operation, with that operation's actual possible `type` values listed in the response `description` text — human-readable, not a compile-time enum/union in generated `schema.ts`.
- **Frontend replaces its 38 per-call-site `conflictMessage` hardcodes with one central `type → message` lookup** in `apiError.ts`, with no per-call-site override escape hatch.
- **Bean-validation (`@Valid` field-level) 400s are explicitly out of scope.** They need a list-of-violations shape, not a single `type` per response, and are the intended next design once this ships.

## Alternatives considered
- **Keep the empty-body contract, just add more `conflictMessage` overrides.** Doesn't scale, and several endpoints above already hide 2-4 distinguishable causes behind one status code — no amount of call-site-level messaging fixes that without knowing which cause fired.
- **An explicit code/type field each exception class declares**, instead of auto-deriving from the class name. Rejected: boilerplate across all 69 (soon more) exception classes for a value already recoverable from the class name that `GlobalExceptionHandler` already treats as the safe identifier.
- **A dereferenceable `https://` URI for `type`.** Rejected: no public doc site exists or is planned (PRD non-goals), and a non-resolving `https://` URI looks broken in a way a URN doesn't.
- **A compile-time enum/union of `type` values per operation in the generated OpenAPI schema.** Rejected for now: needs a bespoke springdoc customizer for marginal gain, since the frontend already does a runtime string check; a human-readable description is enough for a local single-user app. Revisit only if a missed case actually causes a bug.
- **Disambiguating slugs for classes duplicated across aggregate packages** (e.g. `transfer-account-closed` vs. `transaction-account-closed`). Rejected: the duplication exists only for the ArchUnit rule, not because the underlying condition differs; a shared slug is more useful to the frontend than three it would map to the same message anyway.
- **Deriving the 500 case's `type` from the actual unexpected exception's class name**, for consistency with every other case. Rejected: that set is unbounded and includes exception types never vetted for safety, unlike the curated ~69 plus Spring's own well-known classes.

## Consequences
- The frontend can distinguish same-status, different-cause errors (the budget/category/institution/holding/allocation-plan/transfer cases above) without the backend leaking any exception text or entity data — `detail` stays null everywhere, preserving ADR 0011's fix.
- `GlobalExceptionHandler` gets simpler: the three-way special-case rethrow list is replaced by one uniform body-building path reused for every case, including Spring's own exceptions.
- `GlobalExceptionHandlerTest`'s pinned body assertion for the 500 case changes shape (`ProblemDetail` fields instead of `{"message": "..."}`), and every REST integration test that only asserted `status().isNotFound()`/`isConflict()`/`isBadRequest()` with no body check should gain a `type` assertion, since that value is now a tested contract rather than absent.
- The frontend loses the ability to write a bespoke per-call-site message beyond the central `type → message` map; a screen that genuinely needs different phrasing for the same `type` must branch on it at the UI layer, not via a new `unwrap()` parameter — the whole point of this change is removing that duplication.
- OpenAPI's error documentation is human-description-only, not type-checked — `schema.ts` won't catch a missed `type` case at compile time.
- Bean-validation (`@Valid`) 400s are untouched by this ADR and keep today's empty-body behavior until a follow-up design gives them their own (list-shaped) treatment.
