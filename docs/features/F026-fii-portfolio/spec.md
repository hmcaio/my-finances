# F026 — FII Portfolio

## Summary
A dedicated page for managing FIIs (Brazilian real-estate funds) in more detail than the general Investments page gives: a ticker field and a new sector-level `InvestmentSegment` on `InvestmentProduct`, a versioned target `AllocationPlan` (percent per FII), four allocation pie charts (actual/planned × ticker/segment), and dividend tracking (a dedicated `dividend_category` on `Category`, a `Transaction.investmentHoldingId` link, a register form and a history view). PRD §5.13, §6.13. See [ADR 0023](../../adr/0023-fii-allocation-plan-and-dividends.md) for the full rationale.

## Scope
- `InvestmentProduct` gains optional `ticker` (`MAX_NAME_LENGTH`) and optional `segmentId`. Generalized fields — usable by any product — but this feature's UI and validation only ever touch FII-subcategory ("REITs (FIIs)") products.
- New `InvestmentSegment` aggregate: flat, user-editable taxonomy (same shape as `InvestmentCategory`), CRUD, delete blocked while referenced by any product.
- New `AllocationPlan` (one implicit singleton) + `AllocationPlanVersion` (versioned by `YearMonth`, same pattern as `Budget`/`BudgetVersion`) + `AllocationPlanEntry` (`investmentProductId`, `targetPercentage`). Entries of one version must sum to exactly 100%; every entry's product must be classified under the "REITs (FIIs)" sub-category.
- `Category` gains `dividend_category` (boolean, independent of `built_in` and `fuel_category`, at most one row). Seeded once via migration onto a new INCOME category named "Dividends". Delete and rename both blocked while set (stricter than `fuel_category`, which still allows rename — the dividend history view's grouping depends on this category's identity staying put).
- `Transaction` gains optional `investmentHoldingId`, present if and only if the transaction's category is the dividend category.
- New computed-on-read FII portfolio summary, per product (restricted to the FII sub-category): cotas currently held (running sum of tagged trades' `quantity`, buys plus, sells minus), amount contributed (net: buy `amount` minus sell `amount`), current value (sum of holdings' latest snapshots, existing F009/F022 query), latest snapshot date, `needsSnapshot` (existing). Aggregated per product across every holding/account.
- New FII page (`/fii`): portfolio list (one row per ticker, closed holdings hidden by default with a filter to reveal them), allocation-plan editor, four pie charts (actual by ticker, actual by segment, planned by ticker, planned by segment — "No segment" bucket for an unsegmented product in both), a "Register Dividend" form, and dividend history.
- Investment segment CRUD under Settings, alongside Investment Category/Subcategory.
- CSV export (F013): new `investment_segments.csv`, `allocation_plan_entries.csv` (date-range filtered by its version's `effectiveFrom`, like `budgets.csv`); `investment_products.csv` gains `ticker`/`segment_id`/`segment_name`; `transactions.csv` gains `investment_holding_id` (empty for non-dividend rows).
- Out of scope: dividend yield/% or any price-derived calculation (no per-cota price exists, PRD §3/§9); rebalance-suggestion amounts; generalizing the page itself, or the allocation plan's product-membership validation, to stocks/ETFs (the underlying `ticker`/`segmentId` fields are generic, the UI and plan aren't); a `RecurringTemplate` restriction for the dividend category (its only extra field, `investmentHoldingId`, is a simple reference with no interdependent sub-fields, unlike `FuelDetails` — nothing structurally forces a rejection).

## Decisions
See [ADR 0023](../../adr/0023-fii-allocation-plan-and-dividends.md) for the full rationale. Summary:
- **`ticker`/`segmentId` live on `InvestmentProduct`, not a new FII-only aggregate.** Keeps the existing taxonomy/holding/snapshot model as the single source for any ticker-based instrument, reusable later for stocks/ETFs without a migration.
- **`InvestmentSegment` is a new, independent, flat taxonomy — not a third tier under `InvestmentSubcategory`.** Segment (what kind of real estate) is orthogonal to asset class; most sub-categories have no meaningful segment at all.
- **The allocation plan versions like `Budget`, not a single mutable row.** So "what was my target 6 months ago" stays answerable, consistent with why `Budget`/`RecurringTemplate` are versioned (ADR 0002).
- **Entries must sum to exactly 100%.** Simpler mental model; the planned pie chart always fills the circle.
- **"Cotas held" and "amount contributed" are computed on read, never stored** — sums of already-recorded `Transfer.quantity`/`amount`, the same style F009's value series already uses for `units`/`contributed`. Not a new price-derived calculation (PRD §3, amended alongside this feature to say so explicitly).
- **Dividend = `Transaction` + `investmentHoldingId`, gated by a dedicated `dividend_category` flag** — mirrors `FuelDetails`/`fuel_category` (ADR 0021), reusing the same "XOR invariant enforced in the application layer" shape. Unlike `fuelCategory`, this flag also blocks rename (javadoc on `Category.isFuelCategory()` only promised delete-blocking; the dividend history view needs the category's identity, not just its existence, to stay stable).
- **A dedicated "Register Dividend" form, not the generic transaction form.** Faster for the actual recurring workflow (several tickers, monthly), pre-filtered to FII holdings.
- **FII list aggregates by ticker across accounts; closed holdings hidden by default.** Matches how someone thinks about "my KNRI11 position" regardless of brokerage; a status filter (open/closed/all, default open) reveals sold-out positions, same pattern F023's product-list status filter already uses.

## Backend

### Domain
- `domain/investmentsegment/InvestmentSegment.java`: `id`, `name` (`MAX_NAME_LENGTH`, non-blank, domain-constructor-checked). `rename(...)` mutator. Same shape as `InvestmentCategory`; no import of any other aggregate.
- `domain/investmentproduct/InvestmentProduct.java` (F008/F022): gains `ticker` (nullable, capped `MAX_NAME_LENGTH`) and `segmentId` (nullable), folded into the existing full-replace `edit(...)` mutator and both factory methods. No new invariant linking `ticker`/`segmentId` to category/sub-category — any product may carry them, even though only FII-subcategory products get a UI for it.
- `domain/allocationplan/AllocationPlan.java`: `id` only — a one-row marker aggregate (like `Budget` is one row per category, this is one row, period). `AllocationPlanService` ensures it exists (create on first use) rather than it being user-creatable via the API.
- `domain/allocationplan/AllocationPlanVersion.java`: `id`, `planId`, `effectiveFrom` (`YearMonth`), `entries` (`List<AllocationPlanEntry>`, value objects: `investmentProductId`, `targetPercentage`). Invariants: at least one entry, no duplicate `investmentProductId` within a version, every `targetPercentage` `> 0`, and the entries' percentages sum to exactly `100`. Mirrors `BudgetVersion`'s shape: `create`/`reconstitute` factories, `updateEntries(...)` as the one same-month-correction mutator (parallel to `BudgetVersion.updateCap`), `resolveEffective(versions, targetMonth)` static resolver. No tombstone — stopping the plan isn't a modeled concept for v1 (not asked for; a plan simply isn't edited further once stopped is out of scope).
- `domain/category/Category.java` (F002/F024): gains `dividendCategory` (boolean, immutable after creation, same read-only shape as `builtIn`/`fuelCategory` — `create` always yields `false`, only `reconstitute` carries it in).
- `domain/transaction/Transaction.java` (F004/F024): gains nullable `investmentHoldingId`; the existing full-replace `edit(...)` mutator takes it too. No import of `domain.investmentholding` or `domain.category` beyond the existing `CategoryType` — the cross-aggregate invariant lives in `TransactionService`, same as `FuelDetails`'s.

### Application
- New `InvestmentSegmentService`: `create`/`rename`/`findAll`/`delete`. `delete` is `409` (`InvestmentSegmentInUseException`) while any product references it (`investmentProductRepository.existsBySegmentId`), same shape as `VehicleService.delete`'s in-use check.
- `InvestmentProductService` (F008/F022): `create`/`edit` gain `ticker`/`segmentId` (both optional, no new validation beyond the existing length cap — a `segmentId` referencing an unknown segment is `404`).
- New `AllocationPlanService`: `getCurrent(month)` resolves the effective version (creating the implicit `AllocationPlan` row on first write if absent); `setAllocation(entries, effectiveFrom)` creates a new version or replaces the same-month one (mirrors `BudgetService.setCap`) — validates every entry's product exists and is classified under the "REITs (FIIs)" sub-category (`404`/`409 AllocationPlanEntryNotFiiException`), rejects a sum other than exactly `100` (`400 AllocationPlanSumInvalidException`), rejects a duplicate product within the entries (`400`). `findVersions()` for history.
- `CategoryService` (F002/F024): `delete` gains a `dividend_category` guard (`DividendCategoryException`, `409`), parallel to (not reusing) the `fuel_category`/`built_in` guards; `rename` also gains a `dividend_category` guard (`409`, same exception) — the one divergence from `fuelCategory`'s precedent, since this flag's identity (not just existence) backs the dividend history grouping.
- `TransactionService` (F004/F024): create/edit validate the dividend invariant — category is the dividend category XOR `investmentHoldingId` is null is rejected (`400 InvestmentHoldingCategoryMismatchException`); when present, `investmentHoldingId` must reference an existing `InvestmentHolding` (`404`).
- New `FiiPortfolioQuery` (application-layer, read-only, `investmentreport` package alongside `InvestmentValueSeriesQuery`): for every `InvestmentProduct` under the "REITs (FIIs)" sub-category with at least one non-closed holding (or every holding, when a status filter asks for it), returns `{productId, ticker, name, segmentId, cotasHeld, amountContributed, currentValue, latestSnapshotDate, needsSnapshot, hasOpenHolding}`. `cotasHeld`/`amountContributed` computed the same way `InvestmentValueSeriesQuery.seriesOf` already derives `units`/`contributed` — reusing `TransferRepository.findByInvestmentProductId` and `trade.getTradeDetails().quantity()`/`trade.getAmount()`, direction via holding account membership — but as a running total over all trades to date, not bucketed by month. `currentValue`/`needsSnapshot` reuse `LatestInvestmentSnapshotQuery`/the existing freshness query, summed per product across its holdings.
- New `FiiAllocationQuery`: actual allocation by ticker and by segment, both restricted to the FII sub-category, each row `{productId or segmentId, totalValue, percentage}` (percentage of the FII-only total, not the whole portfolio) — reuses `FiiPortfolioQuery`'s `currentValue` per product, summed by `segmentId` for the segment grouping (a `null` `segmentId` groups as "No segment"). Planned allocation by ticker is the current `AllocationPlanVersion`'s entries directly; planned by segment sums `targetPercentage` by each entry's product's `segmentId` (same "No segment" grouping).
- Dividend history: `GET` reuses `TransactionRepository` filtered by the dividend category, date range and `investmentHoldingId`/product (via a join to holdings), with totals grouped by product and by month — a new `DividendHistoryQuery`.

### Persistence
- New migration `V20__fii_segments_allocation_plan_dividends.sql` (check the highest existing `V` number first — `V19` at the time of writing):
  1. `investment_segments`: `id uuid pk`, `name varchar(100) not null unique`, audit columns.
  2. `investment_products`: add `ticker varchar(100)`, `segment_id uuid references investment_segments` (indexed).
  3. `categories`: add `dividend_category boolean not null default false`, partial unique index `uq_categories_single_dividend_category ON categories (dividend_category) WHERE dividend_category`. Seed: insert a fresh INCOME category named "Dividends" with `dividend_category = true` (no adopt-existing step like `V18`'s fuel-category seed — "Dividends" as an income category name is unlikely to collide, and even if it does, inserting fresh avoids silently repurposing a category the user may already use for something else).
  4. `transactions`: add `investment_holding_id uuid references investment_holdings`. `CHECK` enforcing the XOR with the dividend category is **not** a DB constraint (unlike `FuelDetails`'s checks) — it would need a cross-table lookup (`categories.dividend_category`) a plain `CHECK` can't express; enforced at the application layer only, same as any other cross-aggregate invariant in this codebase.
  5. `allocation_plans`: `id uuid pk`, audit columns (no other columns — the singleton marker row).
  6. `allocation_plan_versions`: `id uuid pk`, `plan_id uuid not null references allocation_plans`, `effective_from date not null`, `UNIQUE (plan_id, effective_from)`, audit columns.
  7. `allocation_plan_entries`: `id uuid pk`, `version_id uuid not null references allocation_plan_versions`, `investment_product_id uuid not null references investment_products`, `target_percentage numeric(5,2) not null check (target_percentage > 0)`, `UNIQUE (version_id, investment_product_id)`, audit columns. The exactly-100% sum is an application-layer check (a DB `CHECK` can't aggregate across sibling rows); `numeric(5,2)` bounds a percentage to `0.01`–`999.99`, generous beyond the valid `0`–`100` range (DTO `@DecimalMax` enforces the real bound).
- `ticker` reuses `TextFieldConstraints.MAX_NAME_LENGTH` (flat-taxonomy-style name field); `target_percentage` is a deliberate new exception to the root CLAUDE.md `numeric(19,2)` money-column rule (it isn't money) — document it there alongside F009's `numeric(19,8)` and F024's `numeric(19,3)`/`numeric(19,1)`.
- DTOs bound `targetPercentage` with `@DecimalMin("0.01")`/`@DecimalMax("100")`.

### API
- `POST /api/investment-segments` (`{name}`), `GET /api/investment-segments`, `PATCH /api/investment-segments/{id}` (`{name}`), `DELETE /api/investment-segments/{id}`.
- Investment product create/edit bodies (F008/F022) gain optional `ticker`, `segmentId`; responses gain the same fields.
- `GET /api/fii/portfolio?status=OPEN|CLOSED|ALL` (default `OPEN`) → `FiiPortfolioQuery` rows.
- `GET /api/fii/allocation?basis=ACTUAL|PLANNED&groupBy=TICKER|SEGMENT` → percentage rows for one of the four charts.
- `GET /api/fii/allocation-plan`, `GET /api/fii/allocation-plan/versions`, `PUT /api/fii/allocation-plan` (`{entries: [{investmentProductId, targetPercentage}], effectiveFrom}` — creates or same-month-replaces a version; `400`/`404`/`409` per the service's validation above).
- Transaction create/update bodies (F004) gain optional `investmentHoldingId`. `GET /api/fii/dividends?productId=&from=&to=` → dividend transactions with ticker joined in, plus `GET /api/fii/dividends/totals?groupBy=TICKER|MONTH`.
- Regenerate `frontend/src/api/generated/schema.ts`.

- Investment product form (F008/F022): optional ticker text field and segment select alongside category/sub-category.

- Investment segment CRUD screen under Settings, alongside Investment Category/Subcategory's existing pattern.
