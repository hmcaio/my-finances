## PR 3 — Pilot: Transactions
- [x] Primitive change found by the pilot: on tablet, `ResponsiveTable` adds a leading chevron column so each row can expand its hidden (`tabletPriority: 'low'`) columns as label/value pairs (`aria-expanded`, details row spanning the table); no page code needed. Unit tests plus an e2e check on Transactions (tablet only).
- [x] Migrate Transactions to all four primitives, with a `renderCard` override; Add and Edit open a `ResponsiveDialog` at every size (full screen below `sm`).
  - Decision (revised after review): Transactions never had inline row editing, only one combined add/edit form panel below the table. The panel is removed at every size: an `Add transaction` button in the page header and each row's/card's Edit open the fields (`TransactionFormFields`) in a `ResponsiveDialog` driven by the same form state and mutations (regular dialog from `sm` up, full screen below). A save error shows inside the open dialog (the page banner sits behind it). Pages that already have true inline row editing keep it on tablet/desktop (decide per page in PR 4).
  - Tablet hides only the Payment Method column (`tabletPriority: 'low'`); date, category, account, amount, description and actions stay. Cards (`renderCard`): description and signed, coloured amount on top, then `date · category`, then `account · payment method`, then Edit/Delete.
  - Filters: `ResponsiveFilterBar` replaces the outlined "Filters" panel (its "Clear filters" now shows only while a filter is active). The old panel box and heading are gone on all sizes.
  - `AccountTransactionList` (read-only embed in the account detail page) is not migrated: it has no actions and belongs to the Accounts batch of PR 4, where it can reuse the card layout.
- [x] Playwright spec (`e2e/transactions.spec.ts`): no overflow, cards on mobile, table on tablet/desktop, filter button on mobile, add dialog full-screen on mobile only, and no inline form panel at any size.
- [x] Adjust primitives if the pilot shows gaps (record the change here).
  - No primitive changed; the pilot fit the existing APIs. Note for tests: jsdom without `setViewportWidth` counts as the tablet band (neither `down(sm)` nor `up(lg)` matches), so assertions on the full desktop table need `setViewportWidth(VIEWPORT.desktop)`.

## PR 4 — Remaining features (batches)
Each batch: migrate pages, decide per-page details from the actual markup and record them under the batch, add Playwright checks, keep desktop behaviour unchanged.
- [x] Accounts and transfers.
  - `AccountsPage` (`ResponsiveTable`, generic card): Name (link) is the card title, Institution and Type muted lines, then labelled Balance and Status. Tablet hides only Type (`tabletPriority: 'low'`, behind the row expander). The "Show closed accounts" switch is a single toggle, not a filter row, so it stays inline at every size (no `ResponsiveFilterBar`).
  - Accounts add: the "Add account" panel is removed; a header `Add account` button opens `AccountCreateForm` in a `ResponsiveDialog` (full screen below `sm`). `AccountCreateForm` gained a `dialog` mode (`FormGrid` in `DialogContent`, buttons in `DialogActions`, `banner` for the error, `onCancel`); its default inline layout is unchanged because the onboarding screen (Dashboard/Export/Onboarding batch) still uses it. `InstitutionSelect` gained `fullWidth` for grid cells.
  - Accounts edit: the rename is true inline editing (`InlineEditActions`), so it stays inline on tablet/desktop and, on mobile, the card's Edit opens a full-screen `ResponsiveDialog` (`AccountEditFields`) driven by the same `editingId`/name/institution state and mutation. `AccountNameField` and `isAccountEditValid` are shared by both surfaces. Save errors show inside the open dialog.
  - `AccountDetailPage`: no table of its own. Header wraps (chip and long names), section and balance-card padding is `p: 2` below `sm`, and it already stacks in one column.
  - `AccountTransactionList` / `AccountTransferList` (read-only embeds): `ResponsiveTable` (cards below `sm`, no actions). Transactions hides Payment Method on tablet like the page; the transfer list fits all five columns on tablet. Primitive change: `ResponsiveTable` got an `embedded` prop that drops its outlined frame, so the table does not nest a border inside the detail page's outlined section.
  - `TransfersPage`: same shape as Transactions. `ResponsiveTable` with the generic card (description plus Buy/Sell chip as title, date muted, labelled From/To/Amount; all five columns fit on tablet), `ResponsiveFilterBar` for From/To/Account, `PaginationControls`. The form panel is removed: header `Add transfer` and each row's/card's Edit open `TransferForm` in a `ResponsiveDialog` at every size (there is no inline row editing to preserve). `TransferForm` gained a `dialog` mode (`FormGrid`, one column on phones, Description/Notes and the trade section spanning; trade quantity/price/taxes in a three-column grid from `sm`); its inline layout is unchanged for the buy/sell dialog on the investment product page (Investments batch).
  - Playwright: `e2e/accounts.spec.ts` (list, detail route) and `e2e/transfers.spec.ts`.
- [x] Budgets and recurring templates.
  - `BudgetsPage` (`ResponsiveTable`, generic card): Category is the card title, Current cap and Effective from render as labelled fields; no `tabletPriority` (all three columns fit on tablet, like Transfers). Add: the "Add budget" panel is removed; a header `Add budget` button opens the category picker and cap field in a `ResponsiveDialog` (full screen below `sm`) - the fields aren't reused elsewhere, so they're inline in the dialog rather than a separate form component. Edit cap: true inline editing (`InlineEditActions`, "Edit cap"/"Resume budget" for a stopped budget), so it stays inline on tablet/desktop and, on mobile, the card's Edit opens a full-screen `ResponsiveDialog` (`BudgetCapField`, shared by both surfaces) driven by the same `editingId`/`editingCap` state and mutation; the dialog title and submit label still read "Resume budget"/"Resume with this cap" for a stopped row. "Stop budget" (the tombstone action, issue #61) is a separate icon button next to the edit action in both the row and the card footer - it keeps its existing `ConfirmDialog` unchanged at every size, since a short confirmation reads fine as a card rather than needing the full-screen treatment. `BudgetVsActualReport` is not table-shaped (a list of progress bars, not rows/columns): per the spec's guidance for non-table content, it keeps its own single-column layout and `LoadFailedNotice`; only its per-line header row (category name vs. the "actual / cap" text) gained `flexWrap` and `overflowWrap: 'anywhere'` so a long category name can't force horizontal overflow on a narrow phone.
  - `RecurringTemplatesPage` (`ResponsiveTable`, custom `renderCard` like Transactions): the card leads with description and the Active/Stopped chip, then `category · account`, then `amount · Day N`, then actions. Tablet hides only Category (`tabletPriority: 'low'`) - Description already identifies the bill and Account/Amount/Day/Status are what's needed to manage it day to day, while Category matters more for the Budgets page's own report; Account, Amount and Day of month all stay visible (unlike Transactions, which hid Payment Method - there's no single clearly-auxiliary "how" column here, so Category was the deliberate pick). Add: the "Add recurring template" panel is removed; a header button opens the same five fields (category, account, description, amount, day of month) in a `ResponsiveDialog`, inline rather than a shared component since nothing else reuses that exact field set. Amount/day-of-month edit: true inline editing, so it stays inline (narrow fields, `RecurringTemplateAmountField`/`RecurringTemplateDayOfMonthField`) on tablet/desktop, and on mobile the card's Edit opens a full-screen dialog with the same two fields full width (`RecurringTemplateEditFields`, composing the same two field components). The Stop/Reactivate toggle stays a plain icon button (no confirmation before or after) at every size, matching its existing behaviour.
  - `PendingOccurrencesWidget`: read as markup, it is a genuine 5-column data table (due date, description, category, account, amount) with per-row confirm/dismiss actions, not a list-with-add-form - so it gets the same `ResponsiveTable` treatment as any other 3+ column list (custom `renderCard`: description and amount up top, then `due date · category`, then account), with Category hidden on tablet (`tabletPriority: 'low'`, same call as the templates table above so both lists behave consistently on one screen when both are on `RecurringTemplatesPage`). The confirm form (pre-filled amount/date/account, always-required payment method) moves from a plain `Dialog` into a `ResponsiveDialog` with its fields in a `FormGrid` (2-up from `sm`, 1 column on phones); the dismiss confirmation keeps `ConfirmDialog` unchanged. Embedding stays exactly as before (no `embedded` prop): the widget is not nested inside another outlined section on either host page, so it keeps its own outlined frame.
  - Side effect: migrating `PendingOccurrencesWidget` off a plain `<Table>` to `ResponsiveTable` (cards below `sm`) fixed the Dashboard's known mobile overflow from PR 1 (the widget no longer stretches to a 522px min-content table width in a 358px column) as a byproduct, ahead of the Dashboard batch below. `smoke.spec.ts`'s `test.fail` marker for that (added in PR 1) started failing "unexpectedly passing," so it was removed in this batch rather than carried forward - the Dashboard batch's own remaining item is unaffected (the widget grid's column counts and the other widgets).
  - Playwright: `e2e/budgets.spec.ts` and `e2e/recurring.spec.ts` (list + report/widget, cards vs. table, tablet row expander, add/edit dialogs full-screen only on mobile, confirm/stop dialogs, empty states).
