# F027 — Trade Confirmations

## Summary
Generalizes a buy/sell `Transfer` (F009, ADR 0012) from "one cash movement tagged with at most one product" to "one cash settlement with one-or-more product lines" — matching the real-world *nota de negociação*, which can list several products under one aggregate tax figure. Replaces `InvestmentTradeDetails` with `TradeConfirmation` (a list of `TradeConfirmationLine`s) and makes the backend derive and enforce the settlement `amount`/direction from the lines, rather than trusting a user-typed figure. See [ADR 0024](../../adr/0024-trade-confirmations-as-multi-line-transfers.md), which this spec implements.

## Scope
- `Transfer` carries zero-or-one `TradeConfirmation` (replacing nullable `investmentProductId` + `InvestmentTradeDetails`). A confirmation has one shared cash account, one shared `INVESTMENT` account, a single `taxes` figure (stays on `Transfer`, never apportioned), and one-or-more `TradeConfirmationLine`s: `productId`, `side` (BUY/SELL), `quantity`, `unitPrice`, optional `resultingBalance`, optional `closeHolding` (SELL-only).
- Mixed BUY/SELL lines in one confirmation; the same product on more than one line (partial fills); the same product as both a BUY and a SELL line (same-day round-trip).
- Backend derives `amount` and direction (`fromAccountId`/`toAccountId`) from the lines + taxes; the client never supplies them for a confirmation. Applies uniformly, including a single-line confirmation — there is no separate "simple trade" path.
- Per-line holding validation (existence, open), generalizing F009/F022's single-product check.
- At most one line per product may carry a `resultingBalance` (domain-validated, since a holding has one snapshot per date).
- CSV export splits `transfers.csv` (confirmation-level fields) from a new `transfer_trade_lines.csv` (per-line detail).
- Reworks `FiiPortfolioQuery`, `InvestmentValueSeriesQuery`, `InvestmentSnapshotFreshnessQuery` to read the lines table, signed by each line's `side`.
- Frontend: multi-line trade entry form; `TransfersPage` renders a chip per line; `InvestmentProductDetailPage`'s trade table becomes one row per matching line (Taxes column dropped, each row links to its parent confirmation).
- Out of scope (unchanged from F009/ADR 0012): cost basis, gain/loss, or any value derived from quantity/price; a confirmation spanning more than one INVESTMENT account; backfilling/regrouping historical single-product transfers into the multi-line notes they actually came from.

## Decisions
See ADR 0024 for the full rationale. Implementation-level decisions not already in the ADR:
- **Rounding**: sum each line's `quantity × unitPrice` at full precision, net BUY against SELL, subtract `taxes` once, round only that final net to `numeric(19,2)` (HALF_UP). Verify against the codebase's existing money-rounding convention before implementing (none was found in BigDecimal arithmetic elsewhere as of this writing — `RoundingMode.HALF_UP` is the project default for `@Digits`-bounded fields).
- **Net-zero rejection**: `TradeConfirmation.netCost(taxes)` computing to exactly zero is a domain invariant violation (`IllegalArgumentException`, same family as `Transfer`'s other constructor checks), not a 409/404 — it's a structurally nonsensical confirmation, not a conflict with other persisted state. Caught at the application layer and translated to the new `InvalidTradeConfirmationException` (`400`) — a bare `IllegalArgumentException` would otherwise reach `GlobalExceptionHandler`'s generic-`Exception` catch-all as a `500`, since that handler only rethrows `@ResponseStatus`/`ErrorResponse` exceptions.
- **`closeHolding` on a BUY line**: rejected the same way, but caught one layer up: `TradeConfirmationLineRequest` replicates the DTO-level check (`@AssertTrue`) so a validated request can never reach the domain constructor with this combination — ordinary Bean Validation `400`, same mechanism as the DTO's other per-field constraints. The domain record's own check stays as defense in depth (ADR 0004).
- **API shape**: `CreateTransferRequest`/`UpdateTransferRequest` gain `cashAccountId`, `investmentAccountId` (both nullable) and `tradeConfirmation: {taxes, lines: [{productId, side, quantity, unitPrice, resultingBalance, closeHolding}]}` (nullable). Exactly one of `{fromAccountId, toAccountId, amount}` (all required together) or `{cashAccountId, investmentAccountId, tradeConfirmation}` (all required together) must be present — enforced at the application layer by the new `TransferService.requireExactlyOneRequestShape` (static, state-independent), `400` via the new `InvalidTradeConfirmationException` (not `InvestmentTransferInvalidException`, which stays `409` for the pre-existing state-dependent checks — an investment account that isn't actually `INVESTMENT`, two investment accounts on one confirmation). `TransferResponse` gains `tradeConfirmation` (lines carry `productId`/`side`/`quantity`/`unitPrice`/`resultingBalance`/`closeHolding`; product names are resolved client-side from the already-loaded products list, same as the holding picker does today) and a top-level `taxes` (nullable, alongside `tradeConfirmation` rather than nested in it).
- **New line-level read endpoint**: `GET /api/trade-confirmation-lines?productId=` returns `{transferId, date, side, quantity, unitPrice, resultingBalance}[]` — one row per line matching the product, each carrying its parent `transferId` so the frontend can link back to the full confirmation. Replaces `InvestmentProductDetailPage`'s use of `GET /api/transfers?investmentProductId=` for its trade table (that filter itself still exists for other callers, now matching against the lines table instead of the retired flat column).

## Backend

### Domain
- `domain/transfer/TradeSide.java`: enum `BUY`, `SELL`.
- `domain/transfer/TradeConfirmationLine.java`: record `(UUID productId, TradeSide side, BigDecimal quantity, BigDecimal unitPrice, BigDecimal resultingBalance, boolean closeHolding)`. Invariants: `quantity > 0`, `unitPrice > 0` (both mandatory, unlike the old all-optional `InvestmentTradeDetails` — a line with no quantity/price doesn't make sense once lines are explicit); `resultingBalance`, when present, `>= 0`; `closeHolding` requires `side == SELL`.
- `domain/transfer/TradeConfirmation.java`: value object wrapping an immutable `List<TradeConfirmationLine>`. Invariant: at least one line. At most one line per distinct `productId` may have a non-null `resultingBalance`. `netCost(BigDecimal taxes)`: `Σ(BUY line totals) − Σ(SELL line totals) + taxes` at full precision, rounded once (HALF_UP, scale 2) — positive means net cost (cash → investment), negative means net proceeds (investment → cash); zero is rejected.
- `domain/transfer/Transfer.java`: drop `investmentProductId`/`tradeDetails`; add nullable `tradeConfirmation`. New factory `Transfer.createTradeConfirmation(id, date, cashAccountId, investmentAccountId, description, additionalNotes, taxes, TradeConfirmation confirmation)` computes `netCost`, picks `fromAccountId`/`toAccountId` by its sign, and delegates to the existing private constructor with the computed `amount`. A parallel `editTradeConfirmation(...)` overload recomputes on edit, same full-replace semantics as today. The plain `create`/`edit` overloads (manual `fromAccountId`/`toAccountId`/`amount`) are unchanged and used whenever `tradeConfirmation` is absent. `getTradeConfirmation()` returns `Optional<TradeConfirmation>`.

### Application
- `TransferService`: the F009/F022 investment validation ("an INVESTMENT-side account requires an open holding for the product") generalizes to per-line — every line's `(productId, the confirmation's investmentAccountId)` must resolve to an existing, open `InvestmentHolding` (`404`/`409` as today, now potentially reported per line). `resultingBalance`/`closeHolding` writes become per-line: for each line with a non-null `resultingBalance`, write/replace that holding's same-day `InvestmentSnapshot`; for each line with `closeHolding = true`, close that holding — both still inside the same `@Transactional` use case as the `Transfer` write (backend CLAUDE.md "Transactions").
- `LatestInvestmentSnapshotQuery`, `AccountBalanceQuery`, allocation and close-guard logic are untouched — they already key off `InvestmentHolding`/`InvestmentSnapshot`, not `Transfer`'s trade fields.
- `FiiPortfolioQuery` / `InvestmentValueSeriesQuery`: replace `TransferRepository.findByInvestmentProductId` with a new `TransferTradeLineRepository.findByProductId` (or equivalent query against the lines table); quantity is signed by `line.side` (BUY adds, SELL subtracts) instead of being inferred from the transfer's `fromAccountId`/`toAccountId`.
- `InvestmentSnapshotFreshnessQuery.resolveHoldingId`: reads the matching line's `productId` instead of `transfer.getInvestmentProductId()`.
- `HasInvestmentHistoryChecker`/`HasHoldingHistoryChecker` (F022): "any transfer has `investment_product_id` = the product" becomes "any trade confirmation line has `product_id` = the product".
- `DataExportService.writeTransfers`: drops the four flat trade columns from `transfers.csv`; new `writeTransferTradeLines` writes `transfer_trade_lines.csv` (`transfer_id`, `product_id`, `product_name`, `side`, `quantity`, `unit_price`, `resulting_balance`).

### Persistence
- New migration (next free `V` number): `transfer_trade_lines` (`id uuid pk`, `transfer_id uuid not null references transfers on delete cascade` (indexed), `product_id uuid not null references investment_products` (indexed), `side varchar(4) not null check (side in ('BUY','SELL'))`, `quantity numeric(19,8) not null check (quantity > 0)`, `unit_price numeric(19,8) not null check (unit_price > 0)`, `resulting_balance numeric(19,2) check (resulting_balance >= 0)`, `close_holding boolean not null default false`, audit columns).
- Mechanical backfill: one `transfer_trade_lines` row per existing `transfers` row that has a non-null `investment_product_id`, copying `investment_product_id → product_id`, `quantity`, `unit_price`; `side` derived from the existing direction rule (destination `INVESTMENT` account = `BUY`, source = `SELL`, same derivation `TransferService` already performs at request time, now computed once in the migration's `UPDATE ... FROM`); `resulting_balance`/`close_holding` left null/false (no way to recover which historical trade, if any, carried a resulting balance — it wasn't tied to the line, it was a separate same-day snapshot write that already exists independently in `investment_snapshots`).
- Drop `transfers.investment_product_id`, `transfers.quantity`, `transfers.unit_price` and their `CHECK` constraints (`chk_transfers_quantity_positive`, `chk_transfers_unit_price_positive`, `chk_transfers_quantity_with_unit_price`, `chk_transfers_trade_details_need_product`); `transfers.taxes` and its `CHECK (taxes >= 0)` stay.
- Migration test (backend CLAUDE.md pattern): a pre-existing single-product trade ends up with exactly one `transfer_trade_lines` row with the correct `side`, quantity and unit price; a pre-existing plain transfer (no product) gets zero line rows.
- **Found after the above shipped** (`V22__backfill_trade_confirmation_taxes.sql`): a pre-existing trade recorded with a product tag but no tax figure at all (legal under the old all-optional `InvestmentTradeDetails`) got a line from the backfill above, but `transfers.taxes` stayed `null` — violating `Transfer`'s "a confirmation requires taxes" invariant and throwing a `NullPointerException` the moment that row is loaded (`Transfer.reconstitute`). `V22` backfills `taxes = 0` for any transfer that has a line and `taxes IS NULL`.

### API
- `POST`/`PUT /api/transfers`: request DTOs gain `cashAccountId`, `investmentAccountId`, `tradeConfirmation` (see Decisions above for the mutual-exclusivity rule with `fromAccountId`/`toAccountId`/`amount`). `TransferResponse` gains `tradeConfirmation`.
- `GET /api/transfers?investmentProductId=` now matches against `transfer_trade_lines.product_id` (join), returning the owning confirmations — kept for callers that want whole-confirmation context.
- New `GET /api/trade-confirmation-lines?productId=` (line-granularity, see Decisions). `404` for an unknown product.
- Regenerate `frontend/src/api/generated/schema.ts`.

## Frontend
- `TransferForm.tsx`: an explicit Plain/Trade confirmation toggle (since a confirmation's cash/investment accounts are no longer the same two fields a plain transfer's from/to are, picking a mode can't be inferred from an account's type the way the old form derived buy/sell). Trade mode is a dynamic multi-line form — pick the cash account and the INVESTMENT account, then add/remove lines (product select scoped to that INVESTMENT account's holdings, side, quantity, unit price, optional resulting balance, optional "close this holding" checkbox shown only for SELL), a single taxes field, and a computed/suggested net settlement preview (amount + derived direction) the backend will enforce on submit. `n = 1` is the default/trivial case, not a separate mode.
- `tradeMath.ts`: reworked to compute per-line totals and the overall net preview (mirroring the backend's `netCost`), rather than a single scalar triple.
- `TransfersPage.tsx`: `tradeLabel` renders a chip per line ("Buy PETR4 · Sell HGLG11"), collapsing to "+N more" past a handful.
- `InvestmentProductDetailPage.tsx`: trade table/card switches from `GET /api/transfers?investmentProductId=` to `GET /api/trade-confirmation-lines?productId=` — one row per matching line, Taxes column removed, each row links to `/transfers?focus={transferId}` so the full confirmation (other lines, real total taxes) stays reachable. `TransfersPage` reads that `focus` param (a new `useTransfer(id)` query hook fetching the transfer directly), opens its edit dialog once loaded regardless of the list's current page/filters, and clears the param afterward; an unknown/deleted id surfaces a friendly error instead of a dialog.
- `src/api/transfers/transfers.ts` (hand-written type) and `src/mocks/handlers/transfers.ts`: `Transfer` interface and MSW fixtures updated to the `tradeConfirmation`/lines shape; every test listed in the F027 plan's blast-radius note updated accordingly.
- New `src/api/investments/tradeConfirmationLines.ts` + MSW handler for the line-granularity endpoint.
