# F035 — Category Onboarding

## Summary
Stops migration-seeding Category's eight regular starter rows (Groceries, Rent, Utilities, Subscriptions, Transport, Dining, Health, Salary) and replaces them with a second onboarding step: a localized list of suggested categories the user can accept, reject or supplement with their own, inserted as ordinary categories through the existing create API. The four structurally-flagged categories (Other Expense, Other Income, Fuel, Dividends) keep their existing eager migrations, untouched. F011's single-screen onboarding becomes a two-step `Stepper`. Decision record: [ADR 0028](../../adr/0028-fixed-taxonomy-values-and-onboarding-seeded-categories.md).

## Scope
- Edit `V2__categories_and_payment_methods.sql` directly to drop its eight regular category `INSERT`s, keeping only the two rows `V14` depends on adopting ("Other" `EXPENSE`, "Other Income" `INCOME`). Acceptable since no tagged release exists yet (`CHANGELOG.md` has no `## [X.Y.Z]` section, version `0.1.0`) — see ADR 0028's consequence that a local dev database needs `docker compose down -v` after this ships.
- New onboarding step 2, reached after F011's existing account-creation step 1, inside a `MUI Stepper` (explicit user request): a checkbox list of 11 suggestions, all pre-checked —
  - `EXPENSE`: Groceries, Rent, Utilities, Subscriptions, Transport, Dining, Health, Entertainment, Education, Insurance
  - `INCOME`: Salary
  — plus a free-text "add your own" control (repeatable, category name + type). Unchecking any suggestion excludes it; Finish is always enabled (zero selections is a valid, fully-skippable outcome). A note tells the user categories can be added, renamed or removed anytime later from Settings.
- Suggestions are presented, and if accepted inserted, in whatever UI language is active at onboarding time (§6.14) — the literal name sent to `POST /api/categories` is the translated string shown on screen, not a fixed English string. They are **not** specially flagged or tracked after insertion — indistinguishable from a category the user types in on day 50.
- Translation reuse: extend `frontend/src/i18n/seedNames.ts`'s `CATEGORY_SEED_NAMES` map with **both** the English and Portuguese literal of each of the 11 suggestions (the three new ones — Entertainment, Education, Insurance — need brand-new entries in both languages; the other eight already have an English-literal entry from today's migration seed and need their Portuguese literal added as a second key mapping to the same translation key, since onboarding can now insert either spelling depending on locale). This is the existing F033/ADR 0027 exact-string-match mechanism, unchanged in shape — just fed more literal strings.
- Trigger stays exactly as derived as F011's today: purely "zero accounts exist." Step 2 is only ever reached as part of that same first-run flow; it never resurfaces later even if the user deletes every category afterward. No new persisted flag anywhere. **This does require one change to `App.tsx` itself** (not anticipated when this bullet was first written — see the Frontend section's `App.tsx` bullet): the account-creation mutation alone already flips `hasAccounts` to `true` (every mutation invalidates every query), which happens well before step 2 finishes, so `App.tsx`'s gate needs its own latch to keep rendering `OnboardingPage` through step 2 instead of swapping to the dashboard the instant step 1 succeeds.
- Out of scope: any change to how Category itself is protected or guarded (F002/F034 territory, untouched here); persisting a "categories onboarding done" flag; editing/removing the four protected categories from onboarding (they're not offered as suggestions — they already exist by the time onboarding runs).

## Decisions
See [ADR 0028](../../adr/0028-fixed-taxonomy-values-and-onboarding-seeded-categories.md) for why Category stops being migration-seeded at all beyond its four protected rows. Feature-specific decisions:
- **`MUI Stepper`, not ad hoc step state** — user-requested; F011's `OnboardingPage` gains `activeStep` and a `Stepper` shell around what were previously two unrelated ideas (one existing screen, one new one).
- **Always skippable** — Finish never requires a minimum selection; onboarding's job is to get the user into the app, not to force a category taxonomy decision up front.
- **11 suggestions, not the original 8** — Entertainment, Education and Insurance were common personal-finance gaps in F002's original list; added here since the list is being redesigned anyway.
- **Literal name = whatever's on screen, in whatever language** — no translation-key storage on the backend (consistent with ADR 0011/0026/0027: the backend never carries translatable text); the existing exact-string-match mechanism already handles this once `seedNames.ts` knows both literals.
- **Edit `V2` directly rather than add a compensating migration** — simplest option given no tagged release exists; see ADR 0028's consequences for the local-dev-reset cost this accepts.

## Backend
- `backend/src/main/resources/db/migration/V2__categories_and_payment_methods.sql`: remove the `INSERT`s for Groceries, Rent, Utilities, Subscriptions, Transport, Dining, Health (`EXPENSE`) and Salary (`INCOME`). Keep the `Other` (`EXPENSE`) and `Other Income` (`INCOME`) inserts exactly as today — `V14` still needs to find and flag them. Payment method seeds (F034, untouched) stay in the same file.
- No application/domain change — `POST /api/categories` already exists and is unchanged (F002); the onboarding step is purely a new frontend consumer of it.
- Migration test (backend `CLAUDE.md` pattern): Flyway by hand into a throwaway schema, migrate to the edited `V2`, assert the fresh `categories` table has exactly `Other` (`EXPENSE`) and `Other Income` (`INCOME`) — none of the eight removed rows — then continue migrating through `V14`/`V18`/`V20` and assert the final protected set is still exactly the same four rows (Other Expense, Other Income, Fuel, Dividends) as before this change, confirming the later migrations' adopt-or-insert logic is unaffected by starting from a smaller `V2` seed.

## Frontend
- **`frontend/src/App.tsx`**: the top-level `hasAccounts ? shell : <OnboardingPage />` gate gains a latch (`inOnboarding`, adjusted during render — not a `useEffect`, so it takes effect on the very render that observes `hasAccounts` turn `false`, not one tick later) that, once set, keeps rendering `OnboardingPage` even after `hasAccounts` flips back to `true` mid-flow. Without this, creating the account in step 1 invalidates every query (frontend `CLAUDE.md`'s "mutations invalidate everything" rule), `hasAccounts` resolves `true` on the next accounts refetch, and the gate would swap onboarding for the dashboard before `OnboardingPage`'s own `activeStep` ever renders step 2 — silently skipping the category-suggestions step every time. The latch only releases via `OnboardingPage`'s own `onCompleted` callback (step 2 actually finishing), never merely because `hasAccounts` changed. A page reload mid-flow still resets the latch and re-derives from `hasAccounts` alone (landing straight on the dashboard, skipping step 2) — an accepted edge case, not a regression, since no new persisted flag is in scope here.
- `frontend/src/features/onboarding/OnboardingPage.tsx`: restructure around a MUI `Stepper` with two steps — "Account" (existing `AccountCreateForm`, unchanged) and "Categories" (new). Add `activeStep` state; advancing from step 1 happens on successful account creation (as today), advancing from step 2 happens on Finish (always enabled) and transitions into the normal app shell exactly as F011 already does after account creation.
- New `frontend/src/features/onboarding/CategorySuggestionsStep.tsx`: renders the 11 suggestions grouped expense-then-income (mirroring `CategoriesPage`'s existing grouping convention), each a checkbox pre-checked, labels from `t()` in the `onboarding` namespace; an "add your own" repeatable row (name text field + type select); a Finish button. On Finish, `POST /api/categories` for every checked suggestion and every custom entry (sequential or `Promise.all`), surfacing any failure with the same banner+retry pattern `AccountCreateForm` already uses, then calls the same `onCompleted` callback `OnboardingPage` already uses to leave onboarding.
- New `frontend/src/features/onboarding/suggestedCategories.ts`: the 11-entry list as `{ translationKey, type }`, consumed by `CategorySuggestionsStep` via `t(translationKey)` for both the checkbox label and the literal name sent to the API.
- `frontend/src/i18n/seedNames.ts`: add the English and Portuguese literal of each of the 11 suggestions to `CATEGORY_SEED_NAMES` (new translation keys for Entertainment/Education/Insurance in both `en` and `pt-BR` namespace files; the other eight reuse their existing translation key, just gain a second lookup entry for their Portuguese literal).
- New translation strings: step 2's heading/intro copy, the "you can change this later" note, the add-your-own control's labels — `en`/`pt-BR`, `onboarding` namespace.
- Tests: update `OnboardingPage.test.tsx` for the two-step flow (step 1 unchanged behavior, advancing to step 2, Finish with a mix of checked/unchecked/custom entries, Finish with zero selections); new `CategorySuggestionsStep.test.tsx`; `localeParity.test.ts` picks up the new keys automatically.

## Dependencies
F011 (onboarding, extended by this feature), F002 (Category — unaffected API, just a new caller), F033 (the `seedNames.ts`/`translateSeedName` mechanism this reuses).
