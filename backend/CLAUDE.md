# Backend (Spring Boot / Gradle)

Backend-specific rules. Cross-stack conventions (bounded free text, `numeric(19,2)` money, error-message contract, OpenAPI) are in the root `CLAUDE.md`.

## Commands (run from `backend/`)

```
./gradlew bootRun         # run the API against local Postgres (http://localhost:8080; `docker compose up -d` first)
./gradlew build           # compile + both test tiers + package
./gradlew test            # fast tier: domain, application (fakes) and ArchUnit tests — no Docker needed
./gradlew integrationTest # every @SpringBootTest test — needs Docker running (Testcontainers starts its own ephemeral Postgres, ADR 0010)
./gradlew spotlessCheck   # google-java-format check; `spotlessApply` to fix (don't hand-format — it rewraps javadoc)
```
Swagger UI: `http://localhost:8080/swagger-ui.html`. OpenAPI spec: `http://localhost:8080/v3/api-docs`.

## Layout and shapes

- Layer-then-context packages: `com.chm.myfinances.{domain,application,infrastructure}`, one subpackage per aggregate (ADR 0004). `domain/shared` holds the `IdGenerator` port (ADR 0005 — ids never come from `@GeneratedValue` or ad hoc `UUID.randomUUID()`) and `TextFieldConstraints`. `infrastructure/persistence` holds the `AuditableEntity` base every table-backed entity extends.
- **Domain packages never import another aggregate's package**, enforced by `ArchitectureTest`, with one documented exception: `domain.transaction.Transaction` depends on `domain.category.CategoryType`, a denormalized field captured at creation (see `Transaction`'s own javadoc). Cross-aggregate checks (category exists and is `EXPENSE`, account is open, ...) happen in the application service via the other aggregate's repository port. Domain constructors re-check their own invariants anyway as defense in depth.
- **Use-case service**: one `@Service` per aggregate, constructor-injected with its repository port(s) and, when it creates entities, `IdGenerator`. Plain use-case method names (`create`/`rename`/`delete`/`findAll`, not generic CRUD verbs). `findById(...).orElseThrow(...)` throws `{Aggregate}NotFoundException` (`@ResponseStatus(NOT_FOUND)`) in the same package.
- **Repository adapter** (`infrastructure/persistence/<aggregate>`): package-private Spring Data `JpaRepository`, a `@Component` adapter implementing the domain port and translating via `reconstitute(...)`, and a JPA entity extending `AuditableEntity` with Lombok `@Getter`/`@Setter`/`@NoArgsConstructor` (Lombok is fine here; ADR 0005 only forbids it on domain classes).
- **Query object** for a computed-not-stored value that other features' tables feed into (`AccountBalanceQuery`, `BudgetCapQuery`, `BudgetReportQuery`, `RecurringTemplateCurrentVersionQuery`): an application-layer class beside the service, read-only. When the computation reads only the one aggregate instance passed in and needs no repository at all (`FuelRatiosQuery`, F024: km/L, spend/km, L/km from one `Transaction`'s own fields), it's a plain static utility instead of a `@Service` bean — a response DTO's static `from(...)` factory calls it directly, the same shape every other response DTO already uses, rather than threading a service through the controller just to hand it to the DTO.
- **Domain port for a cross-feature side effect**: an aggregate announces something through a port it owns (`domain/account/AccountClosedNotifier`) and the reacting feature implements it (`infrastructure/recurringtemplate/RealAccountClosedNotifier`), so the announcer never depends on the reactor.
- **Read-only port with no domain aggregate behind it at all** (`application/backupstatus/BackupStatusPort`, F018): when there's no table and no entity — the F018 sidecar's `status.json` marker is owned and written by a separate shell-script codebase, read through a mounted file — there's no `domain/` package either, just the port (`application/`) and its one adapter (`infrastructure/backupstatus/FileBackupStatusAdapter`, reading `myfinances.backup.status-path`/`BACKUP_STATUS_PATH`, default `/backups/status.json`). A missing/unreadable/malformed file is `Optional.empty()`, never an exception. The adapter builds its own `ObjectMapper` (with `JavaTimeModule`) rather than `@Autowired` — this app has no general-purpose `ObjectMapper` bean, the same reason REST-layer tests build one by hand (see Testing below).
- **`Account.getOpeningBalance()`/`getOpeningBalanceDate()` are `null` for an `INVESTMENT` account** (ADR 0012, backed by a DB `CHECK`), so any code that reads them must branch on `getType()` first (`AccountBalanceQuery` does: its `INVESTMENT` branch sums the latest snapshots of the `InvestmentHolding`s pointing at that account, `LatestInvestmentSnapshotQuery`, F022/ADR 0020). `TransactionService`/`RecurringTemplateService` reject such an account with their own package's `AccountTypeNotAllowedException`.
- **`NetWorthQuery` counts an account only between its `openingBalanceDate` and its `closedDate` (exclusive)**, per date — never "every non-closed account", which would drop a closed account from every past month. An `INVESTMENT` account has no opening date, so it always counts and is `0` until its first snapshot. Sums are as-of, computed on read from `AccountBalanceQuery`; nothing is stored. `trend()` computes every non-investment account's balance across the sampled dates in one forward pass (ledger events loaded once, sorted, walked with a per-account cursor) rather than calling `AccountBalanceQuery.balanceAsOf` per date — that re-reads an account's whole history from scratch every time and was O(dates × accounts × transactions) (issue #94). An `INVESTMENT` account still goes through `balanceAsOf` per date since its snapshot history is small by construction; don't "fix" it the same way without a reason, it isn't the bottleneck.
- **Never pass `LocalDate.MAX`/`MIN` to a repository query**: Postgres can't represent it and the request fails with a 500. "The latest snapshot regardless of date" is `LatestInvestmentSnapshotQuery.latestOf(holdingId)` / `latestByHolding()` (in-memory reduce over `findByHoldingId`/`findAll`), not `findAllOnOrBefore(LocalDate.MAX)`.
- **Reports (F030, superseding F013's data export)**: each `ReportGenerator` reads through the existing ports/queries only (no report-specific persistence), and `TransactionRepository.findAll(filter, Pageable.unpaged())`-style calls still need any `Fake*Repository` to handle `isUnpaged()`. `CsvWriter` (`application/report`) guards against spreadsheet formulas only for `String` cells (prefix `'`), so pass amounts, dates and ids as their own types, never pre-formatted strings, or a negative amount would be turned into text. `CsvSectionWriter.Section.rows()` is `List<Object>` for exactly that reason: build a row with `Arrays.asList(...)`, never `List.of(...)`, whenever any cell can be `null` (an optional amount, a snapshot date that may not exist yet) — `List.of()` throws `NullPointerException` on a `null` element, which `Arrays.asList()` permits.
- **Update endpoints** are `PATCH` with a full-replace body (every editable field required).
- **List endpoints**: `PagedModel` (`{content, page: {size, number, totalElements, totalPages}}`, Spring Data `Pageable` underneath) for tables that grow without bound (transactions, transfers); a plain list where the row count is inherently small (budgets, templates, pending occurrences). A filtered `PagedModel` list doesn't have to be a JPA `Specification`: when a filter dimension isn't a column on the entity itself (F023's investment product list filters by `accountId`/`status`, both read through `InvestmentHoldingRepository`, not the product table), filter/sort/paginate in memory over the existing repositories instead, the same "computed on read" style as a query object (`InvestmentProductService.findAll(filter, pageable)`, mirroring `FakeTransactionRepository`'s in-memory `Page` build) — a local, single-user app never has enough rows for this to matter.
- **Versioned history** (`Budget`+`BudgetVersion`, `RecurringTemplate`+`RecurringTemplateVersion`, `AllocationPlan`+`AllocationPlanVersion`): edits create a new forward-only version; the effective one for month X is the latest `effectiveFrom <= X` (`resolveEffective`, pure domain logic). Editing a month that already has a version replaces it in place instead of duplicating — the service decides which, the version class only performs the replace.
- **Replacing a value-object child table wholesale (delete-then-insert) must delete via a bulk `@Modifying @Query`, never a derived `deleteBy...` method** (F026: `AllocationPlanEntryJpaRepository.deleteByVersionId`, replacing a version's `AllocationPlanEntry` rows on every `save`). A derived delete loads matching rows then schedules per-entity removal for the next flush; Hibernate flushes pending inserts before pending deletes, so inserting the fresh rows right after hits the still-present old ones' `UNIQUE` constraint. A bulk query executes immediately, so the delete is visible before the inserts run.
- **Recurring generation is lazy/catch-up** (the app isn't always running): `RecurringOccurrenceGenerator` is a pure function; `RecurringOccurrenceCatchUpService` is the only place it touches persistence, run at startup and before the pending list is served. A pending occurrence stores only a version id and its amount is resolved live, so creating a new version must realign existing pending occurrences (`setCap` does). `runCatchUp` is deliberately *not* `@Transactional` — one transaction would let a broken template roll back the others — and it is safe to run concurrently (startup runner vs a page load, two tabs, React `StrictMode`'s double fetch in dev): a cycle is generated with `PendingRecurringOccurrenceRepository.insertIfAbsent` (`INSERT ... ON CONFLICT DO NOTHING`, backed by `UNIQUE (template_id, due_date)`, V11). Never go back to `existsByTemplateIdAndDueDate` + `save`: two callers both see "absent" and both insert (issue #20). A native insert bypasses JPA auditing, so it sets the audit timestamps itself.

## Errors

- One cross-cutting `@RestControllerAdvice` exists, `infrastructure/web/GlobalExceptionHandler`, and there should never be another: a single `@ExceptionHandler(Exception.class)` that builds and returns an RFC 9457 `ProblemDetail` body (`type`/`title`/`status`/`instance`, F031/ADR 0026) for **every** branch — it no longer rethrows anything to Spring's default resolver chain. Status is resolved the same way the old rethrow condition picked branches: a merged `@ResponseStatus` value, else `ErrorResponse.getStatusCode()` (Spring's own MVC exceptions, e.g. `NoResourceFoundException`), else a hardcoded 400 for the two client-error exceptions that implement neither — `HttpMessageNotReadableException` (bad JSON body) and `TypeMismatchException` (bad UUID/date in path or query, issue #19) — else 500 for anything truly unexpected. Any other exception type Spring maps to 4xx without `ErrorResponse` needs adding to that status-resolution chain, not a second handler. Backed by `spring.web.error.include-{stacktrace,message,binding-errors}: never` (Boot 4.x spelling; not `server.error.*`).
- **`type`/`title` are derived, not authored**: `infrastructure/web/ProblemTypeSlugs.slugFor(exceptionClass)` takes the exception's simple class name, strips a trailing `Exception`, kebab-cases it (a hyphen before each internal uppercase letter, lowercased) — `AccountHasHistoryException` -> `account-has-history` — and `typeUriFor`/`titleFor` wrap that into `urn:my-finances:error:<slug>` / a humanized title. No exception opts in or declares anything; adding a new `@ResponseStatus` exception is the only step, same as before this feature. **Classes duplicated across aggregate packages only for the no-cross-aggregate-import ArchUnit rule** (ADR 0014) — `AccountClosedException` in `application.transfer`/`application.transaction`/`application.recurringtemplate`, `AccountTypeNotAllowedException` in `application.transaction`/`application.recurringtemplate` — deliberately collapse to the identical slug: the duplication is a code-organization artifact, not a different real-world condition, and the frontend only needs one message per condition. **The generic unexpected-exception (500) case uses the fixed `ProblemTypeSlugs.INTERNAL_ERROR_TYPE`/`INTERNAL_ERROR_TITLE` constants** (`urn:my-finances:error:internal-error` / "An unexpected error occurred"), never derived from the actual exception class — that set is unbounded and includes third-party exception types never vetted for safety. `detail` is always left `null` on every branch; that is the field ADR 0011 forbids populating with exception text or entity data, and this feature does not loosen that rule.
- A new *expected* error case gets its own `@ResponseStatus`-annotated exception — never a new `@ExceptionHandler`. Status choice: **409** when validity depends on another aggregate's persisted state (closed account, non-`EXPENSE` category budgeted, category still referenced, duplicate name); **400** when the request is malformed regardless of state (`SameAccountTransferException`); **404** for unknown ids. Document the operation's possible `type` values with `@ApiResponse`/`@Content(schema = @Schema(implementation = ProblemDetail.class))` on the controller method (springdoc 2.8.5 generates the `ProblemDetail` schema itself - no wrapper class needed), one `@ApiResponse` per status code, description text listing every `type` that status can carry for that operation. **If an operation has no success-status annotation of its own** (no `@ResponseStatus(CREATED)` etc., just the method's plain return type), adding only error `@ApiResponse`s makes springdoc 2.8.5 drop that operation's implicit 200 schema from `/v3/api-docs` entirely - add an explicit `200` `@ApiResponse` alongside the error ones (`InvestmentSnapshotController.list`, `InvestmentValueSeriesController.valueSeries`) or a response type used only by that operation silently vanishes from generated `schema.ts`.
- Names are unique (`UNIQUE` on `categories`/`payment_methods`/`accounts`/`institutions`/`investment_categories`/`investment_products` `name`, exact match, case-sensitive) via an application-layer `existsByName`/`existsByNameAndIdNot` check that throws `{Aggregate}NameAlreadyExistsException`. Investment sub-categories are unique per parent category (`existsByInvestmentCategoryIdAndName...`), never globally; investment products moved from per-account to globally unique in F022/ADR 0020 (the same instrument at two brokers is now one product with two `InvestmentHolding`s, not two products sharing a name). `CategoryService.delete()` rejects a category still referenced by a transaction, budget or recurring template (`CategoryInUseException`).
- `AccountService.delete()` hard-deletes only an account nothing references (409 `AccountHasHistoryException` otherwise, ADR 0017), via the `AccountUsageChecker` port (`infrastructure/account/RealAccountUsageChecker`: transactions, transfers on either side, templates incl. inactive, investment holdings incl. closed — moved from `investment_products` to `investment_holdings` by F022/ADR 0020, since the product itself no longer has an `account_id`). **A new table with an FK to `accounts` must be added to that checker** (and `RealAccountUsageCheckerTest`), or deleting an account it references surfaces as a 500 from the FK instead of the 409.
- **A find-then-insert race on a `UNIQUE` constraint is still a new *expected* error case, not a reason for a second `@ExceptionHandler`.** `InvestmentSnapshotService.record()` checks `(holdingId, date)` then inserts; two concurrent callers can both see "absent" (issue #94, same shape as issue #20's recurring-occurrence race). Catch `DataIntegrityViolationException` at the call site and throw the existing `@ResponseStatus(CONFLICT)` exception for that case (`InvestmentSnapshotDateTakenException`) instead of letting it fall through to `GlobalExceptionHandler`'s generic 500.
- **Splitting one method that enforced a cross-cutting invariant unconditionally into several entry points drops that invariant from whichever entry point doesn't obviously need it, unless it's explicitly re-applied to each one** — a design doc's "unchanged" claim about the other path isn't a substitute for rereading the old method's full body line by line. F009/F022's single `TransferService.create`/`edit` ran one `requireValidInvestmentShape` on every call, rejecting a plain (no-product) transfer that touched an `INVESTMENT` account. F027 split that into `create`/`edit` (plain) vs `createTradeConfirmation`/`editTradeConfirmation`, and the equivalent guard (`requireInvestmentShape`) was written only for the new confirmation path — the plain path silently lost it, and no test caught the regression for the rest of that feature's lifetime (issue #113). The fix (`requirePlainShape`) re-derives that one rule from the pre-split method rather than from the split's own stated intent.

## Transactions

Single repository calls are self-transactional. **Any use case that performs more than one write must be `@Transactional` and opt in explicitly** — the app has no other transaction-boundary handling. A failure between two writes otherwise leaves a half-created aggregate (a template with no version) or a duplicate (a confirmed occurrence that wasn't deleted). A buy/sell with a `resultingBalance` is such a use case: `TransferService.createTradeConfirmation` is `@Transactional` (transfer + per-line snapshot/holding-close effects, `TransferServiceTransactionalTest`). It is its own top-level method, not an overload the plain `create` delegates into (F027 replaced the old 9-argument `create`/6-argument-plain-delegate pair with two independent methods - see the Errors bullet above for the invariant that split silently dropped). This includes cascades across aggregates: `AccountService.close()` is `@Transactional` because it triggers template deactivation through a port, and `stop()`'s own `@Transactional` just joins it.

**F025 (ADR 0022) made this apply far more broadly**: any write use case instrumented with `AuditRecorder` is now, by definition, at least two writes (the business change, then the audit insert) — so every such use case needs `@Transactional`, even ones that were a single write (and therefore self-transactional) before. Where several overloads of the same method name exist and a caller outside the class might hit any of them (e.g. `TransactionService.create`'s four overloads — the controller calls the 10-argument one, `RecurringTemplateService.confirmPending` calls the 8-argument one), every externally-reachable overload needs its own `@Transactional`, not just the one with the actual write logic: self-invocation between overloads bypasses the Spring proxy, so only the exact method an external caller's own (proxied) call lands on gets a transaction boundary. A cascade that needs a different `origin` depending on who triggered it (a user's own click vs. another aggregate's cascade, e.g. `RecurringTemplateService.stop`) takes an explicit `AuditOrigin` parameter on an internal overload, with the public no-origin method defaulting to `USER` — both overloads carry `@Transactional` for the same reason.

## Config

`application.yml` holds only settings identical across every environment plus `spring.profiles.default: dev`. Environment-specific values (datasource, `server.address`) live only in `application-dev.yml` / `application-prod.yml`, so nothing is silently inherited across profiles. There is no `application-test.yml`: tests get their datasource from Testcontainers via `@ServiceConnection` (ADR 0010).

## Testing

- **Spring Boot 4.x removed the test-slice annotations** (`@DataJpaTest`, `@WebMvcTest`, `@AutoConfigureMockMvc`, `@AutoConfigureTestDatabase`) and `TestRestTemplate`. Persistence and REST tests use full `@SpringBootTest` + `@Import(TestcontainersConfiguration.class)` + `@Transactional` (automatic rollback between tests). For REST tests build `MockMvc` by hand in `@BeforeEach` via `MockMvcBuilders.webAppContextSetup(webApplicationContext).build()` with a plain `WebApplicationContext` field and a locally-constructed `ObjectMapper` (there's no `ObjectMapper` bean). `TestcontainersConfiguration` is `public` so any package can import it.
- **Two test tiers, split by the JUnit tag `integration`**: `test` excludes it, `integrationTest` runs only it. `@DatabaseIntegrationTest` and `@WebIntegrationTest` carry the tag; a `@SpringBootTest` class that doesn't use one of them (transactional, concurrency, migration, context tests) must add `@Tag("integration")` itself, or `TestTaggingTest` fails.
- Application-layer logic is unit-tested against the hand-written `testsupport/Fake*Repository` fakes, no Spring context. Fakes don't enforce DB constraints, so they need the same port methods as the real repository added by hand.
- **Exception: transaction-boundary tests must NOT be `@Transactional`.** To prove a service method's `@Transactional` rolls back a multi-write use case (`*ServiceTransactionalTest`), the test must carry no class- or method-level `@Transactional`, or the service just joins the test's transaction and a same-transaction re-read still sees the un-rolled-back writes. Spy the downstream repository with `@MockitoSpyBean` on a *field* (not a method parameter), stub the *second* write to throw, then re-read through fresh repository calls. These tests commit real rows: clean up leftovers inline with a repository method you did *not* stub (`reset(spy)` first — custom derived `deleteBy...` queries need a caller-provided transaction, plain `deleteById` does not), and give fixtures with no delete port (categories/accounts/templates) unique names because they stay behind.
- **Seed rows collide with `UNIQUE` constraints in real-DB tests.** `V2` seeds categories/payment methods ("Groceries", "Rent", "Debit Card", ...) into the shared Testcontainers Postgres before any test runs, so rollback never removes them. Real-DB fixtures must not reuse those names (convention: a `" Test"` suffix) or any name a non-`@Transactional` test leaves committed. `V14` flags the seeded `Other` (renamed "Other Expense") and "Other Income" categories as built-in the same way: never reuse those names, and never assume `categories` has no built-in row (one per type). `V12` seeds the built-in institution ("No institution") the same way: never reuse that name, and never assume `institutionRepository.findAll()` is empty or a fixed size. Because `accounts.institution_id` is `NOT NULL` with an FK, **any real-DB test that creates an `Account` needs a valid `institutionId`**: use `TestInstitutions.builtInId(institutionRepository)` (`testsupport`) or save a fixture institution first; a random UUID is rejected by the FK at flush. `V13` seeds the investment taxonomy the same way (categories "Fixed Income", "Variable Income", "Funds", "Pension (Previdência)", "International", "Crypto", "Other", and sub-categories such as "CDB" or "ETFs"): fixtures must not reuse those names (`" Test"` suffix) and no test may assume `investment_categories`/`investment_subcategories` are empty. An `INVESTMENT` account is built with `Account.create(id, name, institutionId, AccountType.INVESTMENT, null, null)`; every other type still needs both opening values.
- **Testing a migration against pre-existing data** (the case a fresh migrate can't show, e.g. a dedupe before a new `UNIQUE`): run Flyway by hand into a throwaway schema of the shared container (`Flyway.configure()...schemas(...).target("N")`, insert the rows, migrate to `N+1`; `PendingOccurrenceCycleUniquenessMigrationTest`). Use a **non-pooled** `DriverManagerDataSource` built from the Hikari pool's URL/credentials — `Connection.setSchema` changes the physical connection's `search_path`, and on a pooled connection that leaks into the next test ("relation does not exist" once the schema is dropped).
- **Concurrency tests** (`RecurringOccurrenceCatchUpConcurrencyTest`): no `@Transactional` on the class, release callers together with a `CyclicBarrier`, and hard-delete the committed fixtures afterwards through `JdbcTemplate` (children first) — the domain has no delete port, and a leftover template breaks other tests that list or count templates (`findAll().hasSize(2)`), or, if active, generates pending rows in their catch-up runs.

## Logging

Rationale in ADR 0011. Boot `logging.*` properties only — no `logback-spring.xml`, no new dependency.

- **Where things are configured**: `application.yml` holds what is identical everywhere — the `[%X{requestId:-}] ` correlation pattern, the rolling caps (50MB per file, 90 days, 300MB total, gzip), and two guards against Spring logging values we never want (below). `application-dev.yml`: `com.chm.myfinances` at DEBUG, file `logs/backend.log` (`backend/logs/` under `bootRun`, gitignored). `application-prod.yml`: INFO, file `/var/log/my-finances/backend.log`, level overridable via `LOGGING_LEVEL_COM_CHM_MYFINANCES` (`LOG_LEVEL` in compose). Profile-specific values stay out of the base file. The rolling caps aren't wired to compose variables (set-and-forget, and `application.yml` stays their single source of truth); to change one, add an env var to the backend service via Boot's relaxed binding — `LOGGING_LOGBACK_ROLLINGPOLICY_MAX_FILE_SIZE`, `LOGGING_LOGBACK_ROLLINGPOLICY_MAX_HISTORY`, `LOGGING_LOGBACK_ROLLINGPOLICY_TOTAL_SIZE_CAP` — and recreate the container. `max-history` is applied first and the size cap second, so the cap can evict logs younger than `max-history`.
- **Reading prod logs**: they live in the `my-finances-logs-prod` volume (explicit `name:` in compose). Without the app: `docker run --rm -v my-finances-logs-prod:/logs alpine sh -c 'ls /logs; tail -n 200 /logs/backend.log'`; with it running: `docker compose -f docker-compose.prod.yml exec backend tail -n 200 /var/log/my-finances/backend.log` (Git Bash on Windows rewrites that path — prefix `MSYS_NO_PATHCONV=1`). Logs survive `stop`/`down`/image updates; `docker compose down -v` (which also wipes the database) or `docker volume rm` removes them, and files older than 90 days or beyond the 300MB total (whichever comes first) are deleted by design.
- **Tests never write a log file**: `build.gradle`'s `tasks.named('test')` sets the system property `logging.file.name` to `''` — tests run under the default `dev` profile, whose file name would otherwise create `backend/logs/`.
- **Request id**: `infrastructure/web/RequestLoggingFilter` (highest precedence) puts `requestId` in the MDC, echoes it as `X-Request-Id`, and writes one access line per request (method + path, never the query string or a body; `/actuator/**` at DEBUG because the prod healthcheck hits it). It accepts an inbound id only if it matches `^[A-Za-z0-9-]{1,64}$`, else takes one from `IdGenerator` — never `UUID.randomUUID()` (ADR 0005).
- **`GlobalExceptionHandler` logging is unchanged by F031's `ProblemDetail` body**: unexpected exception → ERROR with the stack trace; a `@ResponseStatus` exception → INFO with its class simple name only (the response's `type` is derived from that same name, so this isn't a new leak surface, but the log line is still the only place to see the exception's *message*, which the response never carries). Don't add exception messages to either.
- **Never log amounts, descriptions/notes, account/category/payment-method names or opening balances — ids and counts only. Never log in `domain/`** (application services use a plain `private static final Logger log = LoggerFactory.getLogger(X.class)`, not Lombok `@Slf4j`). Log only state-changing events at INFO (cascades, generated data, new versions); plain CRUD is already covered by the access line. Never log inside a loop over a table.
- **Spring's own log lines leak values unless silenced**: `DefaultHandlerExceptionResolver` always warn-logs `Resolved [...]` including a validation failure's `rejected value [-12.34]`, so `application.yml` sets its logger to ERROR; and `spring.mvc.log-resolved-exception: false` is pinned because DevTools (on the `bootRun` classpath, not in tests) turns it on, which warn-logs every `@ResponseStatus` exception's message (entity names).
- **SQL**: `spring.jpa.show-sql` stays off; for ad hoc query debugging set `LOGGING_LEVEL_ORG_HIBERNATE_SQL=DEBUG`. **Never enable `org.hibernate.orm.jdbc.bind`** (TRACE) — it prints bound parameters, i.e. amounts and descriptions.
- **Known leak, accepted**: an ERROR stack trace includes the exception message, and Postgres constraint-violation messages can echo the failing row (`Failing row contains (...)`). The file keeps those traces up to 90 days, so redact before pasting a log into a public issue.
- **Testing logs**: `testsupport/LogCapture` attaches a Logback `ListAppender` to one logger (try-with-resources) so a plain unit test can assert on level + formatted message without a Spring context. `LogCapture.of` forces the logger to TRACE; use `ofConfiguredLevel` in a `@SpringBootTest` to prove a `logging.level.*` setting really silences a third-party logger.
