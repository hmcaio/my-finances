## Project status

F001 (project scaffolding) is done: `/backend` (Spring Boot/Gradle) and `/frontend` (Vite/React/TypeScript) skeletons exist and are buildable/runnable, per `docs/features/F001-project-scaffolding/`.

F002 (categories & payment methods) is done, per `docs/features/F002-categories-payment-methods/`: the first real domain entities (`Category`, `PaymentMethod`), first real Flyway migration (`V2__categories_and_payment_methods.sql`), first real REST controllers, and first real frontend screens (`/settings/categories`, `/settings/payment-methods`) — this establishes the vertical-slice pattern F003+ follow. Its referenced-by-transaction delete guard (409 when a category/payment method is in use) was deliberately deferred — it needed F004's transaction table to check against — and now lands as part of F004 below.

F015 (frontend test tooling) is done, per `docs/features/F015-frontend-test-tooling/`: Vitest + React Testing Library + MSW are wired up (`vite.config.ts`'s `test` key, `src/test/setup.ts`, `src/mocks/`), a real `npm test`/`npm run test` command exists, and F002's frontend (API clients + `CategoriesPage`/`PaymentMethodsPage`) has its first real test coverage — this is what F014's CI `test-frontend` job now actually runs instead of skipping. F003+ each add their own `src/mocks/handlers/<aggregate>.ts` and tests against this tooling rather than re-deriving it.

F003 (account management) is done, per `docs/features/F003-account-management/`: the `Account` aggregate (`domain/account`), migration `V4__accounts.sql` (not `V3` — see that spec.md for why), `AccountService`/`AccountController`/`/api/accounts` endpoints (no `DELETE` — accounts are only ever closed), and the frontend's `/accounts` (list + closed toggle + inline edit + close confirmation) and `/accounts/:id` (detail) screens. This introduces two conventions F004+ should follow rather than reinvent: an **application-layer query object** (`AccountBalanceQuery`, alongside the usual `{Aggregate}Service`) for a computed-not-stored value that other features' tables feed into — opening-balance-only until F004 (Transaction) landed, now sums real transaction activity; F005 (Transfer) will extend it again — and a **domain port for a cross-feature side effect** (`domain/account/AccountClosedNotifier`, implemented for now by a no-op `infrastructure/account/NoOpAccountClosedNotifier` bean) so an aggregate can announce something happened without depending on the feature that will eventually react to it (F007 provides the real listener when it lands). `Account.name`/`institution` extend the `TextFieldConstraints` bounded-name-field convention below, confirming it applies to any free-text user-entered field, not only flat taxonomy entities.

F004 (transactions) is done, per `docs/features/F004-transactions/`: the `Transaction` aggregate (`domain/transaction`), migration `V5__transactions.sql` (not `V4` — F003 claimed that first, see that feature's spec.md), `TransactionService`/`TransactionController`/`/api/transactions` endpoints, `AccountBalanceQuery` (F003) now summing real transaction activity instead of just returning the opening balance, and the frontend's `/transactions` (filterable list/table + combined create/edit form + delete confirmation) screen plus an `AccountTransactionList` embed on F003's account detail page. This is the first paginated list endpoint in the app and sets the convention F006+ should follow: `GET`-with-query-params filtering, Spring Data `Pageable`/`Page` under the hood, returned as a `PagedModel` (`{content, page: {size, number, totalElements, totalPages}}`) rather than a raw `Page` (Spring's recommended envelope, avoids leaking `PageImpl`'s own serialization). `PATCH /api/transactions/{id}` is a full-replace body (every editable field required), continuing F002/F003's existing update-endpoint convention. This feature also finally lands F002's deferred referenced-by-transaction delete guard: `CategoryService`/`PaymentMethodService.delete()` now reject (409, `CategoryInUseException`/`PaymentMethodInUseException`) when the target is still referenced by a transaction, now that `transactions` exists to check against.

F005 (transfers) is done, per `docs/features/F005-transfers/`: the `Transfer` aggregate (`domain/transfer`), migration `V7__transfers.sql` (not `V5` as originally planned — F004 claimed `V5`/`V6` first; see that feature's spec.md for why), `TransferService`/`TransferController`/`/api/transfers` endpoints (following F004's paginated-list/`PagedModel`/full-replace-`PATCH` conventions, with `accountId` filtering matching either side of the transfer per PRD §6.9), `AccountBalanceQuery` (F003, extended by F004) now also folding in transfer activity — the source account's balance always decreases by the transfer amount, while the destination's effect depends on its own `AccountType` (asset balance increases, credit card owed amount decreases) — and the frontend's `/transfers` (filterable list/table + combined create/edit form + delete confirmation) screen plus an `AccountTransferList` embed on F003's account detail page, alongside F004's transaction embed. This introduces one new error-mapping wrinkle worth following: `fromAccountId != toAccountId` can't be expressed as a single-field bean-validation constraint, so it's checked in the application service and mapped to its own `@ResponseStatus`-annotated exception (`SameAccountTransferException`) like every other expected error case — but as a **400**, not a 409, since (unlike a closed-account conflict) no server state ever makes `fromAccountId == toAccountId` valid; it's a malformed request, not a conflict with existing data. The domain constructor/`edit` re-check the same invariant as defense in depth, same spirit as `Account.requireOpen()`.

F006 (budgets) is done, per `docs/features/F006-budgets/`: the `Budget`+`BudgetVersion` aggregates (`domain/budget`) — this codebase's first versioned-history cluster, previewing the shape F007's `RecurringTemplate`+`RecurringTemplateVersion` will follow — migration `V8__budgets.sql` (not `V6` as originally planned — F004 claimed `V5`/`V6` and F005 then claimed `V7`; see that feature's spec.md for why), `BudgetService`/`BudgetController`/`/api/budgets` endpoints, and the frontend's `/budgets` screen (budgeted-category list with inline cap edit + add-unbudgeted-expense-category form, plus a budget-vs-actual view with a month picker and a red over-cap indicator). Version resolution ("the cap effective for month X is whichever version has the latest `effectiveFrom <= X`") is pure domain logic (`BudgetVersion.resolveEffective`, unit-tested directly), reused by two application-layer query objects following F003's `AccountBalanceQuery` convention: `BudgetCapQuery` (a budget's current cap, used by the list endpoint) and `BudgetReportQuery` (`GET /api/budgets/report?month=YYYY-MM`, which reuses F004's existing `TransactionRepository.findAll` with an unpaged `Pageable` rather than adding a new port method, since `TransactionFilter` already has every dimension it needs). `GET /api/budgets` is a **plain list, not paginated** — a deliberate departure from F004/F005's `PagedModel` convention, since the number of budgeted categories is inherently small (there's at most one `Budget` per category). Rejecting a non-`EXPENSE` category is a 409 (`CategoryNotExpenseException`), following `AccountClosedException`'s precedent: whether the request is valid depends on another aggregate's already-persisted state, not on the payload in isolation, so it's a conflict rather than a 400. This feature also surfaced and fixed a real gap in the OpenAPI/codegen pipeline: springdoc has no built-in string mapping for `java.time.YearMonth` (only `LocalDate`/`Instant`/etc. are in swagger-core's default primitive list), so without `infrastructure/config/OpenApiConfig`'s `SpringDocUtils.getConfig().replaceWithClass(YearMonth.class, String.class)` it generated a wrong object-shaped TypeScript type for every `effectiveFrom`/`currentCapEffectiveFrom` field instead of the plain `"yyyy-MM"` string Jackson actually puts on the wire — any future aggregate introducing a new `java.time` type should check its generated schema shape the same way before trusting it.

F007 (recurring templates) is done, per `docs/features/F007-recurring-templates/spec.md`: the `RecurringTemplate`+`RecurringTemplateVersion` aggregates (`domain/recurringtemplate`) follow the versioned-history shape F006's `Budget`+`BudgetVersion` previewed — including the same same-month "replace, don't duplicate" cap-edit rule (`RecurringTemplateVersion.update`, mirrored by `RecurringTemplateService.setCap`) — plus a third, lightweight aggregate this feature introduces, `PendingRecurringOccurrence`: a short-lived record of a not-yet-confirmed cycle, deleted once confirmed (into a real `Transaction`) or dismissed. Migration `V9__recurring_templates.sql` (not `V7` as originally planned — F005 claimed `V7` and F006 claimed `V8`; see that migration's own header and F005/F006's spec.md files for the same renumbering story), which also adds the FK F004's `V5__transactions.sql` deferred on `transactions.recurring_template_version_id`. The rules-heavy core — lazy/catch-up pending-occurrence generation, since the app isn't always running (PRD S7.3) — is `domain/recurringtemplate/RecurringOccurrenceGenerator`, a pure function (no persistence, no Spring) taking a template's `active` flag/versions/`lastGeneratedFor`/"today" and returning exactly which cycles are now due, unit-tested directly per PRD S7.2's TDD emphasis (multi-month downtime catch-up, day-of-month clamping to a shorter month, mid-catch-up version changes, current-month-not-yet-due handling); `application/recurringtemplate/RecurringOccurrenceCatchUpService` is the only place that result touches persistence, run both at startup (`infrastructure/recurringtemplate/RecurringOccurrenceCatchUpRunner`, a Spring `ApplicationRunner`) and lazily before `RecurringTemplateService.findAllPending()` serves the pending list. Confirming a pending occurrence reuses F004's `TransactionService` via a new `recurringTemplateVersionId`-aware `create(...)` overload rather than duplicating its category/account/payment-method validation; overriding amount/date/account at confirmation time never creates a new version, only a one-off variance on the resulting transaction. One real spec gap surfaced and had to be resolved by decision: `RecurringTemplate` has no payment-method field (per spec.md's own field list), but `Transaction.paymentMethodId` is mandatory (F004) — so `ConfirmOccurrenceOverrides.paymentMethodId`/`ConfirmPendingOccurrenceRequest.paymentMethodId` are a required input at confirmation time, not an optional override, since there's no template-level default to fall back to. This feature also supersedes F003's placeholder `NoOpAccountClosedNotifier` with `infrastructure/recurringtemplate/RealAccountClosedNotifier`, the first real consumer of F003's `AccountClosedNotifier` port: closing an account now actually deactivates every `RecurringTemplate` still pointed at it (PRD S5.4), verified end-to-end against a real Spring context. `GET /api/recurring-templates`/`GET /api/recurring-templates/pending` are both **plain lists, not paginated**, following F006's `GET /api/budgets` precedent — a single-user household's template count is inherently small, and pending rows are deleted (not accumulated) once acted on. The frontend's `/recurring` screen (settings list with inline amount/day edit and a stop/reactivate toggle, plus a create form) embeds `PendingOccurrencesWidget` — deliberately prop-less and self-contained so F012's still-unbuilt dashboard can drop it in as-is later, same embeddable-component spirit as F004/F005's `AccountTransactionList`/`AccountTransferList` (which take an `accountId` instead, since they *do* have something to scope by).

A later fix closed a real staleness bug in `setCap`: since the frontend's inline amount/day edit always sends the current month as `effectiveFrom` (`RecurringTemplatesPage.tsx`'s `currentMonth()`), editing a template whose current month has no version yet takes the forward-only new-version branch, not the same-month-replace one — and any `PendingRecurringOccurrence` already generated for a cycle that new version now covers still pointed at the old version id, so it kept showing the pre-edit amount/day until confirmed (`RecurringTemplateController` resolves an occurrence's displayed amount live via `findVersionById`, so a stale version id means a stale display). `RecurringTemplateService.setCap` now calls a private `realignPendingOccurrences` after creating a new version: for every still-pending occurrence of that template, it re-resolves which version `RecurringTemplateVersion.resolveEffective` says should apply now (via a new `PendingRecurringOccurrenceRepository.findByTemplateId`) and repoints it if that changed, leaving occurrences whose cycle is still correctly covered by an older version untouched (preserving what past months showed, per F007 spec). `setCap` is now `@Transactional` too, for the same multi-write reason `confirmPending`/`stop` already are. On the frontend, `PendingOccurrencesWidget` fetches once on mount and takes no props by design, so `RecurringTemplatesPage` now remounts it (via a `key` counter bumped after a successful cap edit or template creation, not a real prop) to force a refetch rather than leaving it stale until a page reload — creation needed the same fix since a new template's `effectiveFrom` also defaults to the current month, so catch-up can immediately generate a pending occurrence for it that the widget wouldn't otherwise pick up.

A post-F007 schema audit (not its own feature) hardened the DB layer with migration `V10__db_constraint_hardening.sql`: `UNIQUE` on `categories.name`/`payment_methods.name`/`accounts.name` (fronted by a create/rename-time application-layer duplicate check — `CategoryNameAlreadyExistsException`/`PaymentMethodNameAlreadyExistsException`/`AccountNameAlreadyExistsException`, 409, exact match/case-sensitive), and `CHECK (amount > 0)` on `transactions.amount`/`transfers.amount`/`budget_versions.monthly_cap`/`recurring_template_versions.amount` — the latter already enforced at both the request DTO (`@Positive`) and domain-constructor layers, so this just closes the third layer to match this codebase's existing defense-in-depth pattern. The audit also broadened `CategoryService.delete()`'s referenced-by-transaction guard (F002/F004) to also check F006's `BudgetRepository.existsByCategoryId` and a new `RecurringTemplateRepository.existsByCategoryId` (F007): a category with a `Budget` or `RecurringTemplate` but zero transactions was previously still hard-deletable, which would have orphaned that row's own FK to `categories` (a raw DB constraint violation surfacing as a generic 500, not the clean 409 `CategoryInUseException` already gives for the transaction case).

## Build / lint / test commands

Local Postgres (required before running the backend):
```
docker compose up -d      # start (data persists in a named volume)
docker compose down       # stop
```
Includes a `pgadmin` service for local database inspection: `http://localhost:5050` (login `dev@myfinances.com` / `myfinances`). The `postgres` server connection is pre-registered via `docker-compose.yml`'s `configs: servers.json` (host `postgres`, port `5432`, user `myfinances`) - pgAdmin still prompts for the password on first connect (Postgres's own dev credentials below), and only seeds this on a fresh `pgadmin` volume, so editing `servers.json` later needs `docker compose down -v` to pick up.

Backend (`/backend`, run from that directory):
```
./gradlew bootRun         # run the API against local Postgres (http://localhost:8080)
./gradlew build           # compile + test + package
./gradlew test            # tests only — needs Docker running (Testcontainers starts its own ephemeral Postgres, see ADR 0010)
./gradlew spotlessCheck   # formatting check (google-java-format); spotlessApply to fix
```
Swagger UI: `http://localhost:8080/swagger-ui.html`. OpenAPI spec: `http://localhost:8080/v3/api-docs`.

Production packaging (F014, `docker-compose.prod.yml` — a wholly separate file from dev's `docker-compose.yml`; see ADR 0006). Not part of the everyday dev loop; for a local smoke test of the prod images:
```
docker build -t ghcr.io/hmcaio/my-finances-backend:local backend
docker build -t ghcr.io/hmcaio/my-finances-frontend:local frontend
cp .env.example .env               # then set IMAGE_TAG=local
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml down -v
```
CI/CD: `.github/workflows/ci.yml` runs backend (`spotlessCheck test`, with Testcontainers providing its own ephemeral Postgres per ADR 0010) and frontend (`npm ci && npm run lint && npm test`, via a runtime check for a `"test"` script rather than a hardcoded step — see F015) on every push/PR, and additionally builds+pushes both Docker images to GHCR on pushes to `main` and on `vX.Y.Z` tags.

Frontend (`/frontend`, run from that directory):
```
npm install               # first time (frontend/.npmrc sets legacy-peer-deps for openapi-typescript)
npm run dev                    # dev server, http://localhost:5173
npm run build                  # typecheck + production build
npm run lint                   # ESLint
npm run format / format:check  # Prettier
npm test / npm run test         # Vitest (jsdom + React Testing Library + MSW, see F015), non-watch, CI-friendly
npm run generate-api-types     # regenerate src/api/generated/schema.ts from the backend's /v3/api-docs (backend must be running)
```

## Structural conventions

- Backend package layout is layer-then-context: `com.chm.myfinances.{domain,application,infrastructure}`, each with one subpackage per aggregate (see `docs/adr/0004-hexagonal-ddd-tdd.md`). `domain/shared` holds the `IdGenerator` port (ADR 0005) and `TextFieldConstraints` (see the free-text field convention below); `infrastructure/persistence` holds the `AuditableEntity` base class every entity with its own table extends.
- Free-text fields are bounded, not unbounded `text`, at every layer: a length check in the domain constructor/mutator (alongside the existing non-blank check for mandatory fields, throwing the same exception type), `@Size(max = ...)` next to `@NotBlank` on the request DTOs, and a matching `varchar(n)` column (narrowed via its own Flyway migration if added after the table already exists). One shared class, `domain/shared/TextFieldConstraints`, holds every such limit — reuse its constants rather than inventing a new number per aggregate: `MAX_NAME_LENGTH` (100) for flat-taxonomy "name" fields (`Category`, `PaymentMethod`, `Account`, and future ones like F008's `InvestmentCategory`); `MAX_DESCRIPTION_LENGTH` (150, mandatory) / `MAX_ADDITIONAL_NOTES_LENGTH` (500, optional) for the narrative "description"/"additional notes" pair on non-taxonomy entities — introduced when F004's `Transaction` replaced its original single optional `note` field with this pair, and reused as-is by F005's `Transfer` and F007's `RecurringTemplate.description`.
- Frontend: `src/api` (typed HTTP clients, one module per aggregate, generated types under `src/api/generated/`), `src/components` (shared UI), `src/features/<area>` (one folder per feature area, mapping to a route).
- Frontend testing (F015): Vitest, configured entirely via `vite.config.ts`'s `test` key (`environment: 'jsdom'`, `setupFiles: ['src/test/setup.ts']`) — there is no separate `vitest.config.ts`. Test files are colocated next to what they test (`*.test.ts`/`*.test.tsx`, e.g. `src/api/categories.test.ts`, `src/features/categories/CategoriesPage.test.tsx`), queried via React Testing Library's accessibility-first queries (`getByRole`, `getByLabelText`) rather than test IDs. `src/mocks/handlers/<aggregate>.ts` (one file per aggregate, mirroring `src/api`) export MSW handler arrays combined in `src/mocks/handlers.ts` and served by `src/mocks/server.ts` (Node `setupServer`), started/reset/closed by `src/test/setup.ts` — every test file gets MSW automatically. `frontend/.env.test` sets `VITE_API_BASE_URL=/api` (relative, same-origin — like `.env.production`) so the axios base URL and MSW's relative handler-path matching resolve against the same jsdom-default origin. `src/test/setup.ts` also calls React Testing Library's `cleanup()` itself in `afterEach`, since Vitest's `globals: true` (which would let RTL auto-register that) is deliberately off here.
- Frontend API clients share one Axios instance (`src/api/client.ts`), configured entirely from `VITE_API_BASE_URL` (`.env.development`/`.env.production`) — that base URL already includes the `/api` prefix, so every call site uses a bare relative path (e.g. `apiClient.get('/categories')`), never a hand-built `${API_BASE_URL}/api/...` string. Errors are unwrapped via `unwrap()`/`ApiError` in `src/api/apiError.ts` (Axios throws on non-2xx, unlike `fetch`) — a `409` can carry a call-site-specific `conflictMessage`.
- Every commit follows Conventional Commits (`docs/adr/0009-conventional-commits.md`).
- Backend config is split by Spring profile: `application.yml` holds only settings identical across every environment, plus `spring.profiles.default: dev`. Environment-specific values (datasource, `server.address`) live only in `application-dev.yml` / `application-prod.yml` — never in the base file, so nothing environment-specific is ever silently inherited across profiles. There is no `application-test.yml`: backend tests get their datasource from a Testcontainers-provisioned Postgres via `@ServiceConnection` instead of a profile file (ADR 0010).
- Application-layer "use case service" shape (established in F002, `application/category/CategoryService.java` / `application/paymentmethod/PaymentMethodService.java`): one `@Service` per aggregate, constructor-injected with its domain repository port and (when it creates new entities) `IdGenerator`; plain methods named after the use case (`create`/`rename`/`delete`/`findAll`, not generic CRUD verbs). A `{Aggregate}NotFoundException` in the same package, annotated `@ResponseStatus(HttpStatus.NOT_FOUND)`, is thrown by `findById(...).orElseThrow(...)` — no `@ControllerAdvice` needed for that mapping.
- One cross-cutting `@RestControllerAdvice` exists — `infrastructure/web/GlobalExceptionHandler.java` — and it is the only one there should ever be: a single `@ExceptionHandler(Exception.class)` that returns a fixed, generic 500 body (`{"message": "An unexpected error occurred"}`) for anything genuinely unforeseen. It rethrows (does not handle) any exception already carrying `@ResponseStatus` (the `{Aggregate}NotFoundException` pattern above) or already implementing Spring's `ErrorResponse` contract (e.g. `NoResourceFoundException` for an unmapped route), so those keep working exactly as before. A new *expected* error case (another 404, a 409, etc.) should get its own `@ResponseStatus`-annotated exception per the existing pattern — do not add a second catch-all advice or a new `@ExceptionHandler` for a specific type here. Backed by `spring.web.error.include-stacktrace`/`include-message`/`include-binding-errors: never` in the shared `application.yml` as defense in depth (Spring Boot 4.x deprecated the old `server.error.*` spelling of these in favor of `spring.web.error.*`).
- Repository adapter shape (`infrastructure/persistence/<aggregate>`): a package-private Spring Data `JpaRepository` interface, a `@Component` adapter implementing the domain's repository port and translating to/from the JPA entity (`reconstitute(...)` on the domain side), and the JPA entity itself extending `AuditableEntity` with Lombok `@Getter`/`@Setter`/`@NoArgsConstructor` (Lombok is fine here — ADR 0005 only forbids it on domain classes).
- **Spring Boot 4.x removed most test-slice annotations** (`@DataJpaTest`, `@WebMvcTest`, `@AutoConfigureMockMvc`, `@AutoConfigureTestDatabase`) and `TestRestTemplate` from `spring-boot-test`/`spring-boot-test-autoconfigure` — confirmed by inspecting the actual jars in F002, not assumed. Persistence- and REST-layer integration tests therefore use full `@SpringBootTest` + `@Import(TestcontainersConfiguration.class)` + `@Transactional` (for automatic rollback between tests) instead of a slice; for REST-layer tests, build `MockMvc` by hand via `MockMvcBuilders.webAppContextSetup(webApplicationContext).build()` inside a `@BeforeEach`, using a plain `WebApplicationContext` field and a locally-constructed `ObjectMapper` (not autowired — there's no `ObjectMapper` bean by default). `TestcontainersConfiguration` (`backend/src/test/java/com/chm/myfinances`) is `public` so tests in any package can `@Import` it.

## Source of truth

**Read [docs/PRD.md](docs/PRD.md) before making any architectural or scope decision.** It is the authoritative, detailed spec for this system — data model (entities, versioning rules, net worth formula), functional requirements, tech stack, and explicit non-goals. Do not re-derive product decisions from first principles; the PRD already resolved many non-obvious tradeoffs (e.g. why credit card spend is a liability-increasing expense and payments are transfers, why budgets/recurring templates are versioned instead of mutated in place, why recurring-occurrence generation is lazy/catch-up rather than a real-time scheduler).

## Planned architecture (from the PRD)

- **Backend**: Java + Spring Boot, built with Gradle; Flyway for schema migrations.
- **Frontend**: React + TypeScript, built with Vite, Material UI (MUI) for components/theming, React Router for client-side routing.
- **Database**: PostgreSQL, run via Docker Compose for local dev.
- **Methodology**: Domain-Driven Design (entity clusters as aggregates — Account+Transfer, Budget+BudgetVersion, RecurringTemplate+RecurringTemplateVersion, the Investment* cluster), Hexagonal Architecture (domain/business logic isolated from Spring/JPA/Postgres behind ports), Test-Driven Design (tests-first for the rules-heavy logic: net worth calc, versioning, recurring catch-up generation).
- **Runtime model**: local, single-user, no auth, bound to `localhost` only, run on-demand (brought up/down by the user) rather than kept always-on — this is why recurring-template generation must be catch-up-based, not cron-based.
